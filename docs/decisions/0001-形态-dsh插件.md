# ADR 0001：形态决策 — skyaxis 作为 deepseek-harness 的独立插件

| 字段 | 值 |
| --- | --- |
| **状态** | 接受 |
| **日期** | 2026-09-19 |
| **记录人** | Claude（基于用户决策） |

---

## 背景

skyaxis 的目标是在 AI agent 之上做一层"工作流薄壳"，让 AI 编程任务的进度、产出、上下文从聊天框里"长出来"，变成可被管理的对象。

在讨论产品形态时，用户明确选择了 **"作为 deepseek-harness（DSH）的独立插件"** 这一形态，而不是：

- 独立 CLI / TUI 工具
- 独立桌面 GUI 应用
- 独立 Web 面板 + 后端服务
- 中立的 SDK / 协议层中间件

[DSH（DeepSeek-Harness）](https://github.com/deepseek-ai/deepseek-harness)（MIT 协议）的核心理念是 **"Everything is a Plugin"**：模型、工具、技能、会话（session）、沙箱、存储、循环、调度、UI 全部都是插件，由 Cordis 微内核负责插件加载、卸载、依赖路由。

---

## 决策

**skyaxis 以 deepseek-harness 的"独立插件"形态存在，而不是独立产品。**

具体含义：

1. skyaxis **不自己实现** agent runtime，直接复用 DSH 提供的模型、tool contract、sandbox、session、storage 等基础设施。
2. skyaxis 的价值集中在 **"信息流管理层"** —— 消费 DSH 的 trajectory / session / ui 事件，做多 session 管理、进度可视化、产出归档。
3. skyaxis **跟随 DSH 的插件 API 演进**，不承诺向后兼容旧版 DSH。
4. skyaxis 命名上仍保持"独立"，但运行时寄生在 DSH 上。

---

## 后果

### 正面

- **开发成本最低**：不用造 runtime，不用处理 KV cache / sandbox / tool contract / agent loop。
- **天然契合"薄壳"定位**：DSH 已把 session / trajectory / ui 插件化，skyaxis 只需要在它们之上做管理层。
- **可观测性复用**：直接消费 DSH 的 [Trajectory](https://deepseekharness.wiki/)（追加式事件流，支持回溯、分叉、重放）作为进度信号源。
- **跨 agent 潜力**：DSH 中立，未来可接入更多底层模型 / 工具，skyaxis 的插件不绑死单一 agent。
- **快速验证**：插件形态允许用最小 demo 验证产品假设，不必先做完整 runtime。

### 负面 / 风险

1. **宿主依赖**：skyaxis 的生命周期与 DSH 强绑定。
   - **假设**：DSH 能稳定到 MVP 完成（DSH 当前为 Developer Preview，迭代快、可能有破坏性变更）。
   - **验证手段**：跑通一个最小 DSH 插件 demo 后重评此假设。
2. **用户群受限**：skyaxis 的潜在用户 = DSH 用户。如果 DSH 没起来，skyaxis 也没用户。
3. **护城河压力**：DSH 内置一个"信息流管理面板"插件的门槛很低。skyaxis 必须提供比 DSH 内置更深的价值。
   - **候选护城河**：跨 session 知识沉淀、跨 agent 适配、产出归档、个人知识库。
4. **脱离成本**：MIT 协议下未来若想脱离 DSH 独立，需要再设计一套抽象层，提前埋下成本。

## 备选项（已考虑，未选）

| 备选形态 | 未选原因 |
| --- | --- |
| 独立 CLI / TUI 工具 | 开发成本低，但与现有 CLI agent 形成"多 CLI"心智负担，不解决"信息流管理"的根痛点。 |
| 独立桌面 GUI 应用 | 视觉体验好，但开发成本显著上升，且与 agent runtime 重复造轮子。 |
| 独立 Web 面板 + 后端服务 | 可视化最丰富，但形态最重、部署最复杂，与"薄壳"定位冲突。 |
| 中立 SDK / 协议层 | 想象空间最大但最早期，技术与产品风险都最高，且与个人开发者的"开箱即用"诉求冲突。 |
