## 背景：为什么此刻做命名审视

「模块」是 research 0006 调研时随 spec-driven 方法论（Kiro/BMAD 系工具词汇）未经本项目审视搬入的——决策 0005 的 D5 只裁过「AI 工作台」这个产品名，从未裁过领域对象命名。起手轮收口后、第二刀（工作包面 + S2/S3 UI）动工前是最后的免费改名窗口：再晚一步，术语就会出现在用户界面、用户词汇和 `$DSH_HOME` 真实文件名里。

## D8「模块」→「工作包（work package）」，id 前缀 WP

**选择**：WorkbenchModule 概念整体更名工作包；id 序号 `M1/M2…` → `WP1/WP2…`（wire 正则 `^WP[1-9]\d*$`，文件名模板 `plans/WP1-v2.md`）；代码标识符 `WorkbenchModule`/`moduleId`/`isModuleId` → `WorkbenchWorkPackage`/`workPackageId`/`isWorkPackageId`。

**定义（本裁决钉死的口径）**：需求经拆分（硬门①批准的是工作包**清单**）产生的最小工作单元；每个工作包持有一份版本化实施计划（硬门②批准的是具体版本），执行以**任务书**（D9）下发给 session 承接（承接事实记入 `sessions[]` 绑定，analysis/dev/review 可多条），以用户验收（硬门③）为完成判据。

**为何准确**（从数据模型反推的七项职责：版本化计划基线 / 可独立委派 / 验收判据与返工历史 / 生命周期含弃置 / criteria 覆盖载体 / 依赖 DAG 节点 / 范围边界声明——全部是 PMBOK 工作包的经典语义，无一是代码结构语义）；七态映射零勉强：planned=拆分登记、plan-draft/plan-approved=计划基线前后、in-dev=执行中、built=执行方声明完成、accepted=用户验收、dropped=弃置——「built ≠ done」恰为「声明完成 ≠ 工作包关闭」的 PM 表述。

**为何否决**：**任务**——本仓 task-graph 已占用该词（session 内 task DAG 节点），跨特性撞名硬伤；**交付项/交付单元**——与阶段⑤「交付」撞车；**子需求**——暗示 requirements.yaml 嵌套；**执行单元**——只覆盖执行半边，漏验收语义。

**实施连带**：decisions/0005 细化②的 moduleId 正则（`^M[1-9]\d*$`）与「M 序号」表述随第二刀联动改为 WP 口径（见 0005 修订记录同轮条目）——**发布前重命名，无任何生产数据引用旧模板，细化①布局模板冻结的破坏性迁移条款不触发**（该条款保护的是发布后漂移）。

## D9「上下文包」→「任务书（statement of work）」

**选择**：research 0006 §7.1 的 bundle 概念整体更名任务书；en 名 statement of work（UI 标签随 P2 词典四处同步定稿）。

**定义**：以某个工作包为主体、下发给 session 的**出站委派文件**——需求快照 + PRD 节选 + 该工作包的边界/依赖/已批准计划正文 + 按 trigger 匹配的知识注入 + 声明块回执格式约定；盖 revision 戳（「生成于 revision N，之后账本变更不自动同步」），一次性，用完即弃、从不入库。

**方向性四测**（本裁决的判定准绳，源于用户的批评）：①单向出站（只能被「下达」，绝无「汇报回来」读法）；②含委派语义（叫对方干活，非情况通报）；③自含上下文（装得下依据/范围/要求/回执格式）；④一次性快照（账本变更重新生成，如现实中的补充任务书）。工程实务佐证：设计任务书本就规定交付物与格式——「输出约定」是任务书原生部件而非外挂；实务中按用途分化（勘察/设计/施工任务书）恰对应 purpose 枚举（分析/开发/评审任务书）。

**为何否决（死因链）**：**上下文包**——与工作包撞「包」字，口语「这个包」必然歧义；**会话简报**——「简报」汉语主导义是「简短的报告」（新闻简报/汇报简报，回来的结果一方），英文 briefing 的出站义在中文语感立不住，方向测试①失败；**派工单**——「单」是薄单据形态，装不下带 PRD 节选与计划正文的书卷，且与通用工单系统词汇纠缠；**交底单**——方向语义最准但行业黑话浓度过高。

**与工作包的关系**：任务书是以某个工作包为主体的**出站投影**（「WP3 的任务书」）；工作包是账本持久对象，任务书是把它喂给 session 的一次性载具——对象/载具/登记三分，委派动作只发生在任务书下达那一刻。

## D10 声明块保留（「任务回执」质疑驳回）

**质疑**（用户 2026-09-29）：回传物为什么不叫任务回执？

**驳回**：认识论状态不匹配——**回执是已证实事实的凭证**（签收单/收条：交易已完成、内容已成立、权威性内建），**声明块四字段全是待裁决主张**：`built` 仍需用户验收（AI 声明≠完成）、`artifacts` 入 pending 待确认、`knowledge` 入候选审阅队列、`stageReady` 仅是提议（AI 永远无权推进阶段）。把待检验的东西叫「回执」，名字本身就把「需查验」洗成「已证实」，直接推翻 built≠done 与四权模型——**裁决纪律的第一道门就是这个词**。类比：声明块是报关单（自报内容、查验后放行），不是签收单。「块」为形态词（session 结尾的 fenced yaml 机器可读块，P3 端点逐字段容错解析）；wire 标记即 `# skyaxis-declare`。诚实预期依据（research §7.1 原文）：「声明块依赖模型遵循度，是半自动而非全自动」——回执承担不起被伪造，声明的字面姿态就是待核。

**连带口径**：任何图注/文档不得将声明块注为「回执」（本轮混淆源即此）。

## 术语体系总表（四方向四词，零重叠）

```
工作包 WP3（持久对象，账本结构）
   │ 出站·委派    ──▶  任务书（下达：开工依据 + 声明块格式约定）
   │ 承接·登记    ◀──  sessions[] 绑定（台账：谁、何时、何种用途）
   │ 回传·主张    ◀──  声明块（自报：built/artifacts/knowledge/stageReady）
   │ 收口·裁决    ──▶  验收 acceptances（硬门③：用户查验后才成立）
```
