# 决策 0011：克隆分支检出（远程同名分支探测与跟踪检出）

> 日期：2026-10-15
> 依据：用户实机缺陷反馈——关联克隆仓库 A（远程已有开发分支 `leizhuang/feat-0831-量本利操作成本线上化`）后，产出的是起点错误（基于默认分支 tip）且无 upstream 跟踪的本地同名分支；git 语义经本机 git 2.55 实测核验（Plan agent 校验轮）。
> 状态：**已拍板**——修订 [决策 0003](0003-仓库池P0决策-路线B专属repos-yaml与校验策略.md) P3b 引擎的 `checkout -b` 无条件建支取舍，补上远程同名分支的跟踪检出臂。

## 背景

[决策 0003](0003-仓库池P0决策-路线B专属repos-yaml与校验策略.md) P3 的克隆链路是 `git clone --progress`（不带 `--branch`/`--single-branch`，全量克隆，HEAD 落在远程默认分支）+ `git checkout -b <branch>`。`-b` 无条件在当前 HEAD 新建本地分支：对「远程还没有该分支、从零开新分支」场景是正确取舍（对任何合法分支名都成功，preflight 只做 `check-ref-format --branch` 名字校验、零网络）；但当远程**已存在**同名分支时（clone 已把 `refs/remotes/origin/<branch>` 抓到本地 refs），产出的是不相干同名分支——远程分支上的提交全不在本地分支上，且无 upstream（`git pull/push` 报 no upstream）。附带边角：branch 恰好等于默认分支名时 `-b` 撞 already-exists → bad-branch。

## D1 探测命令——本地 show-ref，零网络（已拍板）

clone 成功后、checkout 前加一次 `git show-ref --verify --quiet refs/remotes/origin/<branch>`（git 2.55 实测退出码：存在 0 / 不存在 1（坏名同 1，且 preflight `check-ref-format` 已双重拦截）/ 非仓库 128——clone 刚成功的 dest 上不可达，即便到达走 `-b` 臂也只是退化为修复前行为）。**一切非 0 走新支臂**，无需区分 1/128。备选 `rev-parse --verify --quiet` 同语义弃用（show-ref 是纯 ref 存在性语义）。探测期间沿用 `status='branching'`——状态机零新增，wire 协议（`CloneTaskSnapshot.status` 内联联合）零改动。

## D2 跟踪臂形态——`checkout -B <branch> --track origin/<branch>`（已拍板）

探测 exit 0 ⇒ `git checkout -B <branch> --track origin/<branch>`；非 0 ⇒ 维持现状 `checkout -b <branch>`（命令逐字不变）。两个理由链：

- **`-B` 双理由**：① 兜 branch==默认分支名边角——fresh clone 已有同名本地分支，`-b` 必撞 already-exists，`-B` 是同 commit reset（零工作树变更）+ 重新断言 upstream + 留在检出态（`checkout -B`/`switch -C` 明确允许重置当前检出分支，与 `git branch -f` 的拒绝语义不同）；② 远程有且≠默认名时 `-B`≡`-b` 建支。`-B`+`--track` 组合自 git 1.7.3（2010）无版本坑。
- **显式 `--track` 的正确依据是防用户全局 `branch.autoSetupMerge=false`**（默认 true 会对 remote-tracking 起点自动建 upstream，设 false 则两参形式也不建跟踪）。**显式澄清：与 `checkout.guess` 无关**——guess 只影响单参形式 `git checkout <branch>` 的 DWIM 建支，两参 `-B <branch> <start-point>` 的 start-point 无条件解析。此处记档防止后人以「guess 无关」为由把这个防御「修正」掉。

非 ASCII（中文）分支名零新增风险：subprocess 直传 argv（无 shell、CreateProcessW UTF-16 通道），preflight 的 `check-ref-format --branch <中文>` 与既有 `checkout -b <中文>` 已走同一通道。

## D3 失败与取消语义——provider 故障响亮失败，abort 梯子同构复用（已拍板）

- **probe spawn/reject 失败（provider 级故障）⇒ cleanupDest + settleFailure('unknown')，不回落 `-b`**：同一 provider 上的 checkout 大概率同样失败（回落只是把失败挪后一步）；若只是抖动，回落 `-b` 会静默产出错误起点的本地分支——恰是本决策要修的东西。响亮失败优于静默错误数据，与既有 checkout spawn-undefined 模式同构。红利：`settleFailure` 从 probe handle 的 stderr 取首行作 detail。
- **abort**：probe 子进程经 `#spawnGuarded`（带 `task.controller.signal`）并在 spawn 后立即停靠 `task.handle`（terminate 打在活进程上）；continuation 先查 `signal.aborted` 再读 exitCode；`abort()` 即时 settle + `settleFailure` 终态幂等——三层与 clone/checkout 臂完全同构。
- 代码形状：`#drive` 拆出 `#branchPhase(task, exe)`（probe → 两臂 checkout → 终态），不抽通用 runner（两臂 settle 逻辑同形，回调参数反而藏 abort 语义）。

## D4 波及与基线（已拍板）

- reclone（`#check`→`begin`→`#drive`）天然继承同一探测臂。
- endpoint.test.ts 的 clamp 式 fake（outcome 队列不足时取末位）对插入的 probe 透明——全 0 队列自动走跟踪臂，零改动通过。
- protocol/客户端/词典零改动；测试 1077→1080（+3：`-b` 臂 argv / abort during probe / probe provider 失败）。
