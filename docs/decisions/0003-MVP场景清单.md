# ADR 0003：MVP 场景清单 — skyaxis 第一版要解决的 6 个核心场景

| 字段 | 值 |
| --- | --- |
| **状态** | 接受（带风险标注） |
| **日期** | 2026-09-19 |
| **记录人** | Claude（基于用户决策） |

---

## 背景

按 CLAUDE.md 第 5 节议题 2 + 阶段切换条件第 3 条，**MVP 范围必须在立项阶段锁定**。MVP 范围由"要解决的场景集合"定义。

ADR 0001 锁定形态（DSH 独立插件），ADR 0002 锁定定位（可视化向），二者共同锚定了 skyaxis 的产品方向。在此基础上，需要进一步锁定 **MVP 要覆盖的具体场景集合**。

候选场景从用户原话痛点和 ADR 0002 隐含方向中抽取，由用户在立项讨论中**主动扩张**到 6 个场景——含一个原"暂缓项"被提升到 MVP，以及一个"高模糊度新增项"经澄清后落入 MVP。

---

## 决策

**MVP 场景清单（接受，含 6 个场景）**：

| # | 场景 | 来源 | 在定位中的角色 |
| --- | --- | --- | --- |
| **A** | 单 session 内进度可视化（任务树 / 时间线 / 进度条） | ADR 0002 隐含 | **核心**（session 内进度） |
| **B** | 跨 session 产出聚合可视化 | ADR 0002 隐含 | **核心**（跨 session 产出） |
| **C** | 多 session 总览与状态可视化 | 用户原话痛点（A 方向缓解） | **缓解**（补回多 session 心智爆炸痛点） |
| **D** | session 决策 / 代码片段归档与检索 | 用户原话痛点（C 方向部分） | **增强**（已从"暂缓项"被用户主动提升） |
| **D1** | session 内 task DAG（任务间的并行 / 串行依赖） | 用户新增"依赖图"澄清 | **A 的增强** |
| **D2** | session 间输入 / 输出依赖图 | 用户新增"依赖图"澄清 | **B 的增强** |

**显式不进 MVP 的方向**（用户主动排除）：

| 排除项 | 排除原因 | 后续位置 |
| --- | --- | --- |
| **D3**（session 间文件 / 模块冲突视图） | 实现复杂度高，需 git 集成 + file watcher | 迭代候选 |
| **D4**（跨项目 / 跨仓库依赖） | 最复杂，需跨项目元数据 | 迭代候选 |
| C 方向完整版（跨 session 知识沉淀 + 智能检索） | 起步较慢 | 后续迭代 |

---

## 后果

### 正面

- **完整覆盖用户原话痛点**：A + B + C + D 覆盖"被困在聊天框里"和"上下文切换成本高"两个核心痛点。
- **D1 + D2 让"需求进度可视化"真正立体**：从线性进度（A）推进到 DAG（D1），从单 session（B）推进到跨 session 依赖（D2）。
- **护城河更深**：相比 ADR 0002 原本暗示的"任务树 + 时间线"两件套，D1 / D2 把可视化推进到 DAG 和跨 session 维度，与 DSH 官方内置的差异化更强。

### 负面 / 风险（**重点标注**）

1. **MVP 范围宽**：6 个场景 vs. ADR 0002 隐含的 3 个场景，**实现工作量翻倍**。
   - **风险**：每个场景做不深，"什么都做一点、什么都不精"，反而稀释护城河。
   - **缓解手段**：在 `docs/milestones/roadmap.md` 中显式划分 MVP 子阶段（如 v0.1 / v0.2 / ...），把 6 个场景分配到不同子阶段，**先深后广**。
2. **D（归档检索）已被用户从暂缓项主动提升**：
   - **风险**：D 涉及"沉淀什么 / 沉淀格式"的设计问题，可能反向推迟 MVP 完成时间。
   - **缓解**：D 的早期版本仅做"决策与代码片段的**只读归档 + 全文搜索**"，不做语义级智能检索。
3. **D1（task DAG）依赖 DSH 事件流的足够细粒度**：
   - **假设**：DSH trajectory 暴露的 task / subtask 事件足以重建 DAG。
   - **验证手段**：跑通最小插件 demo 后，确认 DSH 是否原生支持 task DAG；若否，D1 降级为 A（任务树）。
4. **D2（session 间依赖）涉及 session 输入 / 输出契约**：
   - **风险**：DSH 是否原生支持"session 输出作为另一 session 输入"的契约？若否，D2 需要 skyaxis 自建一层抽象。
   - **验证手段**：跑通最小插件 demo 后，确认 DSH 是否暴露 session 间通信能力。
5. **A 与 D1 的边界**：
   - **风险**：A（任务树 / 时间线 / 进度条）与 D1（task DAG）在 UI 层可能重叠。
   - **缓解**：A 是基础视图（线性进度），D1 是高级视图（DAG），两者**并存而非互斥**；MVP 阶段 A 先做，D1 后做。

## 备选项（已考虑，未选）

| 备选范围 | 未选原因 |
| --- | --- |
| **MVP 只含 A + B + C**（ADR 0002 隐含） | 用户主动扩张，认为 D 与 D1 / D2 都是核心需求。 |
| **MVP 含 A + B + C + D**（含 D，不含 D1 / D2） | 用户认为 D1 / D2 也是 MVP 必备。 |
| **MVP 含 A + B + C + D + D3 + D4** | D3 / D4 实现复杂度高、用户主动排除。 |
