| --- | --- |

## 背景

按 CLAUDE.md 第 4.4 节"阶段切换条件"第一条，**一句话定位得到用户书面确认**是立项阶段切到下一阶段的硬性前置。这一句话定位将作为后续"用户画像 / MVP 范围 / 业务对象 / 里程碑"的共同锚点。

ADR 0001 已锁定形态（skyaxis 作为 deepseek-harness 的独立插件）。在形态锁定后，定位需要同时回答三件事：

- skyaxis 是什么
- 给谁用
- 和现有工具的差异

针对这三点，候选了三个版本的"一句话定位"：

- **A 版本（多 session 管理向）**：skyaxis 是 deepseek-harness 的个人开发工作流插件，让个人开发者像管理本地项目一样管理多个 AI session。
- **B 版本（可视化向）**：skyaxis 是 deepseek-harness 的 AI 编程可视化插件，把 session 内的进度和跨 session 的产出变成可被一眼看清、可被回溯的对象。
- **C 版本（产出归档向）**：skyaxis 是 deepseek-harness 的个人 AI 知识沉淀插件，把每个 AI 编程 session 的代码改动、决策、上下文沉淀为可被检索的个人知识库。

用户选择 **B 版本**。

---

## 决策

**一句话定位（已接受）**：

> **skyaxis 是 deepseek-harness 的 AI 编程可视化插件，把 session 内的进度和跨 session 的产出变成可被一眼看清、可被回溯的对象。**

### 拆解

| 维度 | 内容 |
| --- | --- |
| **是什么** | deepseek-harness 生态的 AI 编程可视化插件 |
| **给谁用** | 个人开发者 / 一线开发工程师（与 CLAUDE.md 第 3 节"目标用户"一致） |
| **和现有工具差异** | 把 session 内的进度 + 跨 session 的产出"长出来"，而非困在聊天框里 |

### 隐含的产品方向

- **核心能力**：
  - session 内的进度可视化（单一 session 内的过程清晰化）。
  - 跨 session 的产出可视化（多 session 之间的产出聚合与回溯）。
- **隐含取舍**：
  - **不主打开箱即用的多 session 列表 UI**（A 方向）——这是 DSH 容易自己做的部分。
  - **不主打开箱即用的知识沉淀 + 检索**（C 方向）——MVP 起步较慢，留作后续迭代候选。
- **可视化形态（待细化）**：可能包含进度条、任务树、时间线、依赖图等多种表达。**立项阶段不细化形态**。

---

## 后果

### 正面

- **差异化清晰**：不是再多一个 session 列表 UI，而是把 session 内的过程信息与跨 session 的产出信息"立体化"。
- **复用 DSH 事件流**：DSH 的 Trajectory（追加式事件流）天然提供可视化所需的原始信号。
- **护城河起点**：A 方向容易被 DSH 内置吃掉；C 方向 MVP 起步慢。B 方向介于两者之间，既有差异化空间，又能用最小 demo 快速起步。

### 负面 / 风险

1. **"可视化"定义模糊**。
   - **假设**：第一版聚焦"任务树 + 时间线"两种最常见的可视化形式。
   - **验证手段**：跑通最小插件 demo 后回看是否要调整可视化的具体形态。
2. **A 方向被弱化**：如果用户的核心痛点其实是"同时开多个 session 心智爆炸"，B 版本可能在 MVP 中没充分覆盖该痛点。
   - **缓解**：跨 session 的产出可视化天然承载"多个 session 摆在一起看"的价值，不至于完全缺失多 session 视角。
3. **C 方向的"沉淀 / 检索"被推迟**：用户原话提到"上下文切换成本高"，B 版本主要解决"看"的问题，"沉淀 / 跨 session 复用"留到后续迭代。
   - **缓解**：在 `docs/scope/` 显式标注 C 方向为"暂缓（不进入 MVP）"，避免后续无意识地扩张。
