## D1 渲染范围：所有状态常驻（首节）

待计划（planned/plan-draft）是缺口最痛面（计划区只有占位句），但 boundary 的阅读需求贯穿生命周期：in-dev 期 dev 侧对照边界、built/accepted 期验收人回看「这包当初说好做什么」。条件渲染（仅待计划显）会引入两套弹窗形态且计划批准后内容凭空消失——反直觉。常驻无分支：代码更简、测试只钉「planned 与 in-dev 都在场」。位置取**首节**（计划区之上）：详情打开第一眼即任务陈述，先「是什么」后「怎么做」。

## D2 内容来源：台账字段直渲染（正身，非快照）

拆分结果文档的每包小节（序号/标题/边界/依赖/覆盖标准）正是这些字段的原文名——拆分会话按任务书输出契约写文档、工作台机器抽取成提议、采纳后落台账。**台账是采纳后的正身**（可经表单编辑），文档是拆分时点快照——详情以台账为准更对。字段语言逐字复用 ② 列表行（`wp.boundaryLabel` 家族既有键）：边界正文块（pre-wrap 尊重多行）＋ 依赖/覆盖标准 meta 行（空臂显 `—`）＋ 并行标随标题行。否决项「另拉拆分文档原文切片」：多一次 artifacts 请求＋客户端按标题切片的脆弱解析，内容与台账字段同源重复——仅在需要文档里超出结构字段的自由行文时才值得，现状无此需求，且**不留接口**（防蔓延）。
