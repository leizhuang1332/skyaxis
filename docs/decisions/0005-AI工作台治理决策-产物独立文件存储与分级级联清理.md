## 背景与总原则

AI 工作台 P1b 数据面动工前须钉死 schema 所依赖的全部治理裁决。本文一次收口 research 0006 §11 的 D1-D7，并把 D4 拍板牵出的细化项（落点 / 引用形态 / 版本化 / 缺失降级 / 短文本边界）与批判轮补出的遗漏维度（草稿并发语义、任务书缺失降级、路径钉死、产物导出承诺）一并裁决。

全程有效的不变约束：

- observe-only 9 服务白名单；DSH 仓零修改；DSH 钉 0.1.5-rc.2。
- `workbench-shared/protocol.ts` 零依赖铁律：wire 字段只用手写 guard；host 半 zod 镜像 + 双向可赋值断言。
- 字段演进纪律：新字段一律 optional/default + guard 同步放宽（0003「一行旧数据炸整文件」教训）。
- 诚实口径：数据缺失不渲染占位；built ≠ done（批准拆分 / 批准计划 / 验收确认 / 阶段推进四权永不在 AI 手里）。
- 账本信封范式：`{version, revision, records[]}`、原子写（tmp→bak→rename 退避）、内部队列串行、乐观锁、坏文件降级拒写；**双写纪律「账本提交成功后才做目录副作用，失败残留方向必须是有引用无目录」**（repos link/unlink 先例，`src/repos-pool-host/endpoint.ts:166-182`「Only a committed unlink is destructive」）。
- 跨账本边界（milestone 0002「独立文件互不持有状态」，0004 公式化）：读路径 join 容错、互不持外键。**D6 级联是对该边界写路径的首个实质例外**，论证见 D6 节。

## D4 存储形态：产物独立文件 + 账本内引用（已拍板）与五项细化（已拍板）

**已拍板（用户 2026-09-29）**：计划文档、评审报告等结构性正文一律独立文件，账本记录只持有引用性元数据，不走 inline。理由：整文件式账本每次保存全量重写，20 工作包 × 50KB/需求会把 workbench.yaml 推至 MB 级；账本回归纯元数据后体量与 requirements.yaml 同级，R4（yaml 膨胀）消解。

### 细化① 落点：`$DSH_HOME/skyaxis/workbench/<requirementId>/`（否决工作区邻接与扁平前缀）

**选择**：与账本同居插件目录，按需求分目录。路径模板（`dshHomePath` 变参 join，`src/index.ts:39/54` 已用同款建两个 FileStore）：

```
账本      $DSH_HOME/skyaxis/workbench.yaml
          $DSH_HOME/skyaxis/knowledge.yaml
计划文档  …/skyaxis/workbench/<requirementId>/plans/<workPackageId>-v<version>.md
评审报告  …/skyaxis/workbench/<requirementId>/reviews/<reviewId>.md
软删墓碑  …/skyaxis/workbench/.trash/<requirementId>-<ISO8601 时间戳>/
```

端点前置照 prdContext 形态改写（`src/requirements-host/prd-endpoint.ts:57-66`）：账本可读（409）→ 记录存在（404）→ **删除 no-workspace 检查**（产物不依赖工作区绑定，S1 无工作区也能手动添加发现/写计划）。D6 级联清理单点：一个 `<requirementId>/` 目录覆盖该需求全部产物。

**为何否决**：**工作区邻接**（`<workspacePath>/workbench/`）——no-workspace 400 卡死无工作区需求的产物写入；workspace 换绑/移动后引用全量悬空且悬空原因成谜（目录还在旧位置）；research §6.3 明文反对产物混入用户工作区。三重死因。**扁平 + 文件名前缀编码**——requirementId/workPackageId/version 三元编码进文件名，名字约定既是存储又是唯一归属索引（与账本双真源），按前缀批量删的误删面大于删目录。

**显式假设（非挂起验证）**：「DSH 宿主不触碰插件自管子目录」——现有 `$DSH_HOME/skyaxis/` 下 repos.yaml / requirements.yaml / workspaces/ 在生产运行未被清空，即事实证据；失效最坏后果 = 产物丢失（与孤儿容忍面同构），记档不阻塞。

**布局模板 v1 冻结**：模板本身是隐式契约——约定式推导（细化②）下模板一变，旧账本引用按新模板拼出的路径全部悬空，旧文件必须迁移。故**布局模板变更视为破坏性迁移，须修订本 ADR**；细化②的真实优势是「wire guard 与账本 schema 不变」，不是「免数据迁移」。

### 细化② 引用形态：约定式推导——账本只存 version，host 按约定拼路径（否决显式路径字段）

**选择**：plans 条目收敛为 `{ version: number, approvedAt?: string, note?: string, contentHash?: string }`（去掉 doc 字段；contentHash 见细化③）。路径 = host 内部纯函数（如 `planDocPath(requirementId, workPackageId, version)`），browser 永不接触路径。同款先例：unlink 时目录位置由名字快照经 `repoDirName` 重推导、账本从不存路径（`src/repos-pool-host/endpoint.ts:177-181`）。

防御双层：wire 窄正则 guard（workPackageId `^WP[1-9]\d*$`、version `^[1-9]\d*$`、reviewId `^[A-Za-z0-9-]{1,64}$`）+ host join 前再断言（防 wire 被绕过/字段来源变化）。产物文件名由约定生成（uuid + WP 序号 + 整数版本），不需 PRD 式用户名消毒（`sanitizePrdFileName` 面向用户手输名）。

**为何否决**：**显式相对路径字段** `doc: 'plans/WP1/WP1-v2.md'`——路径知识泄漏进 wire 与 browser 半边；穿越消毒义务须把 PRD sanitize 整套搬进 shared；目录调整背永久兼容读包袱（0003 复杂形态温床）。**doc 只存文件名**——doc 与 version 双自由度可各自演化出不一致，对账多出第三种悬空形态。

### 细化③ 版本化与防漂移：每版本一文件 + contentHash + 账本先行（否决单文件覆盖与无 hash）

**选择**：每版本一独立文件（`WP1-v2.md` 天然定名，引用确定、重试幂等、审计轨迹完整）；账本条目记 `contentHash`（host 侧 node:crypto sha256——host 引 node 无约束，hash 过 wire 只是 string 字段，protocol 零依赖不受影响；旧数据无 hash 字段则 guard 放宽、读时不告警，字段演进纪律）。

写入管线（计划新版本为例）：

1. host load 账本 → 记录/工作包存在（404）；
2. **version 由 host 分配**（该工作包 plans 现状 max+1），client 只传内容不传 version——消除 client 侧并发撞名（`src/requirements-host/endpoint.ts:104` uuid host 兜底分配是最近似形态，属新设计记档）；
3. host 算 contentHash；
4. **账本先行**：`file.save(expectedRevision, …)`，409 在此返回、零文件副作用；
5. save 成功后写文件：mkdirSync recursive + tmp + rename（FileStore 原子写同构）。

**已批准版本锁定（端点契约，批判轮补）**：写端点守卫「目标 version 条目已存在且 `approvedAt` 非空 → 400 locked-version」——没有这条守卫，批准锁定只是宣传语。**草稿编辑语义（批判轮补）**：plan-draft 态草稿 = 未批准版本（approvedAt 空），与正式版本走同一写入管线（账本先行）——并发编辑由账本 revision 409 拦截，无静默后写赢；草稿覆盖同 version 文件并重算 contentHash。

**重试幂等的准确表述**：悬空引用重试时，重传内容与账内 contentHash 逐字节一致则免 save 直接收敛；内容有演化则走正常 409 重试路径（乐观锁重走）——不是无条件「无需再 save」。

**为何否决**：**单文件最新版覆盖**——与 research §5.2「批准的是具体版本、返工不抹历史」直接顶牛；历史正文只剩 FileStore .bak 单备份（best-effort），覆盖写使批准锁定物理上不成立。**不记 contentHash**——外部篡改不可检出，诚实口径只覆盖缺失不覆盖篡改，与 releaseItems 已设计的 contentHash（§6.1）形成两套产物两种可信度。

### 细化④ 缺失降级：listing 布尔下放 + 读 404 + 显式缺失态（否决惰性 404 与读时自愈）

**选择**：三件套——① 读端点 `statSync(target,{throwIfNoEntry:false})` 缺失 → 404（PRD delete 同款）；② GET workbench 记录时 host 对每条引用 existsSync 探测，响应下放 `fileExists: boolean`（**响应字段不是账本字段**，先例即 workspace 状态 directoryExists/registered 布尔下放，`src/requirements-shared/protocol.ts:293-305`）；③ UI 显式缺失态：计划卡片「文件缺失（写入中断或被外部删除）」+ 重试写入，不造占位内容。

双写一致性论证：「文件写成功但账本 409」在账本先行顺序下**不存在**（409 时还没写文件）；存在的是「账本已提交、文件写失败」= 悬空引用，可见可重试，方向镜像 link 先例。**hash 不匹配（篡改）的读端点形态（批判轮补）**：读内容响应 200 + `contentTampered: true` 标记（UI 告警），不静默不阻断。**孤儿对账扫描**：目录扫描端点（`scanPrdDocs` 递归版）产出无引用文件清单——同时服务 D6 并发目录复活窗口的收编（见 D6）。

**任务书机器消费面（批判轮补）**：§7.1 注入「已批准计划」遇文件缺失/篡改 → **跳过 + 包内显式标注**「工作包 WP3 计划文件缺失，未注入」——诚实口径延伸到机器消费面，不静默注入空内容。

**为何否决**：**惰性 404**——列表态看到「v3 已批准」点开才 404，与元数据并置时体验断裂，悬空存量不可见。**读时自愈收缩账本**——读路径写副作用破坏账本语义，审计轨迹（曾有 v2 并被批准）被一次文件丢失静默抹掉。

### 细化⑤ 短文本边界：按产物语义一刀切 + 双半边单源硬 cap（否决一律文件与 KB 阈值分流）

**选择**：**结构性正文落文件**（plans 计划文档、reviewReports 评审报告——50KB 量级、有版本/审批/单独引用语义）；**条目性短文本 inline 留账本**（findings[].detail、knowledgeCandidates[].draft、releaseItems[].content、knowledge.yaml 的 content——记录属性片段，随条目整体读写）。判定准则用语义不用体量：「独立成文（有标题、有版本、可能被审批/单独引用）落文件；记录属性片段 inline」。

量化护栏：workbench-shared 零依赖常量 `WORKBENCH_INLINE_MAX_CHARS = 32 * 1024`（UTF-16 码元；实施期数值可调，机制不可变），双半边单源——先例 PRD_CREATE_MAX_CHARS 被 host zod / host endpoint / browser 预检三方共用（`src/requirements-shared/prd-file.ts:1-21`「one truth」头注）。**超 cap 的兜底口径（批判轮修正）**：拒绝写入 + 提示拆分；「导出为文件」是分发副本不是解药（导出后条目仍进不了账本）；未来真有长文需求按 default 纪律加 optional 引用字段，不是现在预留 union。

**为何否决**：**一律文件**——每条 finding 平白多一层双写一致性面，知识列表 N 次文件 fetch，检索/导出跨文件聚合。**KB 阈值动态分流**——同字段 `string | {ref}` union + 迁移逻辑 + 阈值边界反复横跳，0003 教训的复杂形态温床。

**产物导出承诺（批判轮补，诚实声明）**：v1 计划/评审报告仅存在于插件目录，直达路径在确认弹窗与文档写明；上线单导出（§7.3）已有；计划/报告导出副本列 P5 导出增强。用户备份通常覆盖工作区不覆盖 `$DSH_HOME`——记为已知代价，缓解 = 直达路径文档化 + D6 的 .trash 保险。

## D6 需求删除的级联清理：分级级联——账本级联 + `.trash` 软删墓碑（已拍板；否决孤儿容忍与硬级联）

**选择**：级联次序（每步失败不回滚主账本——回滚 = 复活用户明确要删的需求；降级为日志 + 残留，remove 对已删态幂等可重跑）：

1. **墓碑先写进原目录**：`deleted-record.yaml` 写入 `workbench/<requirementId>/`（快照：被删 requirement 主记录 + workbench 记录 + requirement 态 knowledge 条目 + 删除时间）——先写后 rename，rename 的原子性把墓碑一起带走；**顺序反了（先 rename 后补墓碑）会出现「rename 成功墓碑失败 = 无墓碑的 trash 孤儿」**，批判轮钉死此序；
2. requirements.yaml filter + save（主账本先行，用户意图权威落地——现有四步不动）；
3. workbench.yaml 删该 requirementId 记录——**服务注入形态**：workbench host 暴露清理服务，经 cordis setter 注入 requirements host（参照 `src/requirements-host/workspace.ts:31-37` WorkspaceBinder 可选能力先例）；服务缺席时级联跳过，自然回落孤儿容忍。不走 requirements host 直读 workbench FileStore 的内联耦合，也不走客户端两步编排（网络中断必半删最差）；
4. knowledge.yaml 按 **scope 分治**删 `scope==='requirement'` 且 id 匹配条目（快照已随墓碑）；global/workspace 态一概不动——一经 promote 即独立于出生地的公共资产，株连违反 promote 语义；
5. `renameSync` 整目录（含墓碑）→ `.trash/<requirementId>-<ISO 时间戳>/`（同卷 rename 单一原子 syscall：要么在原位要么在 trash，无中间态；对照 rmSync 逐文件递归的半删窗口）。**平台事实**：Windows 下源目录被编辑器占用（句柄打开）时 rename 常见 EPERM/EBUSY → 降级原位残留（无损，等价孤儿容忍），记档防「为什么删了文件还在」的支持成本。

用户可见行为：插件内三处全净；磁盘产物移入 .trash 继续占空间（v1 不做自动过期，YAGNI——用户手动清）；**可找回**：trash 目录直达 + 墓碑自包含（复制回位 + 三账本按快照恢复条目，乐观锁重试；恢复是手动操作，不提供 UI）。

**并发目录复活窗口（批判轮补，B/C 共有）**：级联完成后，在途/重试的产物写（账本先行已 save 成功、文件写后置）会 mkdirSync 重建已删目录并落文件——复活文件成无引用孤儿，由细化④的孤儿对账扫描收编清单，闭环。

**两账本半删中间态（批判轮补）**：workbench.yaml 与 knowledge.yaml 是独立 FileStore 的独立乐观锁 save，存在半删中间态——顺序钉死如上（墓碑快照先于任一账本删除落盘），各自幂等可重跑覆盖。

**knowledge 悬空的呈现边界（批判轮补）**：v1 无全局知识管理面板（S6 已激活列表只按需求过滤显示「本需求相关」），global/workspace 态条目的悬空 provenance **仅为账本事实，无处也无需渲染**——注入按 scope + trigger 匹配不受影响，诚实口径成立且零新 UI；全局知识面板不立项（超出 research 设计面，范围扩张需明示）。

**确认弹窗文案连带**：现句「此操作仅移除清单记录」（`src/client/requirements/dictionary.ts:202`）对 workbench 产物失真（产物在用户不可见的 `$DSH_HOME` 深处，「仅移除记录」暗示文件还可找到）→ 改写为「归档至 .trash（含 AI 工作台产物）」+ dangerButton（`--dsw-alias-state-error-primary` 覆盖先例）。

**为何否决**：**A 孤儿容忍 + 手动清理**——三个已核实事实使其实质等于静默丢失：产物是不可再生资产（区别于可重新 clone 的 repos）、落在用户不可见目录（PRD 孤儿可容忍恰因 prds/ 在用户自己工作区里）、需求 id 铸造制下重建必新 uuid 孤儿永久死寂；且「零代码改动」卖点有水分——确认文案仍须改。**B host 硬级联 rmSync**——对不可再生资产做不可逆物理销毁：误删零救济、逐文件半删窗口（部分丢失且不可知）、并发目录复活同样存在；C 以「最坏情形退化为 A」拿到 B 全部干净收益，B 无独立存活性。

> 边界论证：0002「独立文件互不持有状态」约束的是**读路径** join（互不持外键、容错呈现）——分级级联不破坏读路径对称性，破的是写路径的孤立性，换来的是资产安全；级联经服务注入（可选能力）实现，requirements host 对 workbench 的依赖是显式且可缺席的。

## D1 画像扩展：分层双画像——画像 A 零改动 + 新增画像 B + 公共底座 + 归属声明（已拍板；否决简单并列与扩展画像 A）

**选择**：personas.md 改三层结构：
