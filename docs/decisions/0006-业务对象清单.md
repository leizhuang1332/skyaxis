## 背景

## 决策

**skyaxis 第一版要管理 6 个核心业务对象**（按"对象群"组织）：

| 对象群 | 对象 | 一句话定义 | MVP 场景归属 |
| --- | --- | --- | --- |
| **Session 视图** | **Session**（元数据层） | AI 会话本体，由 DSH 提供，skyaxis 在其上加自己的视图与元数据。 | 所有场景的载体 |
| **Task 体系** | **Task** | 从 session trajectory 中抽取的任务步骤，构成 session 内的进度单元。 | A + D1 |
| | **TaskDependency** | Task 之间的依赖边，构成 session 内的 task DAG。 | D1 |
| **Session 依赖** | **SessionDependency** | Session 之间的输入 / 输出契约，构成 session 间的依赖图。 | D2 |
| **归档体系** | **Decision** | Session 内的关键决策记录，可被检索与回溯。 | D |
| | **Snippet** | Session 内的代码片段，可被检索与回溯。 | D |

### 与同类工具的对象差异

| 对象 | skyaxis 的差异点 |
| --- | --- |
| **Session** | DSH 内置 Session 是 runtime 实体；skyaxis 的 Session 视图是"信息流管理层"——把 Session 的进度、状态、关联关系从 trajectory 里"长出来"。 |
| **Task** | vs Linear / Notion 的 Task：Linear Task 是"用户手动管理的待办"，skyaxis Task 是"从 AI trajectory 自动抽取的执行步骤"。 |
| **TaskDependency** | vs 通用 DAG 库（Terraform、Airflow）：skyaxis TaskDependency 是"从 trajectory 自动推断"，不要求用户手动声明。 |
| **SessionDependency** | vs DSH trajectory 隐式依赖：skyaxis SessionDependency 是显式声明的、可视化的。 |
| **Decision** | vs Git commit message / ADR 文档：skyaxis Decision 是"在 session 过程中被标记的"，与 session trajectory 强绑定。 |
| **Snippet** | vs GitHub Gist / 独立 snippet 工具：skyaxis Snippet 与 Session / Task 强绑定，可被回溯到"哪段 trajectory 产生的"。 |

## 后果

### 正面

- **业务对象清单完整覆盖 6 个 MVP 场景**：每个场景至少有一个核心对象支撑。
- **与同类工具差异化清晰**：每个对象都明确指出与 Linear / Notion / Terraform / Airflow / GitHub Gist 等同类工具的差异，避免 skyaxis 被"看起来像另一个 X"。

### 负面 / 风险

1. **6 个对象 + 4 层关系，工作量较大**：MVP 实现阶段需要为每个对象设计数据模型 + UI 视图。
   - **风险**：MVP 阶段每个对象都"做一点但都不深"。
   - **缓解**：通过里程碑子阶段划分，先做 Session + Task（A 场景必需），再做 TaskDependency + SessionDependency（增强），最后做 Decision + Snippet（归档）。
2. **SessionDependency 依赖 DSH 原生能力**：
   - **风险**：DSH 是否暴露 session 间通信能力尚未验证。
   - **缓解**：跑通最小插件 demo 后验证；若 DSH 不支持，SessionDependency 降级为"skyaxis 自建 session 标签层"。
3. **Decision 与 Snippet 是"标记而非自动抽取"**：依赖用户在 session 内主动标记。
   - **风险**：MVP 阶段用户可能"忘记标记"，导致归档检索为空。
   - **缓解**：MVP 阶段不强求"全量归档"，仅做"用户主动标记的子集 + 全文搜索"。
