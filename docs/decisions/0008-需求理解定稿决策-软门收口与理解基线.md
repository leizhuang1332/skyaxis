# 决策 0008：需求理解定稿（软门收口与理解基线）

> 日期：2026-10-14
> 依据：[research 0009](../research/0009-需求理解定稿业界调研与设计.md)（六家业界调研 + 三缺口分析）+ 用户 2026-10-14 三拍板（AskUserQuestion：定稿软门 / 摘要导出 / 九节翻新同轮）与四项实施裁决（对话整体通过）。
> 状态：**已拍板**——三拍板 + 四裁决全量落定，实施随 milestones/0007。

## 背景

0006 收口后，S1「需求理解」已具备分析任务书投递、报告文件收取、三组待裁决提议与裁决闭环，但「用户裁决完之后」系统无感知：完成度不可见、stageReady 断线、advanceStage 纯指针；S2 拆分会话只拿得到标准清单（盲拆）；stale 基线挂在批准拆分而非理解收口。业界六家（research 0009）收敛于「理解产物有一道用户确认 + 下游从冻结产物派生」，但无一造审批状态机。

## D1 收口形态：定稿软门（已拍板）

**选择**：三组件——就绪披露（计数行 + stageReady 咨询行，两行独立呈现）+ `[定稿需求理解]` 单戳（ack Modal 统计 + 警示**不阻断** + 勾选门控）+ S2 供给升级。**不是硬门③**：定稿不锁任何下游动作（拆分编辑/批准在未定稿态照常可用），也不联动 advanceStage。

**为何否决另两档**：硬门③（定稿才解锁 S2）推翻 P3「硬门只两处」既有裁决，且伤「跳过理解直接拆」的轻路径（业界过半无硬门——Spec Kit/OpenSpec/Linear 无，Kiro 的 confirm 连状态字段都没有，BMAD 自述「没参与思考的人才需要批准级流程」）；纯供给增强（不造收口）没正面回答「何时算理解完」。**软门 = BMAD readiness 的建议性 + Kiro 的确认时点 + Spec Kit 的跳过自由**三者合取。批准挂落盘凭据（BMAD 金句）的账本版 = 单戳 + 快照。

**语义钉死**：定稿是**内容事件**、推进是**注意力事件**，两概念永久解耦——定稿不导航、advance 不检查；重复定稿 400（approve 家族「twice is a client bug」纪律）；主 union 隐式建账 ⇒ 全零记录可定稿（「无需分析、理解已收口」的合法跳过路径）；在 split 锁外（findings 族同侧——定稿冻结的是理解凭据，不是清单×coverage 契约）。

## D2 理解基线：单戳 + 轻快照 = 锚，非第二真源（已拍板）

**选择**：`understandApprovedAt?` 单戳（host-set-only，splitApprovedAt 同构）+ `understandBaseline?` 轻快照（criteria 全文 / findings **仅元信息**（id/status/category/severity/title，**不含 detail/resolution**）/ 已答澄清 {question, answer}）。

**锚非真源**：拆分任务书与理解摘要导出**一律从活账本派生**，不读快照内容——定稿后用户改标准错别字不需要「重新定稿才生效」，S1 变化由计数级提示与 S2 stale 兜住。**轻粒度**：20 findings × 32K detail 会推爆账本 inline 预算，且正文永远活在活行里。**零新 cap**：全部复制写入门已 cap 的数据。撤销 = 键摘除（戳+基线一并消失，revokeSplitApproval 先例）。

**为何不落工作区文档**（`.skyaxis/understanding.md` 候选被否）：与账本构成双真源（谁新？），且单写者归属不清（决策 0007 D3 纪律——0007 管的是「AI 会话写的交付面」，本文件若是插件写则回到 0005 细化①否决工作区邻接的三死因）。**导出（只读投影）覆盖对人面**。

## D3 stale 扩展：两新触发臂（已拍板）

**选择**：`splitBaseline` 扩 `understandApprovedAt?`（锚）与 `answeredClarifications?`（计数），两臂在 `splitStaleReasons` 比对：

- **understand 臂**：`record.understandApprovedAt !== baseline.understandApprovedAt` ⇒ 成因「理解已重新定稿」。两侧 undefined 等价安静（批准时与现在都未定稿不报警）；撤销定稿 = record 侧 undefined ≠ 基线侧字符串 ⇒ 触发（理解契约所基于的状态变了，正是该报的失效）；**批准后首次定稿也触发**（同理）。
- **clarifications 臂**：已答计数不等 ⇒ 成因「澄清答案已变化」（答案在 split 锁外、批准后仍可变化，而它是拆分上下文）。pre-0007 基线缺席按 0 比对不误报；未答行不计入计数。

**两现场一致性**：approveSplit 与 confirmSplitStillValid 共用 `answeredClarificationsOf` 派生——[确认仍有效] 把**全臂重锚到当前态**（与 prd 快照刷新同语义：用户确认的正是「含理解变化在内拆分仍成立」）。**host 从被盖章记录派生**（disposedFindings 纪律），approveSplit 客户端入参零改动。

## D4 摘要导出与 S2 供给（已拍板）

**摘要导出**：`buildUnderstandingSheet()` 纯函数（release-sheet 惯例：固定 zh/空组不渲染/戳收尾）——头（标题 + 定稿状态行）→ 验收标准 → 发现按处置态三组（已解决带方案）→ 待澄清（**已答 = 已定事实；未答 = 评审会待问**，带推荐答案与阻塞标注）。**未答照列**：mockup 悬置四轮的「评审会问题单」本意就是会前问题清单。SheetExportModal 复用（title 覆盖先例）+ 下载 `understanding-sheet-<rid>.md`；纯读零端点。

**S2 供给**：拆分任务书九节化（research 0008 骨架推广）。快照段升级 = 定稿状态行两态 + 标准清单 + **发现处置结论三组（带方案文本）** + 已答澄清（视为已定事实）+ 待裁决提议（勿视为已定）+ 现有工作包现状——BMAD「下游不得自行解释 PRD；缺答案先回填 PRD 再 re-run」的 skyaxis 落地（裁决结论在账本，任务书派生喂给拆分会话）。PRD 整段嵌入对 split **退役**（路径引用替代，analysisInputBlock 共享、purpose 名词分流）；`declarePlainSkeleton()` 逐字节不动；dev/review 五段逐字不动。

## 连带记档

- **stageReady 收编**：seed 戳加 `stageReady?`（endpoint 文件/会话两通道透传 parsed.stageReady——任务书教了、解析器解析了、现在落账渲染了）；S1 咨询行复用 `declare.stageReadyProposal`（零新键），与未决计数行**独立呈现**（AI 提议就绪 + 用户尚有欠账并存是合法态——Devin 绿灯提议与黄灯 open questions 并存同款）；永不落盘到推进动作（四权不动）。
- **S1 变化提示的下限**：定稿横幅的「定稿后上游已变化」= 计数级比对（criteria 数 / findings 处置数 / 已答数 vs 基线，或 seed 更新于定稿后）——文本级编辑不探测（诚实下限；契约级比对在 S2 stale 臂）。
- **词典与 CSS**：`understand.*` 20 键 + `split.staleUnderstand`/`split.staleClarifications`（443→465，四处登记）；CSS 零新类（gonogo/formHint/sowEntryRow/ackRow/advanceRow 全复用）。
