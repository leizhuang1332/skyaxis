## 背景

按 CLAUDE.md 第 4.4 节阶段切换条件第 6 条 + 第 5 节议题 9，**每阶段验收标准**是立项阶段最后一个必填项，落地在 `docs/milestones/acceptance.md`。

CLAUDE.md 第 2.1 节硬性约束："**不写具体指标阈值、不定性能 SLO**"。验收标准应该是"维度 + 判定框架"，不是数值阈值。

CLAUDE.md 第 5 节议题 9 例子：MVP 验收 = 核心场景跑通 + 5 分钟内跑起来 + 关键决策有 ADR（3 个维度）。

## 决策

### MVP 阶段 4 个验收维度

| # | 维度 | 一句话定义 | 判定框架 |
| --- | --- | --- | --- |
| 1 | **功能完整性** | MVP 完整 6 个场景全部可用 | 6 个 MVP 场景（A / B / C / D / D1 / D2）在 v0.3 通过条件满足时全部可用。 |
| 2 | **可用性** | 个人开发者可在本地 5 分钟内跑起来 | 新用户按 README 步骤，从 git clone 到看到可视化界面 < 5 分钟；DSH 插件加载无需手工改配置。 |
| 3 | **文档完整性** | 关键决策有 ADR + README 使用文档 | 关键决策全部有 ADR；README 包含安装、使用、配置、自检 4 个最小章节。 |
| 4 | **测试覆盖** | 核心场景有端到端测试 | 6 个 MVP 场景每个至少有 1 个端到端测试（手动或自动化皆可）。 |

### 验收维度在 3 个子阶段的差异化应用

| 维度 | v0.1（核心可视化） | v0.2（依赖关系） | v0.3（归档检索） |
| --- | --- | --- | --- |
| **功能完整性** | A 场景可用；B + C **基础部分**可用 | D1 + D2 必交付；B + C **增强部分**可用 | D 场景可用；B + C **完整**；**6 场景全部可用** |
| **可用性** | 5 分钟跑起来（基础流程） | 5 分钟跑起来（增强流程） | 5 分钟跑起来（完整流程） |
| **文档完整性** | README + ADR 0001-0007 | README 增量 + 子阶段 ADR | README 完整 + 子阶段 ADR |
| **测试覆盖** | A 场景至少 1 个端到端 | D1 + D2 至少 1 个端到端 | 6 场景各至少 1 个端到端 |

## 后果

### 正面

- **"不绑死时间、只划维度"的约束得到满足**：4 个维度全是判定框架（"可用 ✓"），无具体数值阈值。
- **CLAUDE.md 例子全部覆盖**：3 个例子维度（功能 / 可用性 / 文档）+ 1 个补充维度（测试覆盖）。
- **每个子阶段有差异化应用表**：避免"v0.1 就要求 6 场景全部可用"这种过度约束。

### 负面 / 风险

1. **测试覆盖作为验收维度可能引入工作量**：每个 MVP 场景至少 1 个端到端测试。
   - **风险**：MVP 阶段工作量增加。
   - **缓解**：明确"手动或自动化皆可"，允许 MVP 阶段先用手动测试 + 截图作为验收证据。
2. **"5 分钟跑起来"虽然不是数值阈值，但仍是主观判定**：
   - **风险**：不同用户的"5 分钟"差异大。
   - **缓解**：在 `acceptance.md` 中明确"5 分钟"的具体含义——"git clone 到看到可视化界面"——而非"任何动作"。
3. **维度之间可能冲突**：例如"功能完整性"要求 6 场景全可用 vs "可用性"要求 5 分钟跑起来——6 场景全可用可能让插件加载变慢。
   - **缓解**：在每个子阶段的差异化应用表中明确"该子阶段的功能完整性门槛"。
