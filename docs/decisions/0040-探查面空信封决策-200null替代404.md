# 决策 0040：探查面空信封（200+content:null 替代探查型 404）

> 日期：2026-11-03
> 依据：用户实机反馈——打开无文档需求的工作台，控制台持续红行 `GET /api/skyaxis/workbench/artifacts?kind=requirement-doc… 404`（此前 0040/0041 轮已两次记档为「设计内诚实缺失」观察项，用户第三轮提出后拍板修噪音）；用户拍板「改 200 空信封」。
> 状态：**已拍板**——修订 0008「404 = honest missing」的呈现层语义：**探查型**缺席改为 200 空信封；**按需型** 404 保留。

## 背景

工作台打开时对四个文档面做存在性探查（analysis-report / requirement-doc / planning-doc / split-result；wp-plan-doc 同族），无文件即 404——「无文档」是**常态**（早期需求多数没写文档），但浏览器对任何非 2xx 自动打红行，于是每次打开 × 每个无文档需求 × 每面一条红行，用户三轮报障。功能本身零缺陷（面板正常渲染空态；实机核实 98dc1093 确无基线文档、分片目录只有 record.yaml）。

## D1 探查面 200 空信封（已拍板）

- 五个探查面（analysis-report / requirement-doc / planning-doc / split-result / wp-plan-doc）文件缺失或通道 unarmed ⇒ `200 {ok:true, content:null, contentTampered:false}`——「无文档」是状态不是失败请求；unarmed 与 missing 同形（无工作区即无文件，0008 语义）。
- **too-large 独立成 413**（写路径同码）：文件在场但超读限是错误不是缺失——顺带修掉旧实现「too-large 混入 404 被面板渲染成未生成」的既存 wart。
- **按需面（plan/review 正文）保留 404**：它们由 detail 的 planFileExists/reviewFileExists 存在性投影门控后才取，404 意味着「已列出的正文丢了」——真错误，且日常不触发、不产红行。

## D2 客户端判空不嗅状态码（已拍板）

- wire 类型 `ArtifactContentResponseOk.content: string | null`（注释钉死：null 仅探查面发出）；守卫同步收 null。
- 探查消费点（doc-section 行效应与预览弹窗、view 的 planAckDoc 探针）改判 `content === null ⇒ missing`；404→missing 分支保留为 stale-server 兜底带。
- 按需消费点（work-package-dialog / review-section / sow-modal defaultPlanText）补 null→missing/undefined 防御（类型共享所致，服务端按需面永不发 null——注释记「belt」）。

## D3 不采用的替代与理由（记档防复提）

- **detail 响应加存在性投影 + 客户端门控取数**（planFileExists 先例）：被否——文档可随时生成，投影会 stale，门控将**隐藏新写的文档**（比红行糟）；探查-on-open 正是保活机制。
- **保持 404 现状**：被用户否（红行反复触发报障回合，成本高于契约微调）。

## D4 波及与基线（已拍板）

- 端点 5 面 + protocol 类型/守卫/路由注释 + fetcher 注释 + 客户端 6 消费点；端点测试 5 处 404 断言改 200 空信封；doc-section spec 换空信封桩并**新增 404 兜底带用例**（净 +1）。
- 基线 1331 → **1332**；README 双版同轮追平。
