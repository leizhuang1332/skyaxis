# skyaxis — 目标用户画像（权威出处）

> 本文档是 skyaxis 目标用户画像的权威定义。任何对画像的修订，必须先开 ADR，再回写本文档。
> 现行结构为**分层双画像**（[决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md) D1，用户 2026-09-29 拍板）：公共底座 + 画像 A + 画像 B，各自标注管辖域。

---

## 公共底座（A / B 共享的痛点基线）

两个画像共享同一条痛点基线——这是它们住在同一个产品里的理由：

- **重度 AI 使用**：日常工作大量借助 AI 编程工具完成，session 是主要工作单元。
- **产出散落找回难**：AI 沟通与执行散落在各个 session，事后找回与回溯困难。
- **均需跨 session 视角**：需要从单个 session 之外看清"现在到哪、卡在哪"。

**分层与管辖域**：画像 A 管**天内多 session 并行的看清**；画像 B 管**需求生命周期跨天的推进与裁决**。

**归属声明**：AI 工作台（六阶段流水线 / 双账本 / 上线清单 / 知识库）主要服务**画像 B**；既有六场景（A / B / C / D / D1 / D2）继续服务**画像 A**。

---

## 画像 A：AI 重度多 session 用户

> **管辖域**：天内多 session 并行的看清。本节自初版起零改动。

> **一句话**：每天 4 小时以上 AI 编程、同时并行 3-5 个 session、个人开发者。

### 行为特征

- **使用强度**：每天 4h+ 在 AI 编程工具中工作。
- **session 并行度**：同时打开 3-5 个 AI session，不同 session 在不同任务上并行。
- **典型痛点**：
  - 单 session 内复杂任务被切成多步 AI 调用，无法看清"现在到哪一步"。
  - 多 session 并行时，"哪个 session 在等指令、哪个在执行、哪个已完成"无法一眼看清。
  - session 跑完后产出散落在聊天框里，事后想找回困难。
  - 不同 session 之间存在依赖（如 session B 的 prompt 依赖 session A 的产出），但缺乏显式表达。

### 画像与 MVP 场景的对应

| MVP 场景 | 画像 A 的核心受益 |
| --- | --- |
| **A**：单 session 内进度可视化（任务树 / 时间线 / 进度条） | 高 |
| **B**：跨 session 产出聚合可视化 | 高 |
| **C**：多 session 总览与状态可视化 | **极高**（直接命中痛点） |
| **D**：session 决策 / 代码片段归档与检索 | 中高 |
| **D1**：session 内 task DAG | 高 |
| **D2**：session 间输入 / 输出依赖 | 高（画像 A 的核心场景） |

## 画像 B：需求驱动的企业后端开发者

> **管辖域**：需求生命周期跨天的推进与裁决。
> **一句话**：以需求为工作单元的企业后端开发者，单需求生命周期跨天到数周，从 PRD 评审到上线全程重度借助 AI。
> 素材全部取自 [research 0006 §1.1 实测七步](../research/0006-AI工作台调研与设计.md)，非虚构人设。

### 行为特征（工作流七步）

1. **需求理解**：PRD 评审准备（可行性 / 源码冲突 / 兼容性 / 风险 / 数据体量分析）→ 评审会问题清单。
2. **探索规划**：工作包边界拆分（粗粒度、有范围与顺序）。
3. **执行实施**：逐工作包开发（调研 → 开发计划文档 → 人审 → 实施）。
4. **验证**：工作包自测验收（端到端 → 提问题 → 改 → 过 → 提交）。
5. **评审**：全量代码评审（bug / 性能 / 运行时 + PRD 验收完成度）。
6. **交付**：中间产物登记（SQL 加字段加索引、开关、MQ 配置）→ 上线清单。
7. **沉淀**：知识沉淀（业务知识 + 开发约定）。

### 典型痛点（research 0006 §1.2 四条）

- **持久性**：任务清单 / 计划 / 裁决必须活在 session 之外（→ 账本化）。
- **全局进度**：需求维度的阶段与工作包状态一眼可读（→ 流水线 + 状态聚合）。
- **产物防漏**：上线中间产物在产生时即登记、发布时聚合（→ 登记账本）。
- **知识复用**：业务知识与开发约定自动注入后续 AI 上下文（→ 知识库 + 任务书）。

### 协作边界

对接 PRD / 评审会 / PM，但**协作只消费导出物**（评审会问题单、上线单）——不做多人协同编辑（[决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md) D2 以「单人」焊死）。

### 画像与功能的对应

| 功能（research 0006） | 画像 B 的核心受益 |
| --- | --- |
| 六阶段流水线（拆分 → 计划 → 实施 → 验证 → 评审 → 交付沉淀） | **极高**（直接命中全局进度 + 持久性） |
| 双账本（workbench + knowledge） | 高 |
| 上线清单（SQL / 开关 / MQ 登记 + 上线单导出） | **极高**（产物防漏） |
| 知识库双通道（手动条目 + 候选沉淀） | 高（知识复用） |

## Anti-Persona（明确不服务）

### 反例 1：团队协作用户

- **特征**：多人共用 session、团队任务分配、共享决策。
- **不服务原因**：与单人定位正交；skyaxis 不做团队协作。画像 B 的 PM / 评审会协作只体现为导出物消费，不构成多人协同。
- **依据**：CLAUDE.md 第 3 节 + [决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md)（原「ADR 0002 定位」已佚——git 3938caf 初版可考；现行 decisions/0002 为同号不同文的另一决策，不得错引）。

### 反例 3：跨项目独立 session 用户

- **特征**：同时维护 3-5 个独立项目，每个项目 1 个 session，session 之间无依赖。
- **不服务原因**：MVP 阶段优化重点是"session 间有依赖"的重度多 session 用户；D2 场景对这类用户是过度设计。
- **代号让渡（[决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md) D1，2026-09-29）**：本反例曾占用「B 画像」代号（git 3938caf 初版可考），该代号已让渡给上文的画像 B「需求驱动的企业后端开发者」。本文档内「B 画像」一律指后者。
- **后续位置**：MVP 之后的迭代阶段评估；如 DSH 内置已覆盖则可永久排除。

## 边缘画像（非核心但允许）

### 学习者 / 探索性使用

- **特征**：单 session 为主、低使用强度、上下文切换不频繁。
- **现状**：**未明确排除**，但也不在核心画像。
- **含义**：MVP **不为这类用户做专属优化**，但他们使用 skyaxis 不会被劝退——A / B / C 场景对学习者也有价值，只是 D1 / D2 的复杂度对他们是过度设计。
- **风险**：如果学习者实际使用率高，可能反向要求 skyaxis 适配学习场景，导致 MVP 范围扩张。
