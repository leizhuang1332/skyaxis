
## 与仓库池的差异（减法清单）

- **删除**：URL 语法校验器、git ls-remote 可达性探测、`subprocess` 可选 inject、validate 端点、RiskConfirmation 勾选放行流、整套 URL 合法性错误码族。
- **保留**：revision 乐观锁与冲突自愈、坏文件降级拒写 + `.bak` 提示、删除二次确认、窗口聚焦自动刷新、加载骨架屏、CSS Modules alias-only、SlotCore 契约测试范式。
- **简化**：表单流从「本地校验 → 探测 → 四分支」退化为「本地校验（标题必填）→ 直接保存」。

无 PoC 论证：仓库池 P0 已实证的四个环节——端点回环（PoC-2）、yaml 自管文件回环（PoC-3）、ui-primitives 接入（PoC-4）、组件测试样板（PoC-5）——需求管理全部原样复用，无新宿主能力需求。

## P4 列表页迭代（单栏 + 创建时间 + 排序）

> **2026-09-30 实现完成，自动化门全绿**：typecheck 0 错 / **789/789 tests**（774→789，+15）/ build 通过 + 产物断言（创建时间倒序·创建时间正序·创建于·Newest first·Oldest first·rowTime·sortButton 均入 bundle，旧 `repeat(2, minmax(0, 1fr))` 归零）。**拍板（2026-09-30 AskUserQuestion）**：① 排序菜单只做**创建时间倒序/正序两项**（默认倒序），不加标题序/更新时间序——需求未提的维度不自行扩张；② 行内时间用**本地绝对时间 `YYYY-MM-DD HH:mm`**，不用相对时间、不用仅日期。词典 125→**129 key**（增 view.createdPrefix / view.sort / view.sortCreatedDesc / view.sortCreatedAsc，四处同步：dictionary 接口 + zh + en + register 类型清单 + register.spec 键数组）。
>
> **实现裁决四项**：① **时间不可切 ISO 串**——账本存 UTC（宿主 `new Date().toISOString()`），`slice(0, 16)` 会打印 UTC 钟面，东八区晚间记录差一整天；也不用 `Intl.DateTimeFormat`（字段序随运行时 locale 漂移，行会随浏览器语言变形）。改为手工拼本地字段，完整 wire 串挂 `title`（行内到分钟，悬停给秒与时区）；解析失败返回 `''` 且**整格不渲染**，永不显示 `Invalid Date`。② **排序是纯视图投影**——账本保持文件序为真源，`sortRequirements` 在 view 层 filter 之后再排，刷新/保存都不需要记住排序；并列时按 id 兜底（宿主钟精度可同戳，无兜底则每次刷新都可能重排）；不可解析戳归 0 而非 NaN（NaN 比较器不是全序，引擎可返回任意排列）。③ **排序态随 store**（`listSort`，同 `listFilter` 家族）——宿主 keyed main slot 无 keep-alive，面板切换会卸载组件，组件态活不过往返。④ **排序按钮的可访问名 = 用途 + 当前方向**（`aria-label="排序: 创建时间倒序"`）——裸 `aria-label="排序"` 会**覆盖**按钮自身可见文字，屏幕阅读器用户听不到当前是倒序还是正序；只写方向又读起来像状态而非控件。组合名同时满足 WCAG 2.5.3（可见标签落在可访问名内）。
>
> **变异验证五项（改完即撤，git diff + 残留 grep 复核基线干净）**：① CSS 改回 `repeat(2, …)` → 单栏钉红；② 格式化器换成 `slice(0,16).replace('T',' ')` → 5 个测试红（本地钟面/跨日/offset 串/行内渲染/畸形戳）；③ view 层排序退化成恒等（直接用账本序）→ 2 个测试红；④ 排序按钮补 `disabled={state.busy}`（照抄邻居 detailSwitch 的「貌似合理」回归）→ 1 个测试红；⑤ `aria-label` 退回裸「排序」→ 1 个测试红（可访问名丢方向信息）。**变异④第一次是瞎的（恒绿），教训记档**：store 是 raf 刷新，`store.set` 后 `getSnapshot()` **同步**就报 busy，而 DOM 还是上一次渲染——`waitFor(() => expect(store.getSnapshot().busy).toBe(true))` 在 React 重渲染之前就通过，随后读到的按钮是旧 DOM，断言恒真。改为**同行 `disabled={state.busy}` 的行菜单锚点（`aria-label="编辑"`）当重渲染哨兵**——它翻转即证明 busy 已落到 DOM，此时再断言排序按钮未 disabled 才有意义。这是 snapshot store 测试的通用坑：**等 DOM 证据，别等 store 快照**。
>
> **排序按钮刻意不带 `disabled={state.busy}`**（与其抄来的 detailSwitch idiom 相反）：重排是纯本地投影、不打端点，无可等待之物；busy 期间锁住它会在保存某条需求时把整张列表的排序一并锁死。相应地 `.sortButton` 的 `:disabled` 与 `:hover:not(:disabled)` 规则按死代码删除（`:hover` 直接生效）。
>
> **变异③另暴露测试脆弱点并已修**：排序菜单是 portal 模式，某测试中途失败会把「排序」按钮与行泄漏进 `document.body`，后续测试报 "found multiple 排序 buttons" 掩盖真实原因——已把排序触发器与行序断言全部改为 `within(container)` 作用域（菜单列表仍走全局 `screen`，与既有行菜单测试同款）。文件级 `afterEach(cleanup)` 试过但**撤回**：与 `RequirementsIcon` 测试的手工 DOM 操作冲突（该测试 `svg.remove()` 后不 unmount），本文件纪律是逐个显式 `unmount()`。
