## 各 PoC 明细

### PoC-1：subprocess → git ls-remote 三态分类（真实网络实测）

独立 cordis 运行时挂载真实 `dsh-subprocess-local@0.1.5-rc.2`，`resolveExecutable('git')` 解析到 `C:\Program Files\Git\mingw64\bin\git.EXE`，五场景分类全部正确：

| 场景 | 分类 | 关键 stderr |
|---|---|---|
| S1 公网可达（octocat/Hello-World） | reachable | exitCode=0，refs 正常返回 |
| S2 DNS 失败（.invalid 域） | network | `Could not resolve host` |
| S3a GitHub 不存在/私有仓库 | auth | 带凭据助手时 `Repository not found`；清空助手后 `could not read Username ... terminal prompts disabled` |
| S3b 本地 401+Basic challenge 服务 | auth | `fatal: could not read Username for 'http://127.0.0.1:…': terminal prompts disabled` |
| S4 本地超时 abort（1ms） | network | exitCode=1、signal=null、stderr 空 |

**P2 设计输入（分类器规则已验证）**：
1. **凭据必须中和**：本机默认带 Git Credential Manager——`GIT_TERMINAL_PROMPT=0` 挡不住 GCM 自己的交互/拦截（对未加密 HTTP 直接拒绝）。spawn argv 必须带 `-c credential.helper=`（清空凭据助手）+ env `GCM_INTERACTIVE=never` 才能确定性非交互。清空后 GitHub 401 场景产出标准 `could not read Username` 权限样本。
2. **GitHub 401/404 刻意混淆**：私有/不存在仓库的 stderr 形态取决于凭据环境（`Repository not found` vs `could not read Username`），两种 pattern 都归权限类（文案层区分）。
3. **Windows 终止语义**：taskkill 树终止 = exitCode≠0、signal=null、stderr 无实质内容——规则：剔除 `warning:` 行后为空 + 非零退出 → 本地终止/超时 → 网络类。
4. 权限类 pattern 集（已实测）：`authentication failed` / `could not read (Username|Password)` / `permission denied` / `HTTP 401|403` / `repository … not found`；网络类：`could not resolve host` / `timed out` / `connection refused|reset` / `network is unreachable` / SSL 握手。兜底未知 → 按 D4 拒绝。

### PoC-2：connection 端点回环

- **Leg A（官方 `fetch-routes.host.spec` 同款直构）**：`new HostConnectionService(pluginCtx, [], {})`（发布包公开构造器）→ `fetch.register({path:'/api/skyaxis/repos/validate', methods:['POST'], requestBody:'buffered'})` → `createSharedFetchHandler('/api')` 派发：POST 命中 handler 返回 200 + JSON 体透传回显 ✅；未声明方法（GET）→ 404 ✅；dispose 后撤下 → 404 ✅。
- **Leg B（真实 HTTP）**：webserver（127.0.0.1:38171）+ credentials-local（**临时 DSH_HOME 隔离**，不触碰用户 `~/.dsh`）+ connection 宿主半插件：无 cookie POST → **401**（认证栅栏先于业务派发）✅；伪造 `Origin: https://evil.example.com` → **403**（信任栅栏拒绝跨站）✅。
- 边界说明（如实）：launch-token→cookie 的同源 200 全链路属宿主保障面（frontend-static/web-app 拥有，生产有 4 个官方端点背书），未在本 PoC 复刻——列入 P1 实机验收。

### PoC-3：repos.yaml 自管文件（路线 B）

11/11：初始写入（不存在文件视为 revision 0 初始态）→ zod 读边界 → 落盘为含中文的 YAML → 合法增改 revision 推进 → `.bak` 备份为上一好版本 → **陈旧 revision 写拒绝** → 最新 revision 写通过 → 坏 YAML/坏 schema 读取降级 `{ok:false}` 不抛出 → 从 `.bak` 恢复 → **坏文件上的写入被拒绝**（保护现场待人工介入）。原子写 = temp 写入 → 备份 → rename（Windows MoveFileEx REPLACE_EXISTING，含 EPERM/EACCES 退避重试）。

### PoC-5：组件测试样板（发布包可达面 + 边界如实记录）

**重要边界发现（影响 P1 测试策略）**：
- 官方 `dsh-client-test-runtime`（SlotTestRuntime）**发布版在 DSH monorepo 之外不可用**——其 lib 深度 import renderer 的 `src/*.ts`（发布包不含 src）与多个浏览器工厂入口。
- `/client` 子路径（ui-renderer、locale、ui-sidebar）是**浏览器工厂闭包**（`window.__ModuleLoader__.load`、无 export 语句），jsdom 无法静态导入；ui-renderer 的 `.` 主入口是**空壳 stub**（"browser-only"），locale 的 `.` 是精简 node 半边（无 setLocale/subscribe）→ **完整宿主外壳（PanelRow chrome、syncPanals）无法在 jsdom 单测，只能实机验证**（已列入 P1 验收清单）。
- 发布包可达面：`ui-slots` 的 `.` 含真 SlotCore（注册表核心）+ `resolveSlotLabel`（单参数：thunk 即时求值）；`ui-primitives` 的 `.` 为标准 ESM。
- ui-primitives 发布包**不声明任何依赖**且顶层调用 markdown 栈（`createCssVariablesTheme(...)` 等）→ vitest 需 react/clsx alias + markdown 家族 stub。**已落地为长期测试基建**：[tests/stubs/primitives-heavy-deps-stub.mjs](../../tests/stubs/primitives-heavy-deps-stub.mjs)（命名超集 + chainable Proxy）+ vitest.config alias（react 系列指向自有副本、katex CSS stub）。

**测试本体（3/3 通过）**：
- 5A 真 SlotCore：root 声明（含 RendersCheck 契约：声明 children 的组件须在类型上消费 renderSlot）→ 双槽注册（`PropsRuntime<'sidebar.panellist'>` 携 owner props 契约）→ `{id, order, label}` 投影 → `resolveSlotLabel` 双语解析 → keyed 双 key 共存 → dispose 撤下；未声明槽位 fail-loud。
- 5B RTL：仓库池页面组件 + 图标真实渲染（真 ui-primitives Button/svg）。

## 沉淀为 P1/P2 输入的类型范式

- register 的组件用 `PropsRuntime<'slot-key'>`（owner 契合）；root/声明 children 的组件参数须含 `PropsRenderSlots<...>`（RendersCheck）。
- `resolveSlotLabel(label)` 单参。
- cordis 根 Context 无 `dispose()`，只 dispose fiber。
- 独立 PoC 挂载模式：`new Context()` → `ctx.plugin(pkg)` → `fiber.await()` → `ctx.get('<service>')` 或 `ctx.inject([...], cb)`。
