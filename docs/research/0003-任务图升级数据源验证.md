## 一、背景：升级路线图与四个开放问题

[docs/dist/01-07](../dist/README.md) 拆解了参考插件 task-dag-viewer 的完整实现（数据源 / 折叠 / 布局 / 环 fallback / 指标诚实 / 复刻步骤）。对照 skyaxis v0.3 task-graph（`src/client/task-graph/`）得到的差距结论：

| 维度 | 参考插件 | skyaxis v0.3 |
| --- | --- | --- |
| 节点身份 | 协议 ID 稳定，同 ID 折叠取最新 | `todo-{turn}-{writeSeq}-{i}` 位置型 ID，whole-list 替换全删重建 |
| 折叠模型 | 事件→快照增量折叠 | 每次通知全窗口重放 |
| 边语义 | 7 种 kind，只有 `dependency` 是真依赖 | 无 kind，线性串联边 |
| 布局 | 确定性分层 + `signature` 指纹门控 | dagre 全量重排，拖拽被新数据覆盖 |
| 数据源 | 7 个（血缘 / 目录 / 投影 / 三类节点） | 1 个（当前 session 事件窗口） |
| 指标 | 累计与当次请求严格分离，三态来源标注 | 无 |

由此形成的升级路线图（P0 身份重构 → P1 诚实性 → P2 多源扩展 → P3 布局稳定 → P4 测试纪律）留下四个开放问题，本文逐一验证：

| # | 开放问题 | 裁决（详见各节） |
| --- | --- | --- |
| 1 | `ISessions` 有没有血缘（origin / parentId）形状 | ✅ 就绪，与参考插件近乎同形（§二） |
| 2 | DSH 有没有 session 投影注册能力 | ✅ API 同形，dist/06 模式可近乎原样移植（§三） |
| 3 | `team/*` 事件 schema | ✅ 官方词汇 + npm runtime 验证完毕；缺的只是"本仓库未安装、默认 profile 未挂载"（§四） |
| 4 | `todo/write` 的 TodoItem 有没有协议 ID | 维持原判：无，content 锚定（§五） |

## 二、验证一：session 血缘 —— 就绪，且与参考插件近乎同形

### 2.1 实测类型

[service.d.ts](../../node_modules/@deepseek-ai/dsh-api-session-controller/lib/types/client/sessions/service.d.ts)（`SessionSummary` 约 L22 起，`SessionListState` 约 L61-79）：

```ts
export interface SessionSummary {
  id: SessionId
  title?: string          // 最新的 log-backed 标题（host 投影出来之前缺省）
  displayTitle: string    // 人类可读：durable title → project basename → session id
  cwd?: string
  parentId?: SessionId
  origin?: 'subagent'     // 粗粒度持久来源，仅用于导航过滤
  running: boolean
  completed?: boolean     // 未选中状态下跑完的"绿色提醒"位
  blank: boolean
  updatedAt: number
  projectionValues?: Readonly<Partial<SessionProjectionMap>>
}

export interface SessionListState {
  ids: SessionId[]                          // host 列表顺序
  byId: Record<SessionId, SessionSummary>   // 行级数据
  current: SessionId | undefined
  phase: SessionListPhase
  subagentsByParent: Readonly<Record<SessionId, SubagentCatalogSnapshot>>
  jobsBySession: Readonly<Record<SessionId, readonly JobView[]>>
  currentAddress: SubagentAddress | undefined
}
```

### 2.2 与参考插件（dist/02 §2）的字段对照

参考插件从它的宿主 `useSessions` 三个选择器消费的字段，与 DSH `SessionListState` 几乎**同名同形**：

| 参考插件消费（dist/02） | DSH 实测 | 裁决 |
| --- | --- | --- |
| `state.byId`（摘要 Map，反查血缘/状态/投影值） | `byId: Record<SessionId, SessionSummary>` | ✅ |
| `state.ids`（可导航判据——"列表里没有的 session 不假装能打开"） | `ids: SessionId[]` | ✅ |
| `state.subagentsByParent`（按父索引的 catalog） | `subagentsByParent` | ✅ |
| `summaries[id].{ displayTitle, origin, parentId, completed, running, updatedAt, projectionValues }` | `SessionSummary` **同名字段逐一存在** | ✅ |

结论：

1. **dist/03 §7 的 `lineageDepths`（孤儿/环防御的核心函数）几乎可逐行翻译成 TS**——`origin === 'subagent'` 血缘链、`parentId === undefined` 孤儿、父子环整圈 invalid 的判定条件全部有对应字段。
2. **root label 修复路径钉死**：`byId[current].displayTitle`（替代 `connector.ts` 里 `Session ${id.slice(0, 8)}` 占位符）。
3. **导航诚实规则照抄**：节点可点击 ⟺ 其 session id 存在于 `ids`。

### 2.3 subagent 数据：三通道齐备，但注意归属边界

| 通道 | 内容 | 类型位置 |
| --- | --- | --- |
| 事件（parent 侧） | `subagent/catalog`——"A direct child's complete discovery fact"，versioned parent-owned catalog entry | dsh-subagent `lib/types/catalog.d.ts`（declare-merge 进 `@deepseek-ai/dsh-session/types` 的 `SessionEventMap`） |
| 事件（child 侧） | `subagent/descriptor`——"Durable identity and lifecycle mode … appended once by the establishing provider **inside the child's initial turn**"；携带 `ReasoningEffortId` | dsh-subagent `lib/types/descriptor.d.ts`（同样 declare-merge） |
| 投影 | `subagentCatalog` / `subagent`（身份）/ `subagentTiming`（耗时 + turn 边界） | dsh-subagent `lib/types/projection-types.d.ts`（research 0002 §2.2 已列） |
| 列表 | `subagentsByParent`；与投影 `subagentCatalog` 是**同一事实的两种视图** | `service.d.ts` |

**两个易错点（本次验证时实际踩过 / 差点写错）**：

- `subagent/provider-added` / `provider-removed` 出现在 dsh-subagent 的 `lib/types/index.d.ts`，但它们合并的是 **cordis `Context.Events`（插件生命周期事件），不是 `SessionEventMap`**。不要当作 session 事件消费。
- `subagent/descriptor` 写在**子 session 自己的日志**里，`subagent/catalog` 才是 parent-owned。这正是 dist/01"投影边界 > 全局视图"原则在 DSH 的具体形态：父 session 只持有发现事实（catalog），子 session 持有身份事实（descriptor）。跨 session 拼子代理子树时两边都要读，且 honor 各自的归属。

## 三、验证二：投影注册能力 —— API 同形，dist/06 模式可近乎原样移植

### 3.1 注册契约对照

DSH 的 [`ctx.sessionProjections`](../../node_modules/.pnpm/@deepseek-ai+dsh-session-pr_84cd66f454dbfc7490c4215f4e78e5dd/node_modules/@deepseek-ai/dsh-session-projection/lib/types/index.d.ts)（`ProjectionDefinition` 约 L31 起，`SessionProjectionRegistry` 约 L100 起）：

```ts
interface ProjectionDefinition<K, S> {
  key: K                                  // 拥有的 SessionProjectionStateMap key
  stateSchema: ZodType<S>                 // 持久化 state 入库前校验
  init(header, inheritedEventCount): S    // 空 log 初始态
  apply(state, event): S                  // 纯折叠；不关心的事件必须返回同引用（Object.is 跳过下游）
  wire?: { viewSchema, view(state) }      // 可选 client 视图（host-only 单元可省略）
  stateVersion: number                    // 折叠语义版本，持久缓存失效用
}
// ctx.sessionProjections.register(definition) → disposer（注册是 fiber effect，卸载即摘 key）
```

与参考插件宿主的投影契约（dist/06 §3：`apply` 状态机 + schema 校验 + "值相等返回原 state"）**同名同语义**，包括三条硬约束的对应关系：

| dist/06 的做法 | DSH 对应机制 |
| --- | --- |
| schema `parse()` 拒绝非法组合（空 provider、枚举外值、矛盾组合） | `stateSchema` / `wire.viewSchema`（Zod）入库/出库双校验 |
| 值相等 `return state` 避免 mutation | `apply` 同引用返回 → `Object.is` 零下游工作 |
| 卸载由 Cordis 回收 | 注册即 effect，disposer 摘 key，客户端读作 capability absence |

### 3.2 输入源现成：`request/header` 在基础事件表内

[types.d.ts](../../node_modules/.pnpm/@deepseek-ai+dsh-session@0._54d1a918d77e481567353c23a9e2039f/node_modules/@deepseek-ai/dsh-session/lib/types/types.d.ts) L366-372：

```ts
'request/header': {
  header: EpochHeader   // { config: LlmCallConfig(provider, model, reasoning effort, sampling scalars),
}                       //   adapterDefaults?: LlmCallConfigAdapterDefaults, tools? }
  reason: RequestHeaderReason
  startsSeries?: true   // "A changed header also begins a distinct model-message series"
```

`EpochHeader`（同文件 L208）与 dist/06 §3 折叠的 payload `{ config, adapterDefaults }` **同构**——provider / model / reasoning effort / adapterDefaults 全部有位置。

### 3.3 结论与注意事项

1. **`skyaxis.agentMetrics` 投影可行**：注册位置就是 [src/index.ts](../../src/index.ts)（当前 no-op 的 host 入口），`request/header` 事件折叠 + 三态来源标注（`request-config` / `adapter-default` / `not-recorded`）+ schema 强制，整套照 dist/06 移植。
2. **注册前先查重**：`modelSelection` 投影已存在（research 0002 §2.2 表）。宿主已投影的事实直接消费，**只注册缺失的 key**（dist/01 原则 1：不建第二份真相）。
3. `startsSeries` 白送一个"换模型边界"信号，指标折叠时可用于切分 series。
4. DSH 的投影值有 **plain JSON** 硬约束（持久化缓存前提），指标 state 设计时别放函数 / Date 等非 JSON 值。

## 四、验证三：`team/*` 事件 —— 官方词汇 + npm runtime 齐备，缺的只是挂载

> **初版勘误**：本节初版结论是"依赖树内无来源，Team 视图移除"。该结论建立在只 grep `types.d.ts` 这一个类型声明文件上——而 DSH 的事件词汇表活在**生成的运行时产物**里。复审方法：全树搜索（不限 `.d.ts`、大小写不敏感）+ npm registry 实查。

### 4.1 事件词汇的三个权威载体（全树搜索命中）

| 载体 | 性质 | team 相关内容 |
| --- | --- | --- |
| [known-event-types.js](../../node_modules/.pnpm/@deepseek-ai+dsh-session@0._54d1a918d77e481567353c23a9e2039f/node_modules/@deepseek-ai/dsh-session/lib/types/known-event-types.js)（dsh-session 核心包） | **持久化目录**：`KNOWN_SESSION_EVENT_TYPES`，56 项，generated by `gen-persistence-catalog.ts`，`doc-sync` 校验 | `team/member`、`team/task`、`team/message/queued`、`team/message/delivered` |
| [typert.host.js](../../node_modules/.pnpm/@deepseek-ai+dsh-agent-pres_fc9bf98ae5865ea9f109f84a7d78519a/node_modules/@deepseek-ai/dsh-agent-presets/lib/typert.host.js)（dsh-agent-presets） | **线协议类型表**：内嵌完整合并版 `SessionEventMap` 声明（含 payload 形状） | `'team/member': { version: 2; teamId: TeamId; member: TeamMemberSnapshot }` 等四事件全形状 |
| [client.js](../../node_modules/.pnpm/@deepseek-ai+dsh-api-sessio_3b5e1c08705e08a8c5e35766ba203b1a/node_modules/@deepseek-ai/dsh-api-session-controller/lib/client.js)（session-controller） | **客户端 wire codec 词汇** | 四个 team key 均在 codec 列表 |

持久化目录的 doc 注释明确了识别语义：*read path 拒绝解释集合外的类型，除非事件带 envelope 的 `ignorable` 标记*（out-of-repo 插件事件的兼容机制；事件名注册机制被明确否决，理由见 `.agents/notes/implemented/architecture/2026-08-30-retain-ignorable-external-session-events.md`）。**team/* 在目录内 ⟹ 持久化层完整解释，不是 ignorable 外部事件。**

### 4.2 类型可见性的分层（初版混淆之处）

- **发布出来的 `types.d.ts` `SessionEventMap` 接口**只带基础 13 key（§四初版 grep 的唯一对象）；
- 其余 ~43 个词汇成员（team/approval/compaction/goal/plan-mode/command/tool-workflow/feedback/…）的类型声明**随各自 runtime 包 declare-merge**——runtime 未安装时，消费方（如 skyaxis）在 TS 里看不到它们，但持久化层和线协议照常识别；
- 这解释了为什么 [infer.ts](../../src/client/task-graph/infer.ts) L267-270 的注释列举 team/* 等类别是**准确的**（它描述的是词汇层面的存在），初版把这条注释判为"应修正"是误判，撤回。

### 4.3 runtime：npm registry 实查

`@deepseek-ai/dsh-experimental-agent-team`（"Implicit-root Agent Teams roster, durable peer mailbox, and shared task DAG"）：

| 事实 | 数据 |
| --- | --- |
| 首发 | 2026-09-09（`0.1.5-alpha.2`） |
| 版本序列 | 0.1.5-alpha.2 → rc.1 → **rc.2（2026-09-10）** → 0.1.6-alpha.1/2 → rc.3 → 0.1.7-alpha.1 |

### 4.4 "没有"的精确含义（三件事）

1. **核心包不捆绑 runtime**：dsh-session 只带词汇 + 持久化识别；
2. **默认 profile 不挂载**：standard preset 的 `agent.cordis.yml` 全量插件清单（persona / shell / fs / jobs / skills / goals / plan / compaction / delegation / todo / web / present）**无 agent-team 行**；preset 里连 codex / claude-code provider 都是 `disabled: true` 占位——DSH 的模式就是"可选能力 = 在 Profile 里显式挂载对应 Bundle"；
3. **本仓库未安装**：`pnpm-lock.yaml` 零命中、`.pnpm` 无相关目录——skyaxis 的 devDependency 树里确实没有（初版结论中唯一碰巧成立的部分）。

### 4.5 裁决与移植注意

- **Team 视图恢复为"条件可行"**：数据源词汇官方、payload 形状已知、runtime 可安装且 peerDeps 兼容。前置条件是**目标部署的 profile 挂载了 runtime**（skyaxis 自己不该也不需要捆绑它——插件只消费事件）。
- **版本形状是 v2**：`{ version: 2, teamId, ... }`。参考插件 dist/02 的折叠器只认 `version === 1`（"上游升 v2 时自动忽略"）——DSH 事件直接是 v2，`TeamMemberSnapshot` / `TeamTaskSnapshot` / `TeamMessageSnapshot` 的折叠规则要按 v2 形状重写，不能照抄 dist。
- **消费侧类型获取**：两个选项——(a) 把 runtime 加为 devDependency（只为类型，运行时不挂载）；(b) 沿用 infer.ts 今天对 `todo/write` 的 unknown 中转模式。工程取舍留 P2 决策。

### 4.6 同一词汇表里的连带发现（影响不小于 team 本身）

- **`tool-workflow/run-start | run-end | agent-start | agent-end`**：参考插件 Workflow 视图的 DSH 事件源。且 standard preset **默认挂载** `@deepseek-ai/dsh-tool-workflow` + `dsh-workflow-worker-thread`——**Workflow 视图的数据源与 runtime 都是默认可用的，可行性高于 team**。
- **`approval/asked | decided | policy`**：`types.ts` 里 `approval` 占位节点的真实事件源；approval 栈是 host-plane 默认组成（preset 注释明示"the sandbox and approval stack"留在 host composition）。
- 词汇表其余成员（`compaction/*`、`goal/change`、`plan/mode`、`command/*`、`feedback/*`、`model/selection`、`hook/*`…）均为官方持久化词汇，将来任何视图扩展都应先查这张 56 项目录，而不是 grep 类型声明。

## 五、验证四：TodoItem 协议 ID —— 维持 content 锚定

`todo/write` 事件的 `todos[i]` 是 `{ content, status }`（P1 起由 [todo-write.d.ts](../../src/client/task-graph/todo-write.d.ts) 按线协议形状精确声明），无协议 ID。dist/03 §2 "同 ID 取最新 revision"的折叠规则在 DSH 上**不能按 ID 移植**，P0 的替代方案维持不变：

- 同 turn 内 content 匹配 → 复用节点（原位更新 status）；
- 只删除"新列表里消失"的条目；
- 落实 infer.ts L35 `_todoContent` 注释里写了但从未实现的"跨 todo/write 复用节点 id"意图。

> **P1 补充发现**：payload **同样没有 `turn` 字段**（typert 表：`'todo/write': { todos: TodoItem[] }`）。原实现读 `data.turn ?? 0` 属于信任不存在的字段，生产环境 turn 归属全部失效；P1 已改为 ambient 回合计数（turn/start 设置、user/message 自增）。教训再次印证 §四/§六 的结论：**字段存在性以 typert 线协议表为准，不以测试夹具为准**。
