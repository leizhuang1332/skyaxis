> 日期：2026-10-15
> 依据：用户 2026-10-15 目标重述——「需求理解定稿应是一份文件：包含原始 PRD 但去冗余更精简，采纳发现补细节更完善，采纳标准验收有依据，澄清消歧使表达更准确，补充背景更权威；最终仍是标准需求文档结构，但比原始更适合 AI 阅读」+ 三问（定稿存哪/①→② 衔接仍不明确/摘要导出是否即定稿）。
> 状态：调研完成（四家一手模板 + IEEE 基线 + AI 可读纪律），设计经用户四拍板（[决策 0009](../decisions/0009-需求基线文档决策-融合文档与docHash锚.md)），实施落地（milestones/0008）。

## 0. 白话摘要

**场景**：0007 把「需求理解定稿」做成了账本状态（单戳+轻快照+摘要导出），用户指出这不是想要的最终形态——定稿应是**一份融合的需求文档**；且 ①→② 的衔接仍是无产物的软连接。

**答案**：四家一手模板（Spec Kit spec-template / Kiro requirements+EARS / BMAD PRD / OpenSpec spec delta）在条目级高度收敛于「稳定编号 + 可判定句式 + 不确定显式标记」三件套；Spec Kit 的「澄清答案回填正文并替换旧表述」、BMAD 生态的「[ASSUMPTION] 内联+文末索引收口」、OpenSpec 的「一句一条 + 可观察判据 + 非目标显式化」三个独门机制正好覆盖用户要的四件事（精简/完善/准确/权威）。**溯源各家都弱——条目级来源标注（PRD#章节/F发现编号/Q澄清编号）是 skyaxis 的差异化**。方案：新增「整理任务书」（purpose consolidate）让 AI 会话把 PRD + 全量裁决素材融合写入 `.skyaxis/requirements/<rid>.md`（十节结构），定稿盖章锚定文档哈希，拆分任务书以它为唯一需求真源、哈希变化即 S2 失效。

**意义**：定稿从「盖在状态上」升级为「盖在文档的特定版本上」；①→② 从状态衔接变产物衔接；0008-D2「不落盘」的反对理由（双真源/单写者）在「AI 单写 + 哈希锚定 + 账本仍是裁决真源」下消解，决策 0009 修订之。

## 1. 三问的代码级回答（现状盘点）

1. **定稿存哪**：`~/.dsh/skyaxis/workbench.yaml` 记录上两个字段（`understandApprovedAt` + `understandBaseline` 轻快照）——没有文档文件；`.skyaxis/analysis/<rid>.md` 是 AI 分析报告（输入面）非定稿本体。
2. **①→② 衔接**：两条软连接（拆分任务书快照行的状态衔接 + stale 锚）——无一等产物，拆分会话读到的是浓缩行不是完整需求文档。用户观察准确。
3. **摘要导出即定稿？**：否——它是裁决审计报告（处置分组 + 未答澄清），不含 PRD 任何内容、无融合改写。

## 2. 调研结论（四家一手模板）

### 2.1 横向对比

| 维度 | Spec Kit | Kiro | BMAD v4.44.1 | OpenSpec |
|---|---|---|---|---|
| 组织单元 | 单 feature 单 spec.md | 三件套 requirements/design/tasks | 文档族 PRD→epics→stories | 能力域多文件 + 变更 delta |
| 条目句式 | FR-001 + **MUST** + Given/When/Then 场景 | EARS（WHEN…THE SYSTEM SHALL…） | FR\<N\> 完整陈述句 + 编号 AC | 命名 Requirement + SHALL + GIVEN/WHEN/THEN |
| 编号稳定性 | FR-xxx/SC-xxx 固定前缀 | 无条目编号（靠标题） | FR/NFR/SM/UJ 全局稳定 | 无编号靠命名标题 |
| 不确定项 | `[NEEDS CLARIFICATION]` ≤3 + Assumptions 节 | Analyze 澄清问题流就地改 | Technical Assumptions 节；生态 `[ASSUMPTION]`+索引 | 无显式标记 |
| 溯源/变更 | Clarifications 会话节（Q→A 回填+替换旧表述） | 无条目级 | Change Log 表 + Realizes UJ-X | delta 三段式机械合并 |
| 可判定纪律 | testable/measurable/technology-agnostic；歧义形容词=未完成信号 | EARS 四性（可直译测试） | AC 逐条「precisely define done」 | 一句一条 SHALL；可观察判据「圈外测试者能否判过」 |

（IEEE 830/ISO 29148 传统骨架作基线参照，二手；EARS 完整五句式为原作者站转述，二手标注。）

### 2.2 「适合 AI 阅读」的写法纪律（原文摘录）

歧义形容词=未完成信号（"robust/intuitive lacking quantification"）；分歧性措辞（"large files / fast response times that would produce divergent implementations"）；不可观察=不合格（"handle large uploads gracefully is not observable"）；一句一条（"One statement, one SHALL/MUST"）；可测判据（"could a tester who's never seen the code tell whether it passed?"）；独立可测切片；AI 执行尺寸（"single AI agent in one focused session"）；术语单一来源（"introducing a synonym anywhere is a discipline violation"）。

### 2.3 三个独门机制 ↔ 用户四件事

| 用户要的 | 机制 | 出处 |
|---|---|---|
| 消歧使表达更准确 | 澄清答案**回填正文并替换旧表述**（"replace that statement instead of duplicating; leave no obsolete contradictory text"） | Spec Kit clarify |
| 去冗余更精简 | 非目标显式化 + 术语单一来源 | OpenSpec / BMAD skill |
| 补充背景更权威 | 背景节 + `[ASSUMPTION]` 内联 + 文末索引收口供逐条确认 | BMAD skill |
| 验收有依据 | 编号 AC「precisely define what done means」+ C 编号与账本 criteria 对齐（**skyaxis 独有**） | BMAD / 本设计 |

## 3. 设计定稿（用户四拍板 + 实施裁决）

**四拍板（2026-10-15 AskUserQuestion）**：① 落点 `.skyaxis/requirements/`；② 验收标准 C 编号与账本 criteria 一一对应不增不删；③ 摘要导出保留作裁决审计面（两种读者两种产物）；④ 软门延续（无文档可定稿，ack Modal 披露）。

**机制五条**（详见决策 0009 D1-D4）：账本=裁决状态真源、文档=需求表达真源（整理会话单写，手改→篡改披露）；定稿盖章锚定 docHash（understandBaseline.docHash，approveUnderstand 专属 flow 读盘派生）；C 编号账本对齐；衔接变实物（拆分任务书必读行 + splitBaseline.requirementDocHash 臂）；重整理回路（同入口重跑 + 重新定稿换锚）。

**文档十节结构**：元数据头（基线状态/基于 revision/生成戳）/ 背景与目标 / 非目标 / 术语表 / 功能需求 FR-1..N（一句一条 MUST/SHALL + 条目级溯源）/ 验收标准 C1..N（对齐账本）/ 边界与异常（EARS IF…SHALL）/ 已裁决风险（含未处置如实标注）/ 澄清记录（已答=已定事实；未答=Open Questions）/ 假设（内联+索引）/ 变更记录。**整理任务书**（purpose consolidate，九节骨架第三次复用）快照段嵌全量裁决素材（发现 detail+方案全文、澄清全文——与 analysis/split 行级摘要的分工）。

## 4. 边界与非目标

- 文档条目机器可读块（文末 yaml 锚、C 对齐解析校验）列后续轮——本轮靠任务书纪律。
- 多人协作/版本树（覆盖写 + Change Log 表足矣）。
- prds/ 落点（已拍板 .skyaxis/）；analysis/split/dev/review 四任务书不动。
