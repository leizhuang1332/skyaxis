# skyaxis — research 0032：工作台账本按需求分片立项与设计

> 日期：2026-10-23
> 依据：用户 2026-10-23 三轮拍板——①「要拆分 workbench.yaml，每个需求都是独立的文件」；②否决迁移到 `<workspacePath>/.skyaxis/`（会话内四道墙论证：鸡生蛋/换绑悬空/生命周期反转/git 污染——用户最终认可「非留不可的理由」）；③方案三点全按推荐：D1 分片同居 `workbench/<rid>/record.yaml`、D2 插件加载时点一次性迁移、D3 镜像导出面不做（另立项）。requirements.yaml 明确不在本轮（用户拍板「不动我同意」——纯注册表数据、无膨胀载体、聚合天然全库）。
> 状态：设计定稿，进入刀一实现。

## 0. 白话摘要

**场景**：全机所有需求的流程状态（阶段/发现/拆分批准/工作包/发布项/评审引用/会话绑定）都记在 `$DSH_HOME/skyaxis/workbench.yaml` 一个文件里。每次任何操作都同步 parse 整个文件、每次保存全量重写，且一条坏行落盘会让**所有需求**同时拒写（R#### 事故已实弹发生过一次）。需求只增不减，这个文件会无限膨胀。

**答案**：把台账按需求拆成独立分片 `$DSH_HOME/skyaxis/workbench/<requirementId>/record.yaml`——与该需求已有的 plans/reviews 产物**同居一目录**，记录与产物的生命周期从此完全同构（D6 级联删除的整目录改名自然覆盖记录）。锁从全库一把改为每记录一把；一条坏行只降级一个需求。取证确认全库**不存在任何跨记录的原子写**（每个 mutate 都带 requirementId+expectedRevision，id 铸造全是记录内闭包）——全局 revision 纯属单文件实现的副产品，拆分不扭曲任何既有语义。旧文件在插件加载时一次性迁移（拆分落盘→改名 `.migrated` 留档），宿主域单写者，不需要 0028/0029 那套双通道读机器。

**意义**：爆炸半径从全机收敛到单需求（安全收益即时，不等体量）；跨需求假冲突 409 消失；写放大从「每次全量」降到「每次一条」。客户端取证发现 controller 本就按需求分槽持 revision（未装载槽 0 = 分片缺失的虚拟 revision 0），**UI 零改动**——唯二要动的是两个 watcher（它们把全局 revision 跨需求穿线，须改为按记录 Map 穿线）。

## 1. 问题定义

workbench.yaml 是四同构 envelope store 之一（[workbench-file.ts:8-12](../../src/workbench-host/workbench-file.ts#L8-L12)），单文件 `{version, revision, records[]}`。三个结构性问题：

| 问题 | 取证 |
| --- | --- |
| 每操作全量 parse + 全量重写 | `load()` 同步 parse 整文件（workbench-file.ts:63-87）；`save` 重写全部 records（workbench-file.ts:94-109）；watchers 30s 轮询也在消费 |
| 一条坏行毒全库 | 写侧不重验 schema，坏行落盘后下次 load 全库 schema-degraded 拒写——R#### 事故记档（[record-actions.ts:88-95](../../src/workbench-host/record-actions.ts#L88-L95)，milestones/0006） |
| 增长单调 | 需求只增（删需求才回收，级联删记录）；实测 6 记录/108KB/两周 358 个 revision |

**拆分不扭曲语义的证据**（领域模型已是按需求的）：

- 每个 mutate 请求本就带 `requirementId + expectedRevision`（wire 锁早已是需求级意图）；
- 所有 id 铸造以记录自身集合为域：WP/C 序号（record-actions.ts:256、532、567、734）、R####（[record-actions.ts:97-104](../../src/workbench-host/record-actions.ts#L97-L104)，调用点 endpoint.ts:1541、record-actions.ts:953 均传 `record.releaseItems`）；
- **全库不存在跨记录原子写**：mutate union 每请求恰好写一条记录；知识晋升的双账本写（workbench 记录 + knowledge.yaml）本就非原子（ADR 0005 批判轮记档）；
- declare 两段导入「共享 revision 空间、跨写 409 correct not a bug」（[protocol.ts:1671-1677](../../src/workbench-shared/protocol.ts#L1671-L1677)）——跨需求 409 是单文件强加的假冲突，拆分后消失。

**客户端已是按需求分槽**：controller 每需求一个 slot 持 `{phase, revision, record, ...}`（controller.ts:53-72），mutate 发 `slotRevision(requirementId)`，未装载槽 revision=0「implicit-create actions still land」（controller.ts:178-180）——分片缺失的虚拟 revision 0 与之**精确对齐**。detail 409 → slot degraded 面板（controller.ts:142-146）承载分片降级，UI 零改动。

## 2. 设计

### 2.1 分片布局与信封（D1 拍板：同居）

```
旧：$DSH_HOME/skyaxis/workbench.yaml                        ← {version, revision, records[]}
新：$DSH_HOME/skyaxis/workbench/<requirementId>/record.yaml  ← {version: 1, revision, record}
     每分片自带 record.yaml.bak；目录不存在则首次写记录时 mkdir
```

同居而非新开顶层目录：D6 级联本就按 `<rid>/` 整目录原子改名进 .trash（[cascade-service.ts:162-172](../../src/workbench-host/cascade-service.ts#L162-L172)），墓碑本就内嵌记录副本（cascade-service.ts:99-106）——记录进目录后生命周期与产物完全同构。代价：放弃 index.ts:67-69「级联永不触碰台账」旧不变量，由 2.4 的 step ③ 重定义补回。

分片信封 zod schema（types.ts）：`{version: literal 1, revision: int, record: WorkbenchRecordSchema}`。加载时校验 `envelope.record.requirementId === 目录名`——分片被复制进别的目录必须以 degraded 'schema' 拒载（artifact-path 双层防御的同族纪律），杜绝「甲目录里装乙的记录」。

### 2.2 锁空间：每记录一把 revision

- 分片缺失 = 记录不存在 = **虚拟 revision 0**（与客户端未装载槽 0 对齐；implicit-create 动作发 0 → 匹配虚拟 0 → 铸 revision 1 的分片）；
- `saveRecord(rid, expectedRevision, record)`：按 rid 一条写队列（Map<rid, Promise>），load-check-write，per-record 乐观锁；队列内跨记录零竞争（不同文件）；
- mutate 面 wire **零改动**（`{ok, revision, record}` 同形重释——revision 变为该记录的新 revision）；detail 面响应 revision 改为该记录 revision（record null 时 0）；
- dev 收取流的多步连写（repair-bind save → seed save 的 writeRevision 链，endpoint.ts:686-731）在同一记录内照常传递；
- 409 收敛环不变：客户端持旧 revision → 409 → 重拉 detail/list。级联删记录后客户端 stale revision N → 虚拟 0 ≠ N → 409 → 重拉 → 记录消失，与现状同收敛。

### 2.3 list 面与降级模型

list 响应改形（消费面仅 dev-watcher/review-watcher 两处 + 测试，grep 全量核实）：

```
{ ok: true, rows: [{ requirementId, revision, record }] }   ← 降级分片不出现在 rows（其收取自动化静默跳过，
                                                              下轮重试；用户面上的降级由 detail 409 → slot degraded 承载）
{ ok: false, degraded: true, reason, hasBackup }            ← 仅「迁移阻塞」整库态（见 2.5），沿用旧信封形状
```

分片级降级：一条坏 record.yaml 只让该需求 degraded（detail 409、list rows 缺席、scan 跳过其目录），其余需求照常——R#### 类事故的爆炸半径就此收敛。save 拒绝覆写不可读分片（保留现场契约随分片保留，.bak 随分片）。

### 2.4 级联重推演（step ③ 重定义）

step ③ 从「台账滤记录」重定义为「**unlink record.yaml**」（幂等，ENOENT 即 done，不存在的目录同判）：

| 失败组合 | 结果 |
| --- | --- |
| ③成 ⑤成 | 记录随目录入 trash（正统，与现状同） |
| ③成 ⑤败（EPERM/EBUSY） | 记录已离活树，产物原地孤儿——即现状语义 |
| ③败 ⑤成 | record.yaml 随目录入 trash，离开活树 |
| ③败 ⑤败 | record.yaml 仍活 + requirements.yaml 已删 → 客户端 join 隐藏，级联重跑收敛 |

任何组合不劣于现状。墓碑（step ①）改从分片读取内嵌（读不到时 null，与现状 degraded 快照语义一致）；①~③ 窗口内目录同时存在 record.yaml 与 deleted-record.yaml，无冲突。「降级永不阻塞用户删除」契约（cascade-service.ts:32-33）不破——③ unlink 不可达时降级为日志+残留，重跑收敛。

### 2.5 一次性迁移（D2 拍板：插件加载时点）

宿主域单写者：没有旧版本双写者、没有用户域竞态——**不需要**双通道读、哈希优先、写臂顺迁。

- 构造时执行 `ensureMigrated()`（幂等）：workbench.yaml 不存在 → 完成态；可读 → 逐记录 force-seed 分片（revision 1，原子写）→ **rename workbench.yaml → workbench.yaml.migrated（提交点）**，.bak/.tmp 随迁改名；
- **崩溃安全**：rename 前任何崩溃 → 旧文件仍在 → 下次重跑 force-seed（幂等覆盖）+ rename；
- **degraded 源拒绝迁移**：旧文件 parse/schema 失败 → 原地保留现场（.bak 可用性如实上报），整库 blocked（list degraded 信封 / detail 409），修复后下次加载自动重试——「preserve the scene for manual recovery」契约不破；
- **防影铸**：rename 未成功前（如 EPERM 反复失败）读写一律 blocked 而非「分片缺失 → 虚拟 0 → 铸新记录覆盖真身」——旧文件在场且未改名时，分片永远不是权威；
- 每个读写入口（loadRecord/saveRecord/listAll）先过 ensureMigrated——构造时的主动迁移只是急切收敛，入口自愈兜底。

### 2.6 孤儿扫描

- `record.yaml` 加入 `<rid>/` 直下文件豁免清单（deleted-record.yaml 同待遇，[orphan-scan.ts:117-120](../../src/workbench-host/orphan-scan.ts#L117-L120)）；
- 降级分片的需求目录**整体跳过**（新可选参 unavailableRequirementIds）：其 plans/reviews 引用不可读，报成孤儿是噪音不是信号——该需求的对账面本就不可用（detail degraded），修复后下轮 scan 恢复；
- 目录在场 ≠ 记录在场：只有 record.yaml 在场才进 list rows——级联 ③成⑤败 的产物残留目录不再是「记录存在」的信号（与现状「台账无行」同判），孤儿面的 D6 复活窗语义不变。

### 2.7 客户端（唯二改动点）

两个 watcher 的 sweep 把「单一全局 revision 跨需求穿线」改为**按记录 revision Map 穿线**（dev-watcher.ts:139-179、review-watcher.ts:88-103）——原形在分片下必然跨需求假 409（甲的写推进甲的 revision，穿线值对乙失效）。controller/fetcher 其余面、store、view、词典全部零改动（fetcher.list 的结果形状随 wire 改）。

## 6. 实机验收门（四条）

1. 真机升级：workbench.yaml 消失、workbench.yaml.migrated 在、各 `<rid>/record.yaml` 在、板子数据无损（阶段/发现/工作包/发布项全在）；
2. 两个需求并行操作零 409（旧形态跨需求写必撞全局 revision）；
3. 删除一个需求 → 墓碑含完整记录、record.yaml 不在活树、.trash 里目录完整；
4. 手工毁坏一个分片 → 仅该需求 degraded、其余照常、修复（.bak 恢复）后自动恢复。
