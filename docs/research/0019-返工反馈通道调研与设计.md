## 0. 白话摘要

**场景**：built 卡上验收不通过（返工理由必填）→ WP 回 in-dev——返工理由落了账本、三处 UI 都展示，但没有任何操作能把它送进 dev 会话。设计上的返工正路（0016 验收脚本第 4 条「同会话补话再跑」）要用户手动跳到 VS Code 会话自己打字；工作台内发消息的能力（排队补话）被 0016 D2 裁定搁置在 P4 候选清单。

**答案**：(1) 断点不在状态机——in-dev 有 markBuilt/补投/重规划/watcher re-seed 全套，断在**反馈闭环的主动侧**：`acceptances[].note`（账本✓ 展示✓ 被动 re-seed✓）→ dev 会话（✗ 无通道）。(2) 补法=工作台内「送返工话」：拒绝提交成功后直接弹返工话 Modal（预览可编辑+点击发送），`prompt('queue')` 直入已绑 dev 会话——与 0017 投递直启 v3 同构，降级=深链跳宿主手发兜底；连带把返工历史节补进 dev 任务书（补投新会话也知道上轮为何被打回）。

**意义**：0006 状态机的返工边（fail→in-dev）第一次有了配套的反馈投递动词；0016 设计的「返工 re-seed」闭环（同会话补话→新声明→槽重置 pending）的缺失半边补齐；D2-B「排队补话」从泛用候选收敛为返工场景的定向通道（内容是结构化账本数据、用户刚亲手填写——天然满足「点击发送自己预览过的内容」的追认口径）。

**决定性论证**：0016 D2-A 搁置排队补话的理由是「工作台内排队是拆成两半的交互（发得出、看不到回应）」——针对的是 waiting 应答场景。返工场景不同构：发送后**不需要**即时看到回应——正路就是会话后台跑完、末尾吐新声明块、watcher 收取、收件箱「完成待验收」出行（既有闭环全在场）。拆成两半的批评在此不成立。

## 2. 设计分叉与拍板（2026-10-20 四问四答，全采推荐档）

### D1 通道档位 —— **B 工作台内发送**

预览可编辑 Modal → 点「发送返工话」→ `binding(devSessionId).session.prompt(text,'queue')` 直入已绑 dev 会话；失败降级=深链跳宿主（v2 尾巴：setDraft+open+selectPanel）。**口径追认**：与 0017 v3 同构（用户点击发送自己预览过的内容）；对 0016 D2-A「介入=仅深链」的推翻范围**钉死在返工话这一动词**——通用排队补话/介动词（steer）仍维持 D2-A 搁置。

- 否决 A（仅深链引导）：反馈闭环仍是手动的，用户实机痛点不解决。

### D2 入口位置 —— **C 两处都有**

① 拒绝 Modal 提交**成功后**直接弹返工话 Modal（`await acceptWorkPackage` 返回 ok 才跟进——失败/竞态零跟进，理由刚写完热乎顺手发）；② WP 详情验收节标题行常驻「送返工话」按钮，门控=`in-dev && 尾验收=fail && 尾 dev 绑定存活`（事后补发/换人接手都能用；绑定消亡则按钮退役——正路是收件箱「存疑」行的补投）。看板 in-dev 卡**不加**卡面入口（0018「in-dev 及其后无卡面入口」裁定不动）。

### D3 返工话内容 —— **B 结构化组装**

纯函数 `buildReworkMessage`：头行（`# skyaxis 返工话 <wpId> · <需求标题>`）+ 第 n 轮验收未通过 + 返工理由（尾 fail note）+ 修复指令——**显式要求完成后在回复末尾重吐声明块**（watcher re-seed 链的钩子：不发这句，新声明不来、收取槽不重置、链路断在会话侧行为）。Modal 内可编辑（0009 形制）。

- 否决 A（纯理由转发）：会话不知道要重吐声明块——返工 re-seed 链断。

### D4 补投连带 —— **A 附返工历史**

`workPackageBlock` 增「返工历史」节（历轮 ✗/✓+理由，纯追加、无记录零渲染）。补投=从头按计划重做的场景，新会话同样需要知道上轮为何被打回，否则可能重犯。
