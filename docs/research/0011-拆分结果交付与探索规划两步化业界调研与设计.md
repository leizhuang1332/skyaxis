## 0. 白话摘要

**场景**：① 需求理解经 0007（报告文件通道）/0008（定稿软门）/0009（基线文档+docHash 锚）三轮已形成「AI 写文件 → 插件自动收取 → 页面回显 → 用户裁决锚定」的完整链路；② 探索规划仍是原始形态——拆分任务书投递后，AI 把拆分建议写在会话聊天里，用户对着会话人肉抄录到工作台再点「批准拆分」。且 ② 只有一个 AI 动作：一步出拆分清单，「探索」只是提示词工作流的第 2 步，结论无独立产物。

**答案**：(1) 不对称在代码里全部坐实，且 [research 0009](0009-需求理解定稿业界调研与设计.md) §5 前一日刚把「拆分提议机器回传」挂账为另轮事项——本轮即该轮。(2) 业界分两阵营：**agent 产品**（Claude Code/Codex/Cursor/Windsurf/Devin/Jules/Manus/Copilot）全部把探索+规划+拆分合并在一个 plan mode 里，拆分只以执行期 todo 存在（agent 自管、无人审门）；**SDD 工件链流派**（Spec Kit 为代表，Kiro/BMAD/OpenSpec 同构）把「方案」与「拆分」做成两个独立工件、两道人审门。(3) 两步化的决定性论证是**权重映射**：agent 产品敢合并，因为其拆分是廉价可逆临时件（改 todo 即修正）；skyaxis 的工作包清单是账本持久治理对象（七态生命周期/版本化计划/验收历史/依赖 DAG/覆盖矩阵），拆分在 skyaxis 的权重 ≈ 业界「计划」的权重——业界无一例外给「计划」配审批门+工件化，这笔待遇应转账到 skyaxis 的拆分层，中间补的正是业界默认三层（spec→plan→tasks）中缺失的方案层。

**意义**：拆分结果文件化+回显补齐 0007 对称性（立项痛点「工作包清单只存在于某个 session」的最后一段人肉消失）；规划文档把蒸发在会话里的技术推理实物化，硬门① 从「盲审一份看不到推导的清单」变为有据可依；下游每个 WP 计划会话与 re-split 从此有共同方案真源可读；阶段 key `plan`（探索规划）名实相符。

## 2. 调研结论

### 2.1 两阵营对照（2025-2026 官方来源）

| | agent 产品（八家） | SDD 工件链（Spec Kit / Kiro / BMAD / OpenSpec） |
| --- | --- | --- |
| 探索/规划/拆分 | 合并在一个 plan mode：读码+提问+出计划，计划内嵌步骤清单 | 分层独立：Spec Kit 是 specify→spec.md、plan→plan.md(+research.md)、tasks→tasks.md 三条命令三个工件三道人审；Kiro 是 requirements→design→tasks |
| 拆分的地位 | 执行期 todo/进度（Manus todo.md 重写背诵最典型），agent 自管、无人审门 | tasks.md 落盘工件，人审后才 implement |
| 计划形态 | 两派：对话内（Codex plan items、Claude Code 呈交式）vs 落盘可编辑（Cursor / Windsurf 活文件 / Copilot VS 落 `.copilot/plans/`） | 全部落盘（specs/ 目录） |

### 2.2 Claude Code 与 Codex 的机制要点（官方文档直抓）

- **Claude Code**：plan mode=编辑权限硬门（只读研究 → ExitPlanMode 呈交计划〔该工具调用本身需权限批准〕→ 用户三选一，批准即切换执行权限）；计划可 Ctrl+G 编辑、落盘 `~/.claude/plans/`；批准时可选**清空规划期上下文**（showClearContextOnPlanAccept——规划/执行上下文隔离是官方设计）；官方原则逐字「Separate research and planning from implementation to avoid solving the wrong problem」；**任务拆分（TaskCreate/todo）明确归执行侧自我管理**，无人审、无「计划→todo」自动转换；子代理中 ExitPlanMode 默认被移除（审批权永在主会话）；「If you could describe the diff in one sentence, skip the plan」（门按不确定性触发）。
- **Codex**：2026-02 起原生 plan mode（`/plan`、Shift+Tab，「gather context, ask clarifying questions, and build a stronger plan」），计划默认对话内 plan items（落盘是未实现 feature request；Cookbook ExecPlans/PLANS.md 是落盘流派的官方补充）；sandbox×approvals 权限矩阵与 plan mode 正交。

### 2.3 通用五模式

1. **Plan-approve gate 标配化**（Jules 显式按钮+离开页面自动批准、Devin 审批界面、Manus 批准前不可执行、Copilot 批 blueprint 后才写码）。
2. **计划可编辑**（Cursor/Manus/Devin 审前可改；Windsurf 执行中改 agent 实时响应；Copilot VS 落盘人机共评）。
3. **事前澄清提问**（Codex/Cursor/Manus/Copilot CLI 官方明文——skyaxis 待澄清回路已对齐）。
4. **小任务跳过规划**（Claude Code 官方——门按不确定性触发）。
5. **2026 新信号：自动批准+模型兜底**（Jules Planning Critic 审查自动批准计划，官方数据任务失败率 -9.5%）。

### 2.4 信任假设差异（本轮决定性洞察）

**agent 产品信任模型拆分、人只把方向；SDD 要求人对「规格→方案→拆分」逐层确认。** agent 产品敢合并的前提：拆分是廉价可逆临时件，拆错改 todo 即可。该前提在 skyaxis 不成立——工作包清单是账本持久治理对象，撤销一次错误拆分=撤销批准+重新拆分+已批计划作废。**拆分在 skyaxis 的权重 ≈ 业界 agent 产品里「计划」的权重**；skyaxis 又是「账本+供给器，不是 agent 运行时」（决策 0005 D2 焊点③），天生站在 SDD 阵营——research 0009 对比表已示 Spec Kit/Kiro/BMAD/OpenSpec 全部有中间方案层，skyaxis 目前「基线文档→拆分」两层直通，缺的正是业界默认第三层。

## 3. 论证：一步 vs 两步

**四条支持两步**：A 权重错配（2.4，主论证）；B 盲审——硬门① 现在审的是看不到推导过程的清单（为什么这么切/依赖为什么这么排全在会话散文里；Devin 2.0「modify the plan to ensure alignment」可作反衬）；C 知识蒸发——拆分会话的探索结论（哪些模块/哪些缝/什么顺序/什么风险）只活在会话里，下游 WP 计划会话与 re-split 全部重新探索（0007→0008 的「实物交接」教训在 ② 内部重演；Claude Code SPEC.md/PLAN.md 跨会话交接、Codex ExecPlans、Anthropic「infinite exploration」反模式修复三方同型）；D 修正成本——错误传播链 方案错→拆分错→计划错→dev 白跑，规划采纳门是最便宜拦截点。

**三条反方与回应**：① 业界 agent 产品全合并——成立，但 2.4 映射论证瓦解其可迁移性（它们的拆分不进任何账本受治理）；② 单人仪式感过重（BMAD「没参与思考的人才需要批准级流程」）——真风险，缓解=规划步骤可跳过（拆分任务书输入段诚实行「尚无锚定的技术规划文档」，0010 D2 无锚不回退+doctrinal 推力原样复用）+ Claude Code「小任务跳过规划」原则按需求粒度自选；③ 文档层级膨胀（基线→规划→WP 计划→dev）——回应：WP 计划（硬门②）本就存在，规划文档不是新增一层而是把隐含推理显式化，恰好补齐 spec→plan→tasks 中间层；三层真源维度不同（需求 what/why、方案 how overall、分解 how per unit），0009 D2 真源分治的自然延伸，不造第二真相源（账本仍是状态真源）。

**skyaxis 特有约束**：投递=会话草稿人握发送键，会话中途暂停求批准物理上不可能（Jules/Cursor/Devin 的同会话暂停审批学不了）——中间门必须=两次投递。隐藏红利：拆分会话拿到干净上下文（只读基线+规划+按需 repos），与 Codex plan→implement fresh-context、Claude Code showClearContextOnPlanAccept 同型，规划期探索的海量文件读取不污染拆分上下文。

## 4. 设计定稿（六拍板 + 实施裁决，2026-10-15）

**用户六拍板**：① A（拆分结果文件化+回显）与 B（规划文档两步化）**合并一轮交付**；② 规划采纳=**软门**（定稿同构，不锁下游）；③ 拆分机器块 workPackages 提议键**四权闭环**（提议≠登记，登记权在人，硬门①不动）；④ 落点**一族一目录** `.skyaxis/planning/<rid>.md` + `.skyaxis/split/<rid>.md`；⑤ 裁决动作命名**「采纳规划」**（`planAdoptedAt`，驳回侧=撤销采纳/重新投递）；⑥ 两步化方向本身（② 内拆 2a 探索规划 + 2b 拆分，2a 可跳过）。

**形态**（完整实施裁决与连带记档见 [决策 0013](../decisions/0013-拆分结果文件通道与探索规划两步化决策.md)）：

```
S2 探索规划（stage key 'plan'，名实相符）
│ [生成规划任务书]（新 purpose='plan'，九节；无 declare 回传——整理任务书先例）
│   ▶ AI 单写者写 .skyaxis/planning/<rid>.md（现状盘点含探察文件清单/技术方案/
│     改动面/风险与开放问题/实施顺序草案——顺序草案是论证材料，正式清单仍出自 2b）
│ 规划文档卡片（文件卡家族第四份，按 requirement-doc-section 头注预约抽通用件）
│   ├─ [采纳规划]（ack 弹窗）→ planAdoptedAt + planBaseline{docHash, requirementDocHash}
│   └─ [撤销采纳]（摘戳即摘基线，定稿同构）
│ [生成拆分任务书]（输入段加必读规划行三态；输出段改文件交付 .skyaxis/split/<rid>.md）
│   ▶ watcher 收取（文件单通道，sessionId+sha256 幂等锚）
│ 拆包提议区：WP 提议卡片组（ref/标题/边界/依赖/覆盖，坏行跳过并列出）
│   ├─ 逐条勾选 + [登记选中]（host 铸 WP 序号，planned 态入账本）
│   └─ [忽略]（手动出口；新 seed 替换未登记提议——analysis 先例）
│ [批准拆分]（硬门①语义零变化；locked-split 后登记被 400 拒）
```

**失效链延长**：基线重整理 → 规划失效（planBaseline.requirementDocHash 比对）→ 拆分失效（splitBaseline 增 planningDocHash 第六臂，0008 D4 第五臂模式复制）。

## 5. 边界与非目标

- **不做一会话两产物**（规划+拆分同会话）——它让中间门蒸发（拆分在用户看到规划前已派生），退化回一步只多一个工件；要快走跳过路径，不走伪两步。
- **拆分文件不回传 findings/知识到 ①**——新发现仍以人读形式写在拆分文件正文（机器键只 workPackages+plain 键）；回灌 ① 提议行列留下一轮候选。
- **规划文档不进 declare 体系**（无机器回传键）——纯文件交付+采纳锚定，整理任务书先例；knowledge 候选仍走 ⑤ 手动导入。
- **不做 Jules 式拆分提议自动体检**（覆盖空洞/依赖环的模型审查）——v2 候选；本轮覆盖空洞由既有 criteria 空洞高亮承载。
- **不抽第五处文件卡通用件之后的再抽象**——本轮按 requirement-doc-section 头注预约抽 WorkspaceDocSection（第四份到达即抽），仅此一次。
- **规划/拆分任务书不进 revision 戳**（0010 D4 三 AI 语境口径延续）。
