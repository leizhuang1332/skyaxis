## 0. 白话摘要

**场景**：工作台把「分析任务书」投递给一个在工作区里运行的 agentic AI 会话，让它做需求理解阶段的分析。旧版任务书只有四段（需求快照 / PRD 全文 / 知识 / declare 骨架）——AI 拿到后不知道自己是谁、要干什么、先做什么、什么不能做，还要消化一整篇塞进来的 PRD。

**答案**：三路调研（两个规范驱动框架 + 两个技能库 + 两家 agent 官方实践）给出了高度一致的做法——任务书固定为「目标段（角色+读者假设+产物定义+不做清单）→ 数据段 → 约束段（只读/不裁决/有据/有限停止）→ 编号工作流（每类排查带判据与哨兵词）→ 输出段（报告三节正向模板 + 机器可读块）+ 完成自检」；PRD 和代码仓库一律**路径引用 + 阅读指令**，绝不整篇嵌入（三家官方原文都有直接背书）；小体量的账本快照（需求/标准/知识）继续嵌入。新模板九节，analysis 语境专属；其余三种任务书（拆分/工作包/评审）本轮不动（用户拍板）。

**意义**：用户批评的四条（无上下文/无目标/无工作流/无约束）每条都有措辞级业界先例直接对应；「PRD 用路径引用」从直觉偏好升级为有 Anthropic just-in-time 上下文工程、Codex "reference paths only"、spec-kit 九个命令模板零嵌入三方背书的设计原则；分析会话的散文产出（六类发现 + 验收标准建议）第一次与用户手动转录的目标表单字段对齐。

## 1. 问题定义（用户批评拆解）

旧版 analysis 任务书（0006 P2 落地的五段结构在 analysis 语境的实际投影）：

```
[需求]        标题 + 描述 + 阶段 + 工作包快照
[PRD 节选]    勾选章节全文逐段嵌入（无路径）
[知识注入]    命中知识条目全文（8 条 / 8KB 上限）
[输出约定]    仅 declare 骨架，对报告正文只字未提
（戳）         revision 戳
```

四条缺口：① 无上下文（工作区在哪、仓库怎么摆、PRD 文件在哪）；② 无目标（分析 session 该产出什么——六类发现与验收标准建议，任务书里完全没提）；③ 无工作流（先读什么再干什么）；④ 无约束（只读？不裁决？不确定怎么办）；外加 PRD 全文嵌入的上下文膨胀。

## 3. 调研结论

### 3.1 技能库（superpowers / mattpocock）：任务文档怎么写

1. **开头写死「读者假设 + 职责边界」**（writing-plans 第一段）："an engineer who has not seen this codebase or this spec … What they cannot know is what you decided … **Document those**."——你能自己查到的别问别写；你替人拍板的必须写下来。
2. **路径引用是共识**：writing-plans 头部 `Spec: [path]` + "the spec travels with it; executors read both"；handoff 技能 "Do not duplicate content already captured in other artifacts … Reference them by path"。
3. **事实 vs 决策切分**（grilling）："Finding _facts_ is your job, never the user's … The _decisions_ are the user's"——提问每问带推荐答案，措辞让「是」即接受推荐。
4. **约束两层**：HARD-GATE（brainstorming：批准前不得建任何东西，"Reading and exploring are fine"——显式划定允许域）+ 有限停止点（executing-plans 四条枚举）。只读措辞先例（code-reviewer.md）："Do not mutate the working tree, the index, HEAD, or branch state **in any way**."
5. **产出塑形用正向模板、不用禁令清单**（writing-skills 措辞对照实验：竞争性目标下 don't-X 禁令臂产出更多坏内容；"No nuance clauses … Exemption clauses don't scope"）。
6. **完成判据双属性**（writing-for-agents）："checkable and exhaustive"；「已通读代码」须以列出探察过的文件为证（verification-before-completion："NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE"）。
7. **猜测显式标记**（brainstorming："Mark anything you're guessing as your guess"）。

### 3.2 规范驱动框架（spec-kit / BMAD）：分析命令怎么组织

1. **analyze.md 骨架**（与分析任务书最同构）：Goal（单段动词句 + 前置条件）→ Operating Constraints → Execution Steps（编号子节）→ Operating Principles；Done When 清单收尾。
2. **零嵌入铁律**：spec-kit 九个命令模板全部 `REQUIRED: Read <路径> 的 <具名节>` / `IF EXISTS: …` 式路径引用；必需文件缺失 → "STOP with a clear, actionable message … Do not produce partial output"；禁止越权补救（"do not create a new spec here"）。
3. **只读写两遍**："**STRICTLY READ-ONLY**: Do **not** modify any files"（约束段）+ "NEVER modify files (this is read-only analysis)"（原则段复诵）；修复挂钩人批（"user must explicitly approve … (Do NOT apply them automatically.)"）。
4. **检测面 = 具名分类 + 可执行判据 + 哨兵词表**：六 pass 各配判据；歧义类给形容词哨兵 "(fast, scalable, secure, intuitive, robust)" 与占位符哨兵 "(TODO, TKTK, ???)"。
5. **输出契约内嵌字面骨架 + 量化纪律**："Limit to 50 findings total"（超出聚合溢出行）；"Report zero issues gracefully"；"NEVER hallucinate missing sections"；"Output a Markdown report (no file writes)"；严重度评分表写进任务书（宪法冲突恒 CRITICAL）——两轮分析可比。
6. **HALT 条件枚举成串**（BMAD dev）："HALT for: Unapproved deps | Ambiguous | 3 failures | Missing config | Failing regression"。
7. **来源引用纪律**（BMAD create-next-story）："ALWAYS cite source documents: `[Source: 文件#章节]`"——防幻觉 + 把引用落到每条发现。
8. **宪法（常驻稳定上下文）**：IF EXISTS 加载 + 未填模板优雅跳过 + 冲突恒最高级。**映射**：工作台「参考知识」就是 skyaxis 的宪法层。

### 3.3 官方实践（Anthropic / OpenAI）：任务提示与上下文工程

1. **路径引用的官方原文背书**：Anthropic《Effective context engineering》"just-in-time … maintain lightweight identifiers (**file paths** …) and use these references to dynamically load data"；Claude Code best practices "**Reference files with @** instead of describing where code lives"、CLAUDE.md 排除表 "Detailed API documentation (**link to docs instead**)"；Codex "Don't dump large files … **reference paths only**"。混合模型立场：常驻小上下文预载 + 大内容按需自读——正好对应「知识快照嵌入 + PRD 路径引用」的切分。
2. **自含 spec 三要素**（Anthropic 官方）："name the files and interfaces involved, **state what is out of scope**, and end with an **end-to-end verification step**"。
3. **最小充分纪律**：每行过 "Would removing this cause Claude to make mistakes?"；强调只挑一条（"If you emphasize many lines, none of them stands out"）。
4. **Codex review 输出条款**（可直抄）："Present findings first (**ordered by severity with file/line references**), follow with open questions or assumptions … **If no findings are discovered, state that explicitly and mention any residual risks or testing gaps**."
5. **无边界探索是官方点名失败模式**（"The infinite exploration"）：修法 = 点名范围或子代理回传摘要。
6. **两家姿态分歧需显式选边**：Codex 系 bias-to-action（"do not end your turn with clarifications unless truly blocked"）vs Anthropic 理解优先（plan mode / 反向采访）→ 分析任务书须**显式授权提问**，否则 Codex 系模型会自行假设。

### 3.4 合流

四条批评 ↔ 先例：无目标 → Goal 段 + 自含三要素；无上下文 → 工作区/仓库路径清单；无工作流 → 编号步骤 + 完成判据；无约束 → 只读双保险 + 有限停止 + HALT 枚举；PRD 嵌入 → 三家一致的路径引用。

## 4. 重设计（实施定稿）

### 4.1 设计原则

1. **范围（用户拍板①）**：只改 purpose='analysis'；split/dev/review 保持五段结构不动（buildSow 内分派）。
2. **回传面（用户拍板②）**：declare 机器可读块（knowledge + stageReady）逐字节不动——解析/导入面零改动；分析报告的散文结构在任务书里正向模板化，与用户手动转录的表单字段（六类 × 三级发现；标准文本 + 来源节）对齐。
3. **引用边界 = 物理位置**：工作区内的大文件（`prds/`、`repos/`）路径引用（工作区根给绝对路径，防复制粘贴时 cwd 不符）；工作区外的账本（需求/阶段/标准/发现/知识）继续嵌入快照（P1 快照原则 + 诚实戳）。知识注入上限（8 条 / 8KB）不变。
4. 产物固定中文、不进词典（沿用 sow.ts 文件头既有约定）；静态段为纯函数常量。

### 4.2 新模板（九节）

````markdown
# skyaxis 分析任务书 · <需求标题>

## 目标
为需求「<标题>」的需求理解阶段做一次只读分析，产出一份供需求负责人裁决的分析报告——报告读者没读过你的探索过程，只读结论与证据。本阶段两个产物：
1. 分析发现——需求与代码现状之间的矛盾、风险与空洞（六类 × 三级，判据见「工作流」第 3 步）。
2. 验收标准建议——可判定的验收条目草案（工作台将逐条人工审定）。
本阶段不做方案设计、不做工作包拆分、不改任何代码——那是后续阶段的事，现在动手会污染分析。

## 需求快照（工作台账本，生成时快照）
标题 / 描述 / 当前阶段；已有验收标准逐条；未处置发现 [类别·级别] 标题逐条（resolved 不列）；工作包快照。（record 未建立 → 工作台记录未建立）

## 输入（用文件读取能力按路径阅读；不要凭记忆，不要猜）
工作区根目录：<绝对路径，斜杠归一>（下列相对路径以此为根）
PRD 文档（prds/ 目录）：必读 <当前文档>——重点章节：<勾选章节标题>；其余章节按需；其余文档按需
代码仓库（repos/ 目录，均已检出关联分支）：必读 repos/<dir>（<池名>，分支 <branch>）
（诚实缺席行：工作区未绑定 / PRD 列表未可得 / 确认无文档 / 无仓库 / 目录名不可得计数）
路径不存在或不可读：停下来在「待澄清」中报告——不要假设内容，不要自行创建替代文件。

## 参考知识（工作台注入，已审定）
（同今日知识段；发现与之冲突 → 至少「高」级并注明条目标题——宪法层语义）

## 约束
严格只读（不写文件、报告会话内交付）/ 不裁决（录入裁决权在用户）/ 有据（PRD#章节 或 路径:行号；无据标「推测」）/ 有限停止（四类枚举）/ 依据边界（外部信息仅辅助并注明来源）

## 工作流
1. 通读重点 PRD → 需求要点清单（硬约束 vs 愿望，注 PRD 章节）
2. 探索工作区与仓库（限需求相关范围，不做全库漫游；探察文件清单记入报告）
3. 逐类排查六类（可行性/冲突/兼容性/风险/容量/其他，各配判据；歧义哨兵词表）
4. 验收标准建议（站在「交付后如何判定通过」）
5. 待澄清汇总（每问附推荐答案）
先查后问 + 显式授权提问（防 Codex 系 bias-to-action 自行假设）

## 输出
报告三节（分析发现 F<n> [类别·级别] 标题带证据出处，级别降序，20 条上限，六类逐类结论含「未发现」，全零时披露残余风险与探索缺口；验收标准建议 A<n> 可判定句 + 来源章节；待澄清带推荐答案）+ 级别判据行 + declare 骨架（逐字节同旧）+ 完成自检（普通列表，非 checkbox——Spec Kit「[x] = 评审者确认、agent 不得自勾」纪律）

生成于 revision N · 日期 · 此后账本变更不自动同步
````

（措辞全文以 [sow.ts](../../src/client/workbench/sow.ts) analysis 段常量为准；declare 骨架经 `declarePlainSkeleton()` 共享 helper 与五段路径同源，sow.test.ts 逐字 pin 不变。）
