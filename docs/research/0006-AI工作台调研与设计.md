# skyaxis — research 0006：AI 工作台调研与设计（需求详情页工作流管理）

> **状态**：设计稿，待评审。本文只含调研与设计内容，**不含实施进度**——实施进度见 [milestones/0006-AI工作台实施计划.md](../milestones/0006-AI工作台实施计划.md)（P1a 骨架轮已落地）。
> **一句话形状**：AI 工作台 = **需求维度的工作流账本 + 上下文供给器 + 状态聚合器**；它不是自动执行器——执行仍在 DSH session 里由用户发起，工作台负责让流程状态、产物、知识不随 session 消亡。
> **日期**：2026-09-28

---

## 0. 摘要（TL;DR）

- 在需求详情页新增第三个 tab「AI 工作台」（`requirements.detail.view` 槽位新 seat，`detail.tsx`/`view.tsx` 零改动），承载从 PRD 评审准备到知识沉淀的六阶段流水线。
- **核心解法**：工作流状态（阶段、工作包清单、发现清单、上线登记项、知识条目）全部落在 skyaxis 自管 yaml 账本里，session 只是可绑定的"执行器"——任务清单不再随 session 丢失（调研证实：五个规格驱动工具无一例外把产物做成仓库内持久文件，session 是 ephemeral 的）。
- **权责模型**：built ≠ done。AI/session 可起草产物、声明完成、提议知识，但**批准拆分、批准计划、验收确认、阶段推进四类权力永不在 AI 手里**（BMAD v6 / Spec Kit checklist "评审者所有" 原则）。
- **差异化**：上线产物登记（SQL/config/flag/MQ）在所有被调研工具中**均无原生先例**——这是本设计超出行业现状的部分，采用 Flyway/Liquibase 账本模式（唯一编号 + append-only + 内容哈希漂移检测）+ changesets 式"变更时登记、发布时聚合"。
- **治理预警**：本功能服务的用户画像是"需求驱动的企业后端开发者"，与 personas.md 画像 A（独立开发者多 session 可视化）不同；按仓库规则（画像修订须先开 ADR），落地前需补画像与定位 ADR（见 §11）。

## 1. 背景与问题定义

### 1.1 用户工作流七步与当前痛点

| # | 步骤 | 产物 | 当前痛点 |
| --- | --- | --- | --- |
| 1 | **需求理解**：PRD 评审准备（可行性/源码冲突/兼容性/风险/数据体量分析） | 评审会问题清单 | 分析散在一次性 session 里，会前重组费时 |
| 2 | **探索规划**：工作包边界拆分（粗粒度、有范围与顺序） | 工作包清单 | **只存在于某个 session，新开对话即丢失** |
| 3 | **执行实施**：逐工作包开发（调研→开发计划文档→人审→实施） | 开发计划、代码 | 计划文档游离于流程外，人审靠对话 |
| 4 | **验证**：工作包自测验收（端到端→提问题→改→过→提交） | 验收记录、commit | 进度只活在脑子里/对话里，**全局难把控** |
| 5 | **评审**：全量代码评审（bug/性能/运行时 + PRD 验收完成度） | 评审报告 | 报告是一次性文本，裁决无沉淀 |
| 6 | **交付**：中间产物登记（SQL 加字段加索引、开关、MQ 配置） | 上线清单 | **手工记录，怕上线遗漏** |
| 7 | **沉淀**：知识沉淀（业务知识 + 开发约定） | 知识条目 | 每次都要和 AI 重复强调（如导出功能的注意事项） |

横切痛点：每一步的 AI 沟通与执行**散落在各个 session**，无法从需求维度一眼看清"现在到哪、卡在哪、还差什么"。

### 1.2 核心痛点提炼（设计必须解掉的四个）

1. **持久性**：任务清单/计划/裁决必须活在 session 之外（→ 账本化）。
2. **全局进度**：需求维度的阶段与工作包状态一眼可读（→ 流水线 + 状态聚合）。
3. **产物防漏**：上线中间产物在产生时即登记、发布时聚合（→ 登记账本）。
4. **知识复用**：业务知识与开发约定自动注入后续 AI 上下文（→ 知识库 + 任务书）。

### 1.3 与现有定位/画像的关系（治理项，非阻塞设计）

- personas.md 画像 A = "独立开发者、多 session 并行、项目探索"；本功能的真实用户是"需求驱动的企业后端开发者"（PRD、评审会、PM 协作语境）。二者不冲突但有张力：**画像扩展须先开 ADR 再回写 personas.md**（仓库既定规则）。
- 旧 ADR Non-Goals 中"团队协作"仍成立：AI 工作台是**单用户**的工作流管理，评审会/PM 相关能力只体现为"导出物"（问题单、上线单），不做多人协同编辑。
- `vision/positioning.md` 定位"DSH 的 AI 编程可视化插件"；AI 工作台把能力从"可视化"扩展到"工作流管理"，属定位修订，同样建议走 ADR（见 §11）。

> 三路并行调研（规格驱动工具 / issue 跟踪器 AI 集成 / 国内竞品与登记模式），全部结论以官方文档核实为准，二手来源与不可验证项在 §2.6 显式列出。

### 2.1 规格驱动工具（Kiro / Spec Kit / BMAD / OpenHands / Aider）

| 工具 | 流程模型 | 人工审批门 | 任务持久化 | 对本设计的直接启示 |
| --- | --- | --- | --- | --- |
| **AWS Kiro** | Requirements（EARS 记法）→ Design → Tasks 三阶段；Quick Spec 变体免审批门 | 标准流**每阶段产物一门**（Continue 下拉 + 聊天内选项）；任务执行无门 | `.kiro/specs/<feature>/` 三文件，随代码版本化；任务实时状态；**Sync Files** 上游变更后重生成任务并对账已完成项 | ① Analyze Requirements = 评审准备阶段的直接原型：五类发现（逻辑矛盾/歧义/冲突约束/未声明假设/缺失边界），每条 = 涉及需求 + 解释 + 可选修复建议 + 自定义/忽略；② Sync Files = 变更失效对账机制 |
| **GitHub Spec Kit** | constitution → specify → plan → tasks → implement → **converge（只增循环收敛直到 Converged）** | **硬门唯一化**：仅 spec→plan 强制，clarify/checklist/analyze 为按需加装的质量门；implement 前读取 checklist 勾选状态作门，**agent 绝不许自勾**（`[x]` = 评审者确认） | tasks.md：T001 稳定 ID + `[P]` 并行标记 + `[US1]` story 归属 + Foundational 地基阶段 + 每阶段 Checkpoint | ① 硬门唯一思想 → 本设计只设两道硬门（拆分批准、计划批准）；② "评审者所有、agent 不得自勾" → 验收勾选权归用户；③ converge 只增循环 → 自测验收的返工状态机 |
| **BMAD-METHOD**（v4/v6） | v4：SM 起草 story → 用户批准 → Dev 执行（任务+测试+校验全过才勾）→ 用户验证 →（可选 QA）→ done；v6：Clarify → Plan → Build & verify → Learn | v6 **built ≠ done**：agent 只能到 built，done 永远由用户标记；**评审只追加带日期的块、永不改票据状态** | tickets.toml 稳定数字 ID + 每票 plan 文件"拥有状态"；**完成的计划保留不删**（后续评审/回顾的证据链）；story 文件自包含（不回读 PRD 大文档） | ① built ≠ done 双状态 → 工作包状态机的骨架；② 评审与状态机解耦；③ 自包含运行时文档 → 工作包任务书不依赖回读 PRD 全文 |
| **OpenHands** | 无原生多阶段工作流（核实为明确否定） | 提示中声明"改文件/推送/发消息前须请求批准" | conversation.json 会话即档案；skills 支持 **path 触发的确定性注入**（glob 匹配即加载）；hooks 停止前质量门 | path 触发的确定性注入 → 知识触发模式之一（不依赖模型自觉） |
| **Aider** | 无任务清单/工作流/审批门（核实为明确否定） | — | /save /load 会话可重构脚本；markdown 聊天日志 | 仅姿态可取：人可读的审计轨迹 |

### 2.2 Issue 跟踪器 AI 集成（GitHub Copilot / Devin / Jira / Linear / Claude Projects）

| 产品 | 呈现位置 | 状态模型 | 人工介入点 | 对本设计的启示 |
| --- | --- | --- | --- | --- |
| **GitHub Copilot cloud agent** | issue 只做触发入口（Assignees 指派），session 在全局 Agents 面板；PR timeline 承载事件 | session：working / finished | Research → **Plan（对话式迭代计划）** → Implement；"Approve and run workflows"（agent 代码默认不跑 CI，须人批准） | ① commit ↔ session log 互链（审计闭环）；② 指派时上下文快照、后续评论不可见——**上下文边界要显式声明**；③ 计划评审做成对话而非表单 |
| **Devin** | Linear/Jira 内嵌 Activity feed + **Plan tracking（todo 同步到工单 plan UI）** | session 三态 + ACU | **Scoping-only 模式**：只分析工单回帖摘要+实现计划+**置信度**，人批准才启动 session；Managed Devins 子 session 可关自动放行改人工 | ① Scoping-only = "分析→人审→再执行"闸门蓝本（含置信度字段）；② todo→工单进度同步是进度可视化的最直接样例 |
| **Jira（Jira Coding Agent，原 Rovo Dev）** | 工单上 **Agents 区 + Agent sessions 区**（一等区块）；全局 "For you → My agent sessions" 三态分组 + **待处理数徽标** | needs input / working / finished | Start work 选仓库（多仓=多 session）→ 生成中即可看码/改码 → 人点 Create PR；输出"私有草稿→人审→发布为评论"两段式可见性 | ① **内嵌区块 + 全局三态聚合（含待办徽标）**是最被验证的组合 → 工作台布局蓝本；② 私有草稿先行、人审后转正 → 知识候选的可见性模型 |
| **Linear** | issue 内嵌 coding sessions + Reviews tab；diff 直接进 issue，验证产物（截图/录像）与 diff 并排 | delegate（委托不转移归属，人仍是 owner） | 调查/排障/规划类请求**只 scope 不动码**；项目 Updates：健康度三态 + "Write with Agent" 起草、人润色后发布 | ① "调查/规划 ≠ 实施"的意图分流 → 分析类 session 与开发类 session 分用途标记；② agent 起草 update 人发布 → 复盘/沉淀的权责模型 |
| **Claude Projects（claude.ai/code）** | 专属聚合页：协调对话 + 每任务一 thread；Overview **Threads tab 按状态分组**（Ready for review / Waiting on you / Working / …） | 六态分组 | 可口头约定 "Don't open a pull request until I've seen the plan"；**权限审批在 thread 内等待，协调者不能代答** | 项目级 instructions + memory 一次设定全体 thread 继承 → 需求级知识库 + 逐工作包注入的层级关系 |

**横向结论**：① 主流绑定是"一任务一 session"，多仓/多子任务拆多 session，跨 session 上下文靠项目级 instructions/memory；② 计划评审普遍做成**对话 + 置信度**而非表单审批；③ merge/done 权在所有产品里都保留给人。

### 2.4 产物登记与知识持久化模式

**发布账本（Flyway / Liquibase / changesets / release-please）**：

- Flyway `flyway_schema_history`：版本/描述/**checksum**/执行结果；已应用脚本被编辑 → checksum 漂移即报错；版本化迁移按序**只执行一次**。Liquibase 官方直接称之为 "**This ledger**"：changelog 顺序列出全部变更，部署器**只执行账本中未登记成功的项**——"防漏"的本质是登记与执行互为两面。
- changesets：每个 PR 附一个意图文件（YAML frontmatter + changelog 条目），**发布时机器聚合**出版本与 CHANGELOG；release-please 用 **Release PR**（持续更新、人审后合并）承载同一思想。
- 上线检查单常见形态：按阶段分节的核对表 + **go/no-go 逐项签字**；迁移脚本安全/回滚预案/feature flag 渐进放量是强制必过项。

**知识/约定持久化（Cursor rules / Claude memory / Kiro steering）**：

- Cursor rules：Project Rules（`.cursor/rules/*.mdc`，进版本库）/ User Rules / 四种触发（Always / 智能判断 / **globs 文件模式** / Manual @引用）。
- Claude Code：**CLAUDE.md（人写）与 auto memory（AI 自沉淀）分仓**；分层加载；建议单文件 <200 行、指令具体可验证；`/doctor prompt-audit` 审计过时冲突指令。
- Kiro steering：三个基础文件（product/tech/structure）默认注入；工作区级覆盖全局级；四种注入模式（always/fileMatch/manual/auto）。
- **趋势信号**：Devin 的平台集中式 Knowledge 已宣布废弃，自动迁移为**随仓库版本化的 SKILL.md**——行业从"平台侧集中知识库"转向"可版本化、可评审的载体"。

### 2.5 横向结论：九条可借鉴模式 + 三条反向结论

**可借鉴**：

1. 产物皆持久文件、随代码版本化，session 是 ephemeral 执行器（五工具无一例外）。
2. 审批门分级：每产物一门（Kiro 标准流）/ 硬门唯一（Spec Kit）/ 前置问答免门（Quick Spec）——可做成"流程重量"配置。
3. built ≠ done，done 权永不在 agent（BMAD）；checklist 评审者所有、agent 不得自勾（Spec Kit）。
4. 评审只追加带日期的块、不改状态（BMAD）；分析严格只读、修复须人批准（Spec Kit analyze）。
5. 上游变更失效下游 + 对账重生成（Kiro Sync Files）。
6. 内嵌区块 + 全局三态聚合 + 待办徽标（Jira/Linear/Claude Projects）。
7. 计划评审 = 对话 + 置信度（Devin scoping-only / GitHub plan iterate）。
8. 知识注入分作用域 + 多触发模式 + 注入上限（Cursor/Claude/Kiro steering 共识）。
9. AI 产物 = 受审计的系统原生对象，而非一次性文本（ONES）。

**反向结论（设计需自知）**：

- **部署产物登记无先例**：五个规格驱动工具与四家跟踪器产品均无 SQL/config/flag/MQ 上线清单的原生概念——本设计的第 6 步是差异化创新，只能借 Flyway/changesets 的账本模式类推，**无已验证的交互范式可抄**，设计风险自担。
- **平台集中式知识库在退潮**（Devin Knowledge 废弃）：知识载体优先考虑可导出、可版本化的形态，skyaxis 内部账本为真源、导出为分发。
- **Aider/OpenHands 无多阶段工作流**：纯会话型工具不构成参照，不必对齐。

## 3. 设计原则

- **P1 账本即真相（ledger as source of truth）**：工作流状态、产物、登记项、知识全部落 skyaxis 自管账本；session 只是执行器，可死可换。
- **P2 人握门禁（human-owned gates）**：批准拆分、批准计划、验收确认、阶段推进四权归用户；AI 只能起草、声明、提议。
- **P3 阶段是指示器，不是闸门**：六阶段是"当前注意力指针"，可跳过可回退；硬门只设在两处产物上（拆分批准、计划批准），避免流程变重（对齐 Spec Kit 硬门唯一化 + Kiro Quick Spec 的轻量化教训）。
- **P4 产物是原生对象，不是聊天文本**（ONES 范式）：每类产物有 schema、状态、修订号、导出形态。
- **P5 上下文由工作台供给**：新 session 的启动上下文 = 工作台生成的"任务书"（需求 + 工作包 + 已批准计划 + 触发匹配的知识），知识复用不靠用户重复口述。
- **P6 单用户、本地优先**：不做多人协作、不做云同步、不写仓库文件（显式导出除外），沿用既有 Non-Goals 边界。

## 4. 总体形态：需求详情页第三 seat（页面规格 v2）

> **形态拍板（2026-09-28 用户裁决）**：① 阶段导航 = **顶部横向导轨**（否掉二级 tab / 单页滚动）；② 验证**并入执行实施**（六阶段，否掉独立验证阶段）；③ 执行实施的工作包呈现 = **看板分列**（否掉展开式列表）。阶段词汇沿用用户生命周期命名（§1.1）：需求理解 / 探索规划 / 执行实施（含验证）/ 评审 / 交付 / 沉淀。
> **视觉稿**：[0006-ai-workbench-mockup.html](../design/0006-ai-workbench-mockup.html)——浏览器直接打开；含阶段切换/看板卡片→工作包详情/任务书/知识激活的可点交互与浅深双主题；token 值为占位近似，实施时替换为 DSH 真源。

### 4.1 页面解剖（自上而下）

```
┌─ 需求详情页 header（不变）：← 返回 [标题 ▾] ＋ tab 行：概览 | 工作区 | AI 工作台 ◀ ─┐
├────────────────────────────────────────────────────────────────────────────┤
│ ① 需求理解 ─ ② 探索规划 ─ ③ 执行实施 ─ ④ 评审 ─ ⑤ 交付 ─ ⑥ 沉淀    [完成本阶段 →] │ ← 阶段导轨（sticky 置顶）
│   ●2 待处置    ✓已批准·5工作包   3/5·1待验收    —        4项·1待确认   1 候选      │    每阶段徽章计数
├────────────────────────────────────────────────────────────────────────────┤
│ 关联 session（3）：  ● WP3·开发 运行 12m    ○ WP4·开发 待输入    ✓ 评审 · 已完成    │ ← session 条
├────────────────────────────────────────────────────────────────────────────┤
│ （当前阶段内容，随导轨点击切换）                                                │
└────────────────────────────────────────────────────────────────────────────┘
```

- **阶段导轨**（tab body 顶部、sticky）：每阶段一个 chip + 状态徽章（①待处置发现数 ②拆分批准态+工作包数 ③已验收进度+待验收数 ④未处置评审发现数 ⑤登记项数+待确认数 ⑥候选数——Jira 待办 lozenge 模式）。点击 chip = **切换观看**（自由）；`stage` 字段的推进 = 内容区右上 `[完成本阶段 →]` 按钮（用户操作，记 stageHistory）——观看与推进分离。
- **session 条**（导轨下方、跨阶段常驻）：本需求全部绑定 session 的药丸 chips（detailSwitch 语言）+ 状态点（● 运行 / ○ 待输入 / ✓ 已结束）+ 工作包/用途前缀。空态提示引导"生成任务书 → 粘贴到新会话 → 回来关联"。原设计右栏取消——常驻性由导轨徽章 + session 条承担，上线登记/沉淀候选入口分别在 ⑤/⑥ 阶段视图内（徽章计数全局可见）。
- **内容区**：当前阶段的视图（§4.2）。

### 4.2 各阶段视图规格

**S1 需求理解（understand）** — 两个纵向 section（workspace-tab 堆叠先例）：

- **分析发现**：标题行（`分析发现` + ghost sm `[生成分析任务书]` + ghost sm `[＋手动录入]`）+ 发现卡片行列表。发现行：类别+严重度 Tag（源码冲突·高 / 数据承载·中 …）、标题（14/500）、状态 Tag（待处置=warning / 已解决=success / 不处理=中性）、行尾 ⋯ Menu（记方案解决〔必填方案文本〕/ 不处理 / 编辑 / 删除）。点击行展开：详情 + 涉及需求点 + 来源 session + 处置记录。导出 = `评审会问题单`（markdown）。
- **验收标准（PRD 初提）**：标题行 + `[＋]`；行 = `C1 文本` + 覆盖来源 chips（`← WP1,WP3`），无覆盖的 criteria 行 warn 高亮（空洞）。

**S2 探索规划（plan）** — 拆分编辑期用**列表**（看板只属于 S3）：

- 标题行（`工作包拆分` + `[生成拆分任务书]` + `[＋工作包]`）；上游变更时标题行出 stale 徽章 + `[重新拆分 | 确认仍有效]`。
- 工作包卡片行：`WP1 标题` + 边界一行摘要（12 tertiary ellipsis）+ meta 行（`依赖 WP0 · 覆盖 C1,C2 · [P]并行`）+ ⋯ Menu（编辑/删除/上移下移）。
- 底部动作行：**`[批准拆分]` primary（硬门①）**——确认 Modal 列工作包数与 criteria 覆盖统计；批准后卡片组只读、S3 解锁；再次进入编辑 = 显式"撤销批准"（确认 Modal，历史保留）。

**S3 执行实施（implement，含验证）** — 看板：

```
进度摘要行： 3/5 已验收 · 1 待验收 · 1 开发中
┌ 待计划 ────┬ 计划已批准 ─┬ 开发中 ────┬ 待验收 ────┬ 已验收 ───┐  ← 横向 5 列，
│ WP5 外部接口 │ WP4 数据校验  │ WP3 数据导出 │ (built 队列)│ WP1 CRUD   │     窄则横向滚动
│ [草拟中Tag] │ 计划v1 ✓    │ 计划v2 ✓   │ [验收通过]  │ 计划v1 ✓  │
│             │             │ ●2 会话     │ [不通过]   │           │
│             │             │ commit 3   │            │           │
└ [＋工作包] ───┴─────────────┴────────────┴────────────┴───────────┘
```

- **列 ↔ 状态映射**（6 状态收敛 5 列）：`待计划` = planned+plan-draft（卡上 Tag 区分"未起草/草拟中"）；`计划已批准` / `开发中` / `待验收`(built) / `已验收`；dropped 不入板（历史在工作包详情）。
- **工作包卡**（紧凑）：标题（14/500）+ `计划 v2 ✓/草拟中` + 会话行（状态点×绑定数）+ commit 数；`待验收` 列的卡**直接带 `[验收通过] [不通过]`**——该列即验证队列（验证并入本阶段的落点）。
- **点击卡 → 工作包详情宽 Modal（860px，prdWideDialog 先例）**：头 = `WP3 标题` + 状态 Tag；**计划节** = 版本行（v1 归档 / v2 当前）+ MarkdownText 渲染（body max-height 70vh 滚动）+ Modal footer `[退回修改 ghost] [批准计划 primary]`（硬门②，批准的是当前版本）；**会话节** = 绑定行 + `[＋关联 session]`；**commit 节** = 记录行 + `[＋记录]`；**验收节** = 历史（含返工原因）+ 通过/不通过；**节脚** = `[生成工作包任务书]`。
- **v1 无拖拽**：列归属由状态派生，状态只能经动作变更（批准计划/声明导入 built/验收/返工）——拖拽改状态与硬门语义冲突（拖入"已验收"绕过验收权），列为 v2 评估项（若做，拖拽仅允许映射到用户有权的目标列并弹确认）。

**S4 评审（review）**：

- 评审报告卡片列表（`报告 · 2026-09-28 · 发现 8 · confirmed 6 / rejected 2` + `[＋导入报告]`）；点击 → 宽 Modal + MarkdownText 全文。
- 裁决列表（报告下方或报告 Modal 内）：发现行 + 裁决切换（confirmed/rejected，rejected 需填理由——对齐既有对抗校验习惯）+ confirmed 附处置（待修复/已修复/wont-fix）。
- **覆盖矩阵**：criteria 行 + 覆盖工作包 chips（`C1 ← WP1,WP3 ✓`），空洞行 warn 高亮；完成口径 = 发现全处置 + 无空洞。

**S5 交付（deliver）**：

- **go/no-go 总览卡**（banner 语言）：`待确认 1 · 已确认 3 · 漂移 0 · 回滚预案 ☐` → 结论 Tag（前置条件未满足 / GO）。
- **分组清单**（SQL / 配置 / 开关 / MQ / 其他 五个 section）：行 = `R0001 t_order 加索引` + 来源工作包 + envs + 状态 Tag（pending 待确认=warning / confirmed / applied / verified=success / rolled-back）+ ⋯ Menu（确认 / 标记已执行 / 标记已验证 / 回滚 / 编辑〔pending〕/ 删除〔pending〕）。漂移行内 warn 图标+提示；applied 后内容锁定只读（修正 = 新登记 + 旧条目 rolled-back）。
- 头行：`[＋登记]` `[导入声明]` `[导出上线单]`。

**S6 沉淀（retro）**：

- **知识候选**卡片：标题 + draft 两行摘要 + `[激活] [编辑] [丢弃]`；激活 Modal：scope（全局/工作区/本需求）+ type（business/convention）+ 触发（always/path/keyword/manual + 参数）。
- **已激活知识（本需求相关）**：行 + 触发模式 Tag + `[编辑] [归档]`。
- **统计卡**：session 数 / 发现处置数 / 返工次数 / 周期天数（createdAt→closed）。

### 4.4 状态、空态与降级

- **首用**（无 workbench 记录）：导轨全中性、当前阶段 = ①；S1 内容 = 虚线动作卡（addCard 语言）：`生成分析任务书`（无 PRD 时提示并引导跳"工作区"tab）/ `手动添加发现`。

- 徽章计数在数据缺失（degraded）时隐藏不占位。

## 5. 工作流模型

### 5.1 需求级：阶段指针

- `stage` 字段 = 当前注意力所在（六阶段 + closed；key：`understand|plan|implement|review|deliver|retro`，中文标签 需求理解/探索规划/执行实施/评审/交付/沉淀），**用户手动推进**，可回退可跳过（P3）；AI 可在声明块中提议 `stage-ready`，但无权改。观看（导轨点击）与推进（`[完成本阶段 →]`，记 stageHistory）分离（§4.1）。
- `stageHistory[]` 追加式记录每次切换（时间 + 备注）——回溯"这个需求什么时候进的评审/开发"。

### 5.2 工作包级状态机（核心）

```
planned ──起草计划──▶ plan-draft ──用户批准(硬门②)──▶ plan-approved
    │                                                  │ 开发（绑定 session）
    ▼                                                  ▼
 dropped ◀──放弃── planned ──▶ in-dev ──AI声明──▶ built ──用户验收──▶ accepted
                                ▲                   │                │
                                └──返工（验收不通过）──┘                │
                                ▲←──────────重开（评审后发现问题）────────┘
```

- **built ≠ done**：`built` 是 AI/session 的声明（"我认为完成了"），`accepted` 只能由用户操作产生（BMAD v6 原则）。
- 计划文档带版本（v1, v2…），批准的是具体版本；返工不抹历史（"完成的计划是证据链"——BMAD）。

### 5.3 门禁矩阵（AI vs 用户权责）

| 动作 | AI/session | 用户 |
| --- | --- | --- |
| 起草任何产物（发现/拆分/计划/报告/知识候选） | ✓（经声明块导入） | ✓（直接编辑） |
| 批准工作包拆分（硬门①） | ✗ | ✓ |
| 批准开发计划（硬门②） | ✗ | ✓ |
| 工作包标记 built | ✓（声明） | — |
| 工作包标记 accepted / 重开 | ✗ | ✓ |
| 登记上线项 | ✓（声明，入 pending 态） | ✓（确认/新增/删除） |
| 知识条目激活 | ✗（仅提议候选） | ✓ |
| 阶段推进 / 需求关闭 | ✗（仅 stage-ready 提议） | ✓ |
| 评审发现裁决（confirmed/rejected） | 提议 | ✓ |

> 裁决模型刻意对齐本仓库既有的"对抗校验"习惯（confirmed/rejected 双态裁决、rejected 需理由），降低采纳成本。

## 6. 数据模型

### 6.1 WorkbenchRecord（每需求一条，`workbench.yaml` 账本）

```ts
WorkbenchRecord {
  requirementId: string            // 主键，与 requirements.yaml 的 id 对应（容错 join，不持有外键约束）
  stage: 'understand'|'plan'|'implement'|'review'|'deliver'|'retro'|'closed'
  stageHistory: Array<{ stage, at, note? }>
  criteria: Array<{                // PRD 验收标准（S1 初提，可编辑）
    id: 'C1'…, text, sourceSection?, coveredBy: workPackageId[]
  }>
  findings: Array<{                // S1 发现清单
    id, category: 'feasibility'|'conflict'|'compatibility'|'risk'|'capacity'|'other',
    severity: 'high'|'medium'|'low', title, detail,
    status: 'open'|'resolved'|'wont-fix', resolution?, sessionId?, createdAt
  }>
  workPackages: Array<{
    id: 'WP1'…, title, boundary, order, dependsOn: workPackageId[],
    parallel?: boolean, covers: criteriaId[],
    status: 'planned'|'plan-draft'|'plan-approved'|'in-dev'|'built'|'accepted'|'dropped',
    plans: Array<{ version, approvedAt?, note?, contentHash? }>   // 产物文件引用已裁（D4 + 决策 0005 细化②：约定式推导，账本只存 version 等元数据，host 按约定拼路径）
    sessions: Array<{ sessionId, purpose: 'analysis'|'dev'|'review', boundAt }>
    commits: Array<{ hash, repoId?, note, at }>
    acceptances: Array<{ at, result: 'pass'|'fail', note? }>   // 返工历史
  }>
  releaseItems: Array<{            // 上线登记（持续累积）
    id: 'R0001'…, type: 'sql'|'config'|'flag'|'mq'|'other',
    title, content, contentHash,                  // 登记时计算，防漂移（Flyway checksum 模式）
    envs: string[], workPackageId?, sessionId?,
    status: 'pending'|'confirmed'|'applied'|'verified'|'rolled-back', appliedAt?
  }>
  reviewReports: Array<{           // 产物文件引用已裁（decisions/0005 细化①②同款收敛）：报告正文落
    id, at, title?,               // reviews/<reviewId>.md，账本只存引用元数据；P1b 起手轮已按此实施
    contentHash?,                 // host sha256（plans.contentHash 同款；research 原稿的 doc 字段废止）
    verdicts: Array<{ title, severity, verdict: 'confirmed'|'rejected', disposition?, note? }>
  }>
  knowledgeCandidates: Array<{     // 沉淀候选（S6 审阅）
    id, title, draft, type: 'business'|'convention', proposedSessionId?, at,
    status: 'pending'|'promoted'|'dismissed'
  }>
}
```

### 6.2 KnowledgeRecord（全局知识库，`knowledge.yaml` 账本）

```ts
KnowledgeRecord {
  id, scope: 'global'|'workspace'|'requirement',   // workspace 带 path，requirement 带 id
  requirementId?,                                   // requirement 态归属键（P1b 实施补充）：区别于
                                                    // provenance.requirementId（出生地审计）——promote 后
                                                    // scope 变更而 provenance 保留，两者不能混用（D6 级联
                                                    // 按 scope+requirementId 过滤）
  type: 'business' | 'convention',
  title, content,                                    // markdown；建议单条 ≤200 行（Claude memory 官方口径）
  trigger: { mode: 'always'|'path'|'keyword'|'manual', value? },  // Cursor rules 四模式
  status: 'active'|'archived',
  provenance: { requirementId?, sessionId?, at }     // 可追溯（ONES 审计范式）
}
```

### 6.3 存储决策（设计拍板候选，见 §11 决策点）

- **两个独立自管账本**：`workbench.yaml`（按 requirementId 一条）+ `knowledge.yaml`，沿用 repos/requirements 的信封范式（`{version, revision, records[]}`、原子写、乐观锁、坏文件降级拒写）。不并入 requirements.yaml——字段演进风险隔离（milestone 0003 "一行旧数据炸整文件"教训）。
- **产物正文一律独立文件 + 账本内只放引用**（计划文档、评审报告为磁盘上的独立 markdown 文件，账本记录持有引用性元数据）：用户 2026-09-29 拍板（D4），推翻本节原"v1 inline"建议——整文件式账本每次保存都全量重写，产物正文会把 workbench.yaml 推至 MB 级（20 工作包 × 50KB/需求），写放大与 yaml 可读性均不可接受；账本回归纯元数据（指针/状态/历史），体量与 requirements.yaml 同级，R4 随之消解。**五项细化已由 [决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md) 裁决（2026-09-29 用户拍板）**：① 落点 `$DSH_HOME/skyaxis/workbench/<requirementId>/`（与账本同居插件目录，级联清理单点；PRD 的 `workspacePath/prds/` 先例把文档放进工作区，工作流产物不宜混入用户工作区）；② 约定式引用——账本只存 `{version, approvedAt?, note?, contentHash?}`，路径由 host 纯函数从约定推导，browser 永不接触路径；③ 每版本一独立文件（`WP1-v2.md` 定名）+ host 分配 version + sha256 contentHash + 账本先行 + 已批准版本端点级锁定（400 locked-version）；④ 缺失降级三件套——listing 下放 `fileExists` 布尔 + 读 404 + UI 显式缺失态（不造占位），篡改读 200 + `contentTampered` 标记，外加孤儿对账扫描端点；⑤ 短文本按语义一刀切——结构性正文（计划/评审报告）落文件，条目性短文本（findings.detail / 知识条目 / 上线项 content）inline 留账本 + `WORKBENCH_INLINE_MAX_CHARS`（32K UTF-16 码元）双半边单源硬 cap。**上限语义**：单文件读取上限参照 PRD 先例的字节 cap（MarkdownText 冻结阈值，PRD_READ_MAX_BYTES=1MiB）；计划/报告的导出副本列 P5（v1 直达路径文档化，见决策 0005「产物导出承诺」）。
- **字段演进纪律**：所有新字段 optional/default + 手写 guard 同步放宽（0003 教训）；运行态（session 实时状态）不入账本，读时经 `ctx.sessions` 投影。
- **孤儿容忍**：需求删除不级联（避免跨账本耦合，对齐 0002 边界精神）；workbench 记录容错显示"需求已不存在"，提供手动清理。是否改为级联，列为决策点 D6——产物独立文件（D4 拍板）后，D6 的裁决面从"一条账本记录"扩展为"账本记录 + 该需求的产物文件目录"两处，权重上升。

### 6.4 协议与工程落点（按既有范式）

- `src/workbench-shared/protocol.ts`：零依赖 wire + 手写 guards + 路由常量 `/api/skyaxis/workbench/*`。
- `src/workbench-host/`：zod 镜像 + 双向断言（`types.ts`）、`workbench-file.ts` / `knowledge-file.ts`（FileStore）、`endpoint.ts`（list/save/remove + 声明导入 `declare`）。

## 7. 关键机制

### 7.1 任务书（statement of work）——知识复用与半自动回传的枢纽

**生成**：任意阶段可"生成任务书"，产出一段自包含 markdown（Kiro `#spec` 引用 + BMAD story 自包含原则）：

```
[需求] 标题 + 描述摘要 + 当前阶段/工作包状态快照
[PRD 节选] 用户勾选的相关段落（不整篇注入）
[工作包] 边界 + 依赖 + 覆盖的 criteria + 已批准计划（仅当前工作包，S3）
[知识注入] 按 §7.4 触发规则匹配的 active 知识条目（带总量上限，防上下文膨胀）
[输出约定] 要求 session 结束时输出「声明块」——机器可读的 fenced yaml（见下）
```

**投递**：v1 = 复制到剪贴板，用户粘贴进新 DSH session（现状工作流的自然延伸）；v2 视 P0 验证结果接 DSH session 启动/预填 API。**上下文边界显式声明**（GitHub 教训）：包内标注"生成于 revision N，之后账本变更不自动同步"。

**声明块（半自动回传）**：session 被要求以如下结构收尾，工作台提供"从会话抓取 / 剪贴板粘贴导入"解析（P3b 落地）：

```yaml
# skyaxis-declare
workPackage: WP3          # 块级作用域：built 声明与 artifacts 的归属（决策 0006 D8：module: 键已废）
claims:
  - built: true           # 工作包标记 built（AI 声明，仍需用户验收）
artifacts:                # 上线产物登记（入 pending，待用户确认）——条目必须用缩进键值，勿用行内逗号
  - type: sql
    title: "t_order 加索引"
    content: |
      ALTER TABLE ...
    envs: [prod]
knowledge:                # 知识候选（入 S6 审阅队列）
  - type: convention
    title: "导出功能必须走异步 id 滚动"
    draft: "..."
stageReady: false         # 阶段就绪提议（仅预览咨询行，永不落盘——四权在用户）
```

> 诚实预期：声明块依赖模型遵循度，**是半自动而非全自动**（决策点 D3）。兜底 = 全手动录入；声明导入失败逐字段容错（坏行跳过并提示），不整块拒绝——**唯一的整块拒绝是 YAML 语法错误**（带行号提示，保留原文可改）。

### 7.2 session 绑定与实时状态

- 绑定：手动（右栏"关联 session"选择器，从 `ctx.sessions.list` 选取）或声明块携带 sessionId 自动提议；绑定记录 `{sessionId, purpose, boundAt}` 挂在工作包上。
- 实时卡片：session 标题、running 状态、subagent 数（`subagentsByParent`）、点击跳转会话页任务图（复用 task-graph 槽位，不重复造画布）。
- "待输入"判定：bound session 非 running 且存在未完成的用户轮次——**DSH 能力需 P0 验证**；不可得则降级为"运行/空闲"两态。
- 解绑不删历史（`boundAt` 记录仍在，session 消亡只影响实时卡片，不影响账本——P1 原则的直接体现）。

### 7.3 上线清单（登记 / 漂移 / 聚合 / 导出）

- **登记三通道**：① 声明块 artifacts（入 `pending`）；② 右栏"＋"手动登记；③（v2）从 commit/diff 提示补登。
- **防漂移**：登记即计算 `contentHash`；内容再编辑 → 哈希不匹配 → UI 告警"已登记内容被修改"（Flyway checksum 模式）。已 applied/verified 的条目内容锁定只读，修正 = 新登记一条 + 旧条目标 rolled-back。
- **状态流**：`pending（AI 声明）→ confirmed（用户确认进清单）→ applied（已执行）→ verified（已验证）`；任一态可 `rolled-back`。
- **聚合**：S5 视图按 type 分组、每项带 envs/module 归属/状态；go/no-go 总览 = 全部 confirmed 以上 + 无漂移告警 + 回滚预案确认。
- **导出**：上线单 markdown（分组清单 + 状态 + 备注 + go/no-go 结论），贴进发布单/工单。

### 7.4 知识沉淀（双通道 + 触发注入 + 候选审阅）

- **双通道**（对应用户第 7 步的两种沉淀）：`business`（业务知识：域规则、表关系、坑）与 `convention`（开发约定：如"导出功能必须异步 + id 滚动 + 防大表全量"）。
- **捕获**：① 声明块 knowledge（AI 提议，入候选）；② S6 复盘时从本需求的 findings/decisions/评审裁决中手动提炼。**候选 → 用户审阅（编辑/激活/丢弃）→ active**（两段式可见性，Jira 私有草稿模式；"AI 自沉淀"与"人审定"分仓——Claude memory 双机制原则）。
- **注入**：任务书生成时按 trigger 匹配——`always` 全注入；`path` 按当前工作包涉及的仓库/路径 glob（确定性注入，OpenHands 模式）；`keyword` 标题/边界文本命中；`manual` 仅显式勾选。**注入总量设上限**（条数 + 字节数），超限提示用户收窄。
- **导出**：单条/批量导出为 markdown 文件（形态对齐 AGENTS.md / steering / SKILL.md——行业趋势是可版本化载体，skyaxis 账本为真源、导出为分发）。

### 7.5 PRD 验收标准追踪（步骤 5 的"验收标准是否全部完成"）

- criteria 列表是第一等公民（S1 由 AI 初提 + 用户修订），工作包 `covers` 显式引用 criteriaId。
- S4 覆盖矩阵 = criteria × 工作包：每条 criterion 至少被一个 accepted 工作包覆盖；空洞高亮。评审报告的 verdicts 与覆盖矩阵共同构成"需求符合性"证据（对齐 code-review skill 的"需求符合性"维度）。

### 7.6 变更失效与对账（stale）

- 触发：拆分批准后，PRD 文件变化 / findings 新增处置 / 已批准计划的手动编辑 → 相关下游标 stale（badge，不阻塞操作）。
- 动作：用户选择"重新拆分"（旧工作包列表归档保留，新列表生成）或"确认仍有效"（清除 stale）。v1 不做自动 diff 对账（Kiro Sync Files 的全自动版列为 v2）。
