# skyaxis — research 0009：需求理解定稿（S1 收口 → S2 衔接）业界调研与设计

> 日期：2026-10-14
> 依据：用户 2026-10-14 提问——「用户处理完待裁决提议/标准提议/待澄清之后，系统应该如何推进？① 需求理解是不是还应该有一个最终产出？与 ② 探索规划如何衔接？」；结合代码现状盘点 + 六家业界产品一手调研（调研报告全文见本轮会话，全部一手来源直抓）。
> 状态：调研完成，设计经用户三拍板 + 四实施裁决（[决策 0008](../decisions/0008-需求理解定稿决策-软门收口与理解基线.md)），实施落地（milestones/0007）。

## 0. 白话摘要

**场景**：阶段①「需求理解」已走完「分析任务书 → AI 报告 → 用户逐条裁决」的闭环，但系统对「处理完了」无感知——裁决完成度页面上看不到、AI 的就绪提议解析了却断线、推进按钮是纯指针；而下游的拆分会话拿到的上下文只有标准清单，风险裁决与澄清答案一概不知（盲拆）。

**答案**：六家业界产品（Spec Kit / Kiro / BMAD / OpenSpec / Devin / Trae）给了高度一致的画像——理解阶段的收口是一份「把裁决固化进去的产物」+ 一次「轻量的人的确认」，无一造审批状态机；对账分重跑式与只读体检式两派。skyaxis 已对齐两件重件（分析体检≈Kiro Analyze Requirements、澄清回路≈Devin 黄灯），缺的只是收口时刻。补法是**定稿软门**：就绪披露（欠账计数行 + stageReady 咨询行）+ [定稿需求理解] 单戳与轻快照（凭据与对账锚，非第二真源）+ S2 供给升级（拆分任务书九节翻新、从活账本派生处置结论与已答澄清）。

**意义**：「何时算理解完」第一次有了系统内的定义；mockup 悬置四轮的「评审会问题单」以摘要导出兑现（未答澄清正是评审会材料）；stale 对账起点从 S2 门上移到理解收口处，撤销/重定稿/答案变化都成失效信号；P3「阶段是指示器不是闸门」与「硬门只两处」既有裁决原样保持（警示不阻断、可跳过、可撤销）。

## 1. 问题定义（代码现状盘点）

S1 收口真空带的四个事实（2026-10-14 代码核实）：

1. **推进 = 纯指针**：`advanceStage` 无就绪检查、无确认、不看裁决完成度（P3 设计使然——权责正确，但「收口时刻」无处落）。
2. **裁决完成度不可见**：S1 徽章只数 open findings；待裁决提议刻意不进徽章（回传轮拍板④）、未答澄清零信号。
3. **stageReady 断线**：分析任务书教了（sow.ts 输出节）、解析器解析了（declare-parse），但 seed 落账结构无此字段、S1 不渲染——半浪费状态。
4. **S2 盲拆**：拆分任务书只嵌 criteria 清单；未处置发现、处置结论（含方案文本）、已答澄清一概不进；且拆分任务书仍是五段老结构（PRD 整段嵌入——research 0008 已为 analysis 废除的形态）。

另：stale 基线在**批准拆分时**才铸（splitBaseline）——对账起点挂在 S2 门上，理解期的变化对 S2 无感知。

## 2. 调研结论（六家一手来源）

### 2.1 衔接点横向对比

| 产品 | 理解阶段收口产物 | 批准/冻结机制 | 阶段②消费什么 | 上游变更对账 |
|---|---|---|---|---|
| **Spec Kit** | spec.md（clarify 答案逐条回写正文 + Clarifications 节 + coverage 表） | **无批准机制**；软纪律「clarify 应在 plan 前完成，跳过须警告返工风险」；assess 扩展出 go/needs-clarification/kill 决定 | plan 读 spec.md + constitution.md；tasks 再读 plan + spec（双必需） | 无 stale；/speckit.analyze 只读跨产物一致性检查，修复需用户显式批准 |
| **Kiro** | requirements.md（EARS） | **会话确认门**：`Once you confirm the requirements` 才生成 design；无批准状态字段；生成前可选 Analyze Requirements 体检 | design「implements them」→ tasks 从 design 派生 | AI 同步式：改 requirements → 让 Kiro 更新 → design+tasks 一次带齐（`This is expected`） |
| **BMAD** | PRD（组织路径）/ tech-spec（单人 Quick Flow） | **五个具名 sign-off 时点**各阻断后继一步（PRD validate 阻断设计与架构）；「批准必须挂落盘凭据」；readiness 判 READY/NEEDS WORK 为**建议性**；「没参与思考的人才需要批准级流程」——单人走旁路 | spec per epic 从 PRD 派生、**引用不复制**；「下游不得自行解释 PRD——缺答案先回填 PRD 再 re-run」 | **重跑式**：改 PRD → re-run bmad-spec（capability ID 稳定、未涉故事不动）→ 重切 story |
| **OpenSpec** | change 文件夹（proposal + spec 增量 + design + tasks 一次生成） | **无 gate 明文**；批准 = 人过七问检查单后自己跑 /opsx:apply；DAG 依赖是 enabler 不是 gate | tasks 逐条映射 requirement（无映射即红旗） | 文件即真相随手改；/opsx:update 反向涟漪；/opsx:verify 只读核查不阻断 |
| **Devin** | 工单 scoping 评论：置信度灯 + 相关文件 + 分步计划 + open questions | **点链接=批准**（绿→开会话）；黄→工单答问→**re-evaluate 常升绿**；红→转人工（分析留用） | 批准后自动开实施会话出 PR | 问答回流即复评置信度（内建回路） |
| **Trae SOLO** | spec.md → tasks.md → checklist.md 三件套 | **三道逐文档确认门**：每阶段暂停等确认，最终确认后才写码 | tasks/checklist 由确认过的 spec 派生 | 未找到官方对账机制 |

### 2.2 四条可借鉴规律

1. **收口产物 = 把裁决固化进下游要读的产物**（Spec Kit 答案回写 spec 正文、BMAD「答案先进 PRD 再 re-run 下游」）——裁决痕迹不是单独存放的记录。
2. **批准 = 轻量确认挂落盘凭据，无一造审批状态机**；强度三档（逐文档门 / 具名 sign-off / 无门纯纪律），过半无硬门。
3. **下游派生而非复制**（point-not-copy / implements them / 双必需输入）。
4. **对账二式**：重跑式（BMAD/Kiro）vs 只读体检式（Spec Kit/OpenSpec）——后者成本低且与纯读面倾向一致。

### 2.3 与 skyaxis 已建能力的映射（已对齐 / 缺口）

| 业界件 | skyaxis 现状 |
|---|---|
| Kiro Analyze Requirements（design 前体检） | **已有**——分析任务书九节 + 六类排查（research 0008） |
| Devin 黄灯回路（答问 → 复评） | **已有**——待澄清答案进账本 → 任务书快照回灌「已答澄清」→ 新报告（决策 0007 D3） |
| Spec Kit 式理解收口产物 + 确认时点 | **缺**——本轮补 |
| 上游变更 → 下游对账 | **半有**——splitBaseline 在批准拆分时才铸（挂错门上） |

## 3. 差异化约束（不能直接抄业界的地方）

业界全是「文档为真相」（spec.md/PRD 即基线本体）。skyaxis 是**账本为真相（P1）+ 单写者纪律（决策 0007 D3：用户状态永不回写报告文件）**：

- 「答案回写 spec.md」的 skyaxis 等价物**不是**生成新文档，而是**账本裁决状态的冻结快照 + 从活账本派生的任务书供给段**（派生不复制，规律 3）。
- 落一份 `.skyaxis/understanding.md` 会造第二真相源（账本与文件谁新？）+ 单写者归属问题——**导出（只读投影）安全，落盘（第二真源）不做**（本轮 Non-Goal）。

## 4. 设计定稿（三拍板 + 四实施裁决）

**用户三拍板（2026-10-14 AskUserQuestion）**：① 收口形态 = 定稿软门（三组件全做）；② 对人产出 = 定稿摘要导出；③ 拆分任务书九节翻新同轮做。

**四实施裁决（随设计整体通过）**：
- **轻快照**：criteria 全文 + findings 元信息（不含 detail/resolution——20×32K 推爆账本）+ 已答澄清 Q&A。快照是**凭据与对账锚，不是第二真源**——拆分任务书与摘要导出都从活账本派生。
- **stale 两新臂都加**：understandApprovedAt 锚（重定稿/撤销定稿触发；两侧 undefined 等价安静）+ 已答澄清计数（pre-0007 基线缺席按 0 比对不误报）。host 从被盖章记录派生（disposedFindings 纪律）。
- **advanceStage 不动**：定稿是内容事件、推进是注意力事件，解耦；就绪行本身就是提示。
- **摘要导出列未答澄清**：评审会材料核心价值。

**形态三组件**：
1. **就绪披露**（读面零动作）：S1 就绪区 = 未决计数行（待裁决提议 N · 未答澄清 M · 未处置发现 K，warning）+ stageReady 咨询行（success，复用 declare.stageReadyProposal 文案）——两行独立呈现（AI 提议就绪 + 用户尚有欠账并存，Devin 绿灯与黄灯并存同款）。
2. **[定稿需求理解] 单戳**：与 [完成本阶段 →] 并排（advanceRow）；ack Modal 统计四段 + 警示不阻断（带着 wont-fix 进规划是用户裁决权——BMAD readiness 建议性同款）+ 勾选门控；已定稿横幅（gonogo 复用）+ 计数级变化提示（诚实下限：文本级编辑不探测）+ [撤销定稿]（摘戳即摘基线）；主 union 隐式建账（全零定稿 = 合法跳过路径）；重复定稿 400（approve 家族纪律）。
3. **S2 供给升级**：拆分任务书九节化（目标/快照升级/输入路径引用（复用 analysisInputBlock，purpose 名词分流）/参考知识/约束/工作流/输出）；快照段喂**发现处置结论三组（带方案文本）+ 已答澄清 + 定稿状态行 + 现有工作包现状**——BMAD「下游不得自行解释 PRD」的落地；`declarePlainSkeleton()` 逐字节不动；dev/review 五段逐字不动。

## 5. 边界与非目标

- **不做硬门③**（推翻 P3「硬门只两处」且伤跳过路径——业界过半无硬门背书）。
- **不落盘理解文档**（第二真源 + 单写者归属两难；导出已覆盖对人面）。
- **不做拆分提议机器回传**（declare 块扩 workPackages 键——另轮四权论证 + 解析面工程；本轮拆分建议保持散文形态由用户手动录入）。
- **advanceStage 语义零改动**。
