# 仓库池（repos pool）调研：DSH 宿主能力评估与方向规划

> 阶段：需求调研 / 能力评估 / 方向规划（不含实现细节）
> 日期：2026-09-24
> 需求：sidebar.panellist 注册「仓库池」按钮（i18n：仓库池 / repos pool）→ main 区域打开管理页面，维护 git 仓库清单（名称 / URL / 简介），增删改查；添加时校验 URL 合法性（不合法拒绝）与可达性（不可达时区分网络 / 权限原因，用户确认后可放行）；UI 全部复用宿主主题体系（可被任意主题插件一键换装）；数据倾向 YAML 存储。
> 约束：deepseek-harness 宿主源码（../deepseek-harness）仅作调研参考，禁止修改 / link / 引用。

## 0. 调研方法与可信度

- 编排：16 个并行调研 agent（5 主题调研 + 每主题 2 个对抗校验 + 1 个完备性批判），共 916 次工具调用。其中 1 个校验 agent（storage 主题的已发布包审计）因 API 限流失败，其残余缺口已由人工补验关闭（见 §4）。
- 双通道验证：每条关键结论同时对照 **本地 DSH 源码**（可能领先，0.1.7-rc.1 线）与 **已发布包**（skyaxis `node_modules/@deepseek-ai/*` 及 npm 上 0.1.5-rc.2 tarball，skyaxis 实际构建依赖线）。未发现已审计 API 存在版本漂移；但 0.1.5-rc.2 → 0.1.7-rc.1 的契约 diff 未做（见 §7 风险）。
- 负向结论（"做不到 X"）均经过独立猎手扩大范围重搜；4 条负向结论被推翻或修正，修正版收录在附录 A，正文一律采用修正后的表述。

## 1. 总览（TL;DR）

**需求在 DSH 0.1.5-rc.2 上完全可实现，无宿主能力硬阻塞。** 正确架构是「宿主半（Node）负责校验与存储 + 浏览器半负责 UI」：

- **挂载**：向 `main`（keyed 槽位）注册自有 key + 向 `sidebar.panellist`（list 槽位）注册同 id 图标条目，成对出现。点击切换、激活态、tooltip、aria 全部由宿主状态机自带，插件只需两个注册调用。
- **重要澄清**：`main.conversation` 本身是 single 槽位且已被宿主 ConversationRoot 占用，**不能**做附加式注册（注册即整体替换会话外壳）。需求中"main.conversation 区域"的正确机制对应 `main` 槽位中央列（与 conversation 同一区域、并排的新页面）。
- **git 能力**：DSH **没有**任何 git 能力（全库 + 全部已发布包验证，零命中）。但 skyaxis 宿主半可消费 `ctx.subprocess` 原语跑 `git ls-remote`（Windows 支持已核实），失败原因按 stderr/exitCode/signal 分类为网络 / 权限 / 未知三态；浏览器半经 `connection.fetch.register` 自定义 `/api` 端点调用。
- **主题**：三层 token 体系（`--dsw-alias-*` 79 个语义别名，已发布包实测），只消费 alias token 即天然被任意主题插件一键换装；共享组件库 `ui-primitives`（Button/Input/Modal/Menu/RiskConfirmation 等）可直接复用，其中 **RiskConfirmation（复选框门控确认）精确匹配"不可达但用户确认后放行"的需求**。缺 textarea/字段级校验/空态/列表，需按官方规则自建（token 化）。
- **存储**：DSH 无 YAML 存储后端、也无暴露给插件的 yaml 运行时服务，但满足"YAML 落盘"有 4 条路线（§4），推荐 **settings namespace 路线**（落盘就是 `$DSH_HOME/settings.yaml` 的一个 section，真 YAML，浏览器读写通道 `ctx.remote.settings` 现成、带 revision 乐观并发）。
- **需要拍板的唯一架构级决策**：YAML 的语义——共享 `settings.yaml` 的一个 section（路线 A，推荐）还是插件专属 `repos.yaml` 文件（路线 B）。

## 2. 调研问题一：sidebar.panellist 与 main.conversation 槽位

### 2.1 机制：声明-注册两级模型

宿主 UI 包在 `register()` 的 `children` 里声明槽位，插件通过 `ctx.slots.inject(key, () => ctx.slots.register(...))` 在声明存活期贡献内容。仓库池的正确挂载是**成对注册**：

```
浏览器半（src/client/repos-pool/register.tsx）
ctx.slots.inject('main', () =>
  ctx.slots.register({ name: 'main', key: 'repos-pool' }, ReposPoolPage))     // 中央列页面
ctx.slots.inject('sidebar.panellist', () =>
  ctx.slots.register(
    { name: 'sidebar.panellist', id: 'repos-pool', order: 100, label: () => t('panel.reposPool') },
    ({ size, active }) => <svg width={size} height={size} data-active={active} ... />))
```

- **硬约束：`sidebar.panellist` 的 id 必须与 `main` 的 key 完全一致**，否则点击时 `ctx.layout.selectPanel(id)` 抛 `main panel "x" is not registered`（ui-layout service.ts:68-74）。
- 点击链路全宿主内置：PanelRow onClick → `selectPanel(id)` → layout store 的 `activePanelId` → AppFrame 按 `renderSlot('main', {}, { entryKey: activePanelId ?? 'conversation' })` 派发中央列。`selectPanel(null)` 返回会话页。插件**不需要**自己写导航；只有想从别处编程式打开页面时才需 cordis 级 inject 加 `'layout'`。
- 图标条目组件只收 owner props `{ size: 16|18, active }`——插件只画 glyph，按钮本体（chrome、Tooltip、aria-label、aria-current、active 高亮、宽窄两态）全由 sidebar 外壳拥有。
- 排序：`order` 升序、平序保持注册序。i18n：`label` 支持 thunk（`() => t(...)`），locale 切换时宿主自动重解析、无需重注册；注册项还可声明 `locale: NS` 让组件获得 `t` prop。双语即 zh/en 词典各一条（skyaxis task-graph 的 `dictionary.ts` + `ctx.locale.register` 是现成先例）。
- `ui-primitives` 已导出 60+ 个 16px `ic_ds_*` 图标（`fill="currentColor"`，收 `{size, className}`），与 panellist owner props 直接匹配，图标选型无缺口。
- 当前 `sidebar.panellist` 零 shipped 占用者——仓库池将是该槽位第一个真实按钮：无 order 碰撞顾虑，但宽/窄两态视觉无先例，需实机目测。
- 卸载安全：`retainMainPanels` 在选中 key 注销时自动把 `activePanelId` 置 null 回落会话页，无残留。

### 2.2 为什么不能注册进 main.conversation 本身

`main.conversation` 是 single 槽位、scope session-maybe、occupants `['client-ui-conversation ConversationRoot']`、`replaceRisk: 'shadows-shipped-ui'`（slot-catalog.ts:1394-1427）。浏览器半 guard 会为动态注册强制分配低于所有 shipped 条目的 priority，而 single/keyed cell 中最低 priority 者渲染——**插件一注册即成为渲染者、顶掉 ConversationRoot**（整体替换会话外壳，非并排新页面）。官方文档明示："将 single 和已有 occupant 的 keyed cell 视为替换点。增量扩展使用 list id 或尚未占用的 key"（docs/subsystems/slots.zh.md:183）。

`main` 槽位 keyDomain 开放（"open: any string"），非 conversation 的 key 无 session 绑定——正适合全局管理页。宿主自己的测试 `panel-list.client.spec.tsx:104-111` 给出了 main key + panellist id 同值配对的权威最小示例。

### 2.3 限制（负向结论，均经独立复核）

| 限制 | 影响 | 缓解 |
|---|---|---|
| 注册 API 无条件渲染字段（无 when/if/enabled） | 不能"有数据才显示按钮" | 注册/注销生命周期控制；或先注册、图标按 store 状态渲染占位 |
| panellist 条目不能自定义按钮本体，无 badge/二级菜单/分组 | 按钮形态完全跟随宿主 | 无（也正是主题一致性的来源）；页脚 `sidebar.footer.action` 槽位允许自持按钮 chrome，但不带 selectPanel 接线 |
| `activePanelId` 不持久化（layout store 无 persist） | 刷新后回到会话页，仓库池页不保留 | 已知限制，接受或后续向宿主提需求 |
| 非 conversation 面板的浏览器标签标题回落通用 productTitle | 无宿主级自定义标题机制 | 已知限制，接受 |
| skyaxis 依赖树缺 `dsh-client-ui-layout/ui-sidebar` 的 rc.2 副本（npm latest 标签停在 0.0.1-rc.1） | 裸装类型包会拿到过期契约 | 照 task-graph 先例用本地 `declare module` 合并 SlotMap（零新增依赖，已验证可行） |

## 3. 调研问题二：git 地址校验与 DSH git 能力

### 3.1 DSH 没有 git 能力（负向结论，已扩大范围复核）

- 全库（packages/ 约 70 子包 + apps/ + docs/ + vendor/ + native/ + python/ + benchmarks/ + pnpm-lock）无 isomorphic-git/simple-git/dugite/nodegit、无 git 命令服务、无 git URL 解析器；唯一 git 痕迹是 shell 工具的 prompt 示例文案。
- 全部已发布 `@deepseek-ai` 包（node_modules 20 包 + 抽查 rc.2 tarball）`.d.ts` 中 'git' 关键词零命中。
- **`@deepseek-ai/dsh-api-remotes` 的 "Remote" 与 git remotes 无关**——它是 Host↔Client RPC BFF（19 个命名空间：session/settings/workspace/... 无 git/exec/fetch）。skyaxis inject 它对 git 校验无用（但对 settings 读写有用，见 §4）。

结论：git 校验逻辑必须插件自建，但原语齐备。

### 3.2 正确路径：宿主半校验服务 + 浏览器半 UI

skyaxis 本身就是双面插件（node 半 exports "." 跑在宿主进程、浏览器半 exports "./client"），宿主半可 `ctx.inject(['subprocess'], ...)` 可选消费 base composition 默认装载的原语服务（skyaxis 已用同模式消费 sessionProjections）：

**可达性主路径：`git ls-remote --heads <url>`**

```
const exe = await ctx.subprocess.resolveExecutable('git')   // PATH 解析 + 绝对路径校验
const h = ctx.subprocess.spawn({
  argv: [exe, 'ls-remote', '--heads', url],                 // 显式 argv，无 shell 解释
  stdio: { stdin: 'ignore', stdout: { maxBytes: 65536 }, stderr: { maxBytes: 65536 } },
  graceMs: 5000, signal: ctrl.signal,
})
const { exitCode, signal } = await h.done
const stderr = h.collected.stderr?.readFrom(0).text          // 注意返回对象取 .text
```

失败分类（git 通用行为）：
- **可达**：exitCode === 0
- **权限原因**：stderr 含 `Authentication failed` / `could not read Username` / `Permission denied` / `HTTP 401/403`
- **网络原因**：stderr 含 `Could not resolve host` / `timed out` / `Connection refused`，或 signal 非 null（本地超时 abort）
- **未知**：兜底第三态（stderr 文案随 git 版本与 locale 变化——zh_CN 环境可能是中文 fatal，匹配需宽松 + exitCode 兜底）

工程细节（均已核实）：spawn env 默认剥离凭据形环境变量、自动传递代理变量（HTTPS_PROXY 部署下仍可用）；注入 `GIT_TERMINAL_PROMPT=0` 避免挂起等输入（其 stderr 表现恰好归入权限原因）；`subprocess-local` 完整支持 Windows（win32 环境变量大小写不敏感合并、taskkill /PID /T /F 树终止）——本机 Windows 11 宿主可用。私有仓库凭据可选用宿主 `ctx.credentials` 服务存 token（`$DSH_HOME/.credentials.yaml`，非必需）。

**宿主未装 git 的降级**：`resolveExecutable('git')` 失败时退化为"仅语法校验 + 提示可达性未验证"，或回退 `ctx.web.fetch` 探测（仅公网 http/https：GET-only、无认证头、SSRF 防护拦截私网 IP/NAT64/URL 内嵌凭据——企业内网 GitLab 会被拦，故只作备选）。需产品决策（§6）。

**合法性校验**：DSH 无现成实现，插件自写（WHATWG URL + scp 启发式正则，覆盖 https/http/git@ssh/scp 风格 `host:path`/ssh:///file://，schema 层复用已依赖的 zod/schemastery）。**安全要求：必须显式拒绝 `ext::`/`fd::` 等传输**（git 历史上可执行任意命令；argv 无 shell 降低了注入面，但传输协议本身是执行面）——scheme 白名单需拍板（§6）。

### 3.3 浏览器半 ↔ 宿主半通道（官方扩展缝，两条）

浏览器半不能执行命令、不能直连外站 git 服务（remote 命名空间固定集无 exec/fetch；CORS 阻断），校验必须宿主半做，经以下通道暴露：

1. **`connection.fetch.register`**（推荐，最简）：宿主半注册 `/api/skyaxis/repos/validate` 路由（POST，buffered），浏览器半同源 `fetch` 自动认证（launch-token → 签名 cookie）。宿主侧 4 个官方用例（session-log-export/media-references/file-upload/ui-deliverables）。硬约束：path 必须在 `/api` 之下、methods 仅 GET/HEAD/POST。
2. **`connection.rpc.intercept`**：对齐 Gateway 的 `ConnectionRpcResult` 错误词汇（`{ok:true,value}|{ok:false,error:{code,message,details}}`），浏览器侧 `ctx.connection.rpc.call('/api', 'skyaxis/repos.validate', payload)`。

skyaxis 的 `dsh.client.inject` 已含 `dsh-client-connection`，通道现成。

### 3.4 被排除的替代路径（附修正后的理由）

- `ctx.remote.commands/execute`：**不是** LLM 轮次（原始调研误读，已被裁决修正）——它路由到 dsh-commands 注册表的确定性宿主 handler、零 token。但仍是 agent-scope（需活跃会话）、输入为单条斜杠文本行、每次执行向会话日志追加 command/run+done 事件污染记录、公开 API 只返回 `{matched}`。不适合表单校验。
- 动态 Cordis（dynamicCordisRunner）：定义 session-scoped 且仅存进程内存（重启即失）、宿主半跑 node:vm 沙箱。不适合。

## 4. 调研问题三（主题）与问题四（存储）

### 4.1 主题 / 设计 token / 组件

**token 体系（三层，`ui-theme` 包独占拥有）**：

1. `--dsw-static-{amber,blue,deepseek,green,neutral,neutral-bluish,red}-{50..1000}` 原始色板（亮暗同值）——feature 组件**禁止**直接使用
2. `--dsw-alias-*` 语义别名（已发布 rc.2 实测 79 个；亮暗双套，`body[data-ds-dark-theme]` 切换）：`bg-base/bg-layer-1/2/3/bg-overlay/bg-skeleton`、`border-l1..l4`、`label-primary/secondary/tertiary/caption/dimmed`、`button-*` 家族、`interactive-bg-hover/active/hover-danger`、`state-error/success/warn/business-*`、`link`、`toast-bg`、`tooltip-bg`、`scrollbar-bg-l1/l2`——**feature 组件只允许用这一层**（注意：`--dsw-alias-state-business-secondary` 不存在，business 家族只有 primary/tertiary）
3. `--dsw-specific-*` 组件面 token（sidebar-fill 等）——官方定位归组件所有者，仓库池保守不用

另有字体阶梯 `--dsw-font-{xl-24..xxxs-11}`、elevation `--dsw-elevation-{stroke,panel,prominent,soft}`、动效 `--ds-transition-duration`/`--ds-ease-in-out`、正文 `--dsh-content-font-size`（12-17px 联动）。

**一键换装原理**：主题切换 → `theme/change` → ui-layout 的 theme-presenter 把解析后的 token 逐个写成 **body 内联 CSS 变量** + 切 `body[data-ds-dark-theme]` → CSS var 级联到所有消费方。第三方主题插件 = 普通 client 插件调 `ctx.theme.register({id, colorScheme, tokens})` 或 `overrideTokens`。因此**仓库池页面只要消费 alias token、不做任何事即可被任意主题插件换装**。JS 侧感知主题用 `ctx.theme.getTheme()`（type-only import，禁止 value import）。

**官方硬规则**（docs/web-styling.md）：只用 `--dsw-alias-*`；不抄 static 值、不写字面颜色；不写 dark-theme 选择器；CSS Modules + clsx；不引入组件库/Tailwind；字号配行高；0.5px 发丝边框；浮层 border:0 + elevation shadow。第三方主题注册无完整性校验——所以只用核心 alias 家族（bg/border/label/state）保证被覆盖面最大。

**可复用组件**（`@deepseek-ai/dsh-client-ui-primitives`，rc.2 已发布且在宿主 web shell 冻结静态模块表内，插件 external 后 require 即得宿主同一实例）：

| 需求 | 组件 | 备注 |
|---|---|---|
| 按钮 | `Button` | variant primary/ghost/outline/toolbar；size md/sm |
| 仓库名/URL 输入 | `Input` | 单行，icon 可选 |
| 添加/编辑仓库弹窗 | `Modal` | open/onClose/title/footer，Escape+遮罩关闭 |
| 行内操作菜单 | `Menu` | items 支持 danger/separators/submenu |
| **不可达确认放行** | **`RiskConfirmation`** | 复选框门控确认（勾选前主按钮禁用）——精确匹配需求 |
| 状态徽标 | `Tag`(8 tone) / `StateDot`(5 态) | 校验结果展示 |
| 提示 | `Tooltip`/`Toast`/`HoverCard` | |
| 图标 | `icons/*` 60+ 个 16px glyph | `currentColor`，与 panellist 对齐 |

**宿主没有、需自建**（官方规则允许且预期，自建时样式只消费 alias token）：textarea（简介字段——宿主 Input 明确是单行原子，composer textarea 属会话特性包不可跨插件 import）、字段级校验错误提示（用 `--dsw-alias-state-error-primary` + Tag tone='danger'）、空状态、加载态（StateDot 'ongoing' 或 `--dsw-alias-bg-skeleton` 骨架）、列表/表格布局。

**skyaxis 侧现状与接入成本**：

- **task-graph 是反面教材**：view.tsx 20 处 `var(--skyaxis-*, #hex)`（变量全仓库零定义，实际生效的是硬编码浅色 hex）、0 处 `--dsw-*`——暗色/主题插件下不可用。仓库池**不可照抄**此模式；同页共存会有视觉割裂（是否顺带迁移 task-graph 超出本次范围，见 §6）。
- 接入 ui-primitives 三步：`pnpm add -D @deepseek-ai/dsh-client-ui-primitives@0.1.5-rc.2`（latest 标签过期，必须显式 pin）→ `shared/tsdown.client.ts` 的 `PLATFORM_MODULES` 加该 specifier（否则自建纯度门禁构建报错）→ import。无需动 `dsh.client.inject`（静态表成员与 inject 机制正交）。
- CSS 管线：skyaxis vendored 构建预设无 CSS Modules 管线（task-graph 现状是 `?inline` 字符串 + 手动 `<style data-plugin>`）。两条路：照抄 DSH 官方 `dsh-css-modules-inline`（lightningcss，loader 自动注入）补齐预设；或继续手动 style 标签但值全部换 `--dsw-alias-*`。实现期决策。
- 组件测试：skyaxis 现状 node 纯函数测试，但宿主有 10+ 个 `@vitest-environment jsdom` per-file pragma 组件测试先例（真 SlotRegistry/真 cordis fiber，零 mock 桩）可直接照抄——jsdom 与 ui-renderer 已在 devDeps。

### 4.2 存储路线（决策矩阵）

DSH 存储事实（均已对 rc.2 已发布包验证）：

- 存储子系统只有 json/sqlite 后端（`packages/storage/` 四包），无 storage-yaml；**但后端注册表是公开扩展点**——已发布 `dsh-storage@0.1.5-rc.2` 的 `registry.d.ts:21` 导出 `register(name: string, backend: StorageBackend): () => void`（本次人工补验关闭残余缺口）。
- 运行时无暴露给插件的 yaml 服务（宿主内部 settings-file/credentials-local 私有依赖 yaml ^2.9.0）；坚持 YAML 自管必须自带 yaml 库。
- cordis 插件 Config 是组合期声明，无持久化写路径，不能作 CRUD 载体。
- 浏览器半不能直接碰宿主 fs / ctx.storage（host-side only）；现成 client→host 通用读写通道只有 `ctx.remote.settings`。
- skyaxis 仓库内无任何持久化先例（store 全内存随 disposer 销毁）；但 `createSnapshotStore` 原生支持 `persist:{name}`（localStorage，可作 UI 镜像非权威存储）。

| | **路线 A：settings namespace**（推荐） | 路线 B：专属 repos.yaml | 路线 C：storage-domain(JSON) + 手写 typert remote | 路线 D：自实现 yaml backend |
|---|---|---|---|---|
| 落盘 | `$DSH_HOME/settings.yaml` 的一个 section（**真 YAML**，保注释/锚点、原子写、跨进程文件锁、热重载） | `$DSH_HOME/skyaxis/repos.yaml`（自管） | `$DSH_HOME/storages/<unit>.json` | `$DSH_HOME/storages/` 下 YAML 介质 |
| 浏览器读写通道 | **`ctx.remote.settings` 现成**（describe/update/mutate + expectedRevision 乐观并发；skyaxis 的 inject 已含 dsh-api-remotes + dsh-client-ui-settings，client 入口 cordis inject 加 `'remote'` 即用） | 自建（复用校验端点扩展 list/save） | 手写 TypertContribution（`ctx.typert.register` + `ctx.remote.$mount`，官方文档支持的手写路线；typert-protocol rc.2 已发布） | 同 C |
| 校验端点 | 仍需自建 `/api` 端点（settings remote 不能执行代码） | 同一端点顺带承载 | 同 A | 同 A |
| 数据语义 | namespace 内 schemastery schema 校验；数组写是整体替换；插件卸载 section 不丢 | 全自管（自带 yaml 库 + node:fs + 自担原子性；有 .credentials.yaml 先例） | zod 读边界、单写原子、domain/changed 事件、域语义最正规 | domain 层完整落在 YAML 上 |
| 新增依赖 | `@deepseek-ai/schemastery`（类型源；skyaxis 现用社区版 schemastery——fork 的 npm 可得性未验证，可能需类型断言） | `yaml` + `@deepseek-ai/dsh-home-paths` | `dsh-storage-domain` + `dsh-typert-protocol`（npm 均有 rc.2） | 同 C + `yaml` |
| 主要风险 | ① 用户手编坏整份 settings.yaml = **宿主 boot 失败**（官方 fail-loud 设计）；② 注册时 section 已坏 = `ctx.settings.register` 抛错 → **宿主半 apply 失败**（需 catch 降级）；③ 宿主设置页可能按 schema 自动渲染该 namespace 表单（未验证）；④ `redactSecrets` 只剥 role('secret')——URL 内嵌凭据明文往返并存 YAML | 脱离宿主原子写/校验/热重载体系，全自建 | 非 YAML；手写 remote 需一次 PoC 回环 | 工作量最大（实现 KvUnit 契约 + bundle patch 改 routes），收益仅"domain 层 + YAML" |
| 成本 | **最低** | 中 | 中 | 高 |

**推荐：路线 A 为主案**——它同时满足"YAML 落盘"与"最大化复用宿主能力"（读写通道、schema 校验、原子写、乐观并发、热重载全部宿主自带），新增活动部件最少；把 §6 的三个风险点作为设计约束处理。若"专属文件"是硬诉求再转路线 B。命名注意：settings namespace 只允许 `-`（`skyaxis-repos-pool`），storage 域名只允许 `_`（`skyaxis_repos_pool`），两套规则互斥。

### 阶段划分

- **P0 拍板与 PoC**（§6.1 决策点 + §7 PoC 清单）——本阶段产出。
- **P1 骨架**：双槽注册 + 空页面 + i18n 词典 + ui-primitives 接入（devDep + PLATFORM_MODULES）+ token 化样式基座。验收：按钮出现、点击切换、亮暗/主题插件下视觉正确。

- **P3 打磨**：列表/空态/加载态/删除确认、revision 冲突处理、错误文案双语。
- **P4 测试与实机验收**：纯函数测试（校验器/schema/分类器）+ jsdom 组件测试（照宿主 pragma 模式）+ 实机检查单（宽窄两态、主题插件换装、Windows ls-remote、卸载回落）。

### 6.1 需要拍板的决策点

> **已全部拍板（2026-09-24）**：路线 B（专属 repos.yaml）、file:// 拒绝、git 缺失仅语法校验放行、未知失败拒绝——详见 [决策 0003](../decisions/0003-仓库池P0决策-路线B专属repos-yaml与校验策略.md)；实施计划见 [milestones/0001](../milestones/0001-仓库池实施计划.md)。以下为决策时的原始选项。

1. **YAML 语义**（架构级，前置）：路线 A（settings.yaml 的 section，推荐）vs 路线 B（专属 repos.yaml）。差异本质：共享文档 + 全套宿主能力 vs 专属文件 + 全自建。
2. **URL scheme 白名单**：https/http/git@/ssh/scp 必收；`file://` 是否放行（本地仓库）；`ext::`/`fd::` 必拒（安全）。scp 风格与 ssh 的歧义处理策略。
3. **宿主未装 git 的降级**：仅语法校验放行（提示可达性未验证）vs 回退 web.fetch 公网探测。
4. **三态分类的用户交互映射**：网络/权限/未知三类失败，哪些允许"确认后放行"（需求原文网络+权限可放行；建议未知也允许但文案更谨慎），以及放行后是否在列表上持久标记"未验证"状态。
5. **settings 页副作用**（若走路线 A）：宿主设置页可能自动渲染 namespace 表单——PoC 确认后决定接受（当作免费配置入口）还是规避。
6. **URL 内嵌凭据策略**：`https://user:token@host` 形态的 URL 是否允许入库（会明文落 YAML；redactSecrets 不覆盖）。建议拒绝并引导用 credentials 服务。
7. （可选，超范围）task-graph 既有硬编码样式是否借机迁移 `--dsw-alias-*`。
