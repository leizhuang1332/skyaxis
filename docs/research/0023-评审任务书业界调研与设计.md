# skyaxis — research 0023：评审任务书业界调研与设计

> 日期：2026-10-21
> 依据：用户 2026-10-21 拍板「立项补齐」——评审任务的目标有两大方向：① 需求完成情况（代码是否满足验收标准）；② 代码质量情况（代码本身是否有风险漏洞或 bug）。前一轮缺口评估（会话记录）结论：当前评审任务书是「数据简报＋输出契约」而非「评审方法论」，两目标都依赖 AI 对「评审」二字的自行发挥。要求调研业界同类产品与大厂开发规范后重设计。
> 状态：调研完成（四路并行），设计草案成形，待用户决策点拍板。

## 0. 白话摘要

**场景**：工作台把「评审任务书」投给一个 agentic AI 会话，让它在读过基线文档与仓库代码后，回答两个问题——代码做到验收标准了吗？代码本身有没有毛病？旧任务书只递了材料（标准清单＋仓库路径）和回传契约（`# skyaxis-review` findings 块），没说一句要查什么、怎么查、查到什么程度算数。

**答案**：四路调研高度合流——① Google 官方评审指南给「查什么」的九维清单与「逐行读、看全文、以代码库健康为准绳」的纪律；② Sonar 三域（可靠性/安全/可维护性）＋ OWASP 六类漏洞模式给质量审计的具名分类；③ 与 AI 任务书最同构的 Qodo PR-Agent 提示词原文里有**逐条验收标准的结构化核验**（满足/不满足/需人工复核三分）、「有把握才报、不确定但高危要标注不确定性」的发现纪律、每条发现带文件行号的证据结构；④ 微软 ICSE 研究佐证评审动机里找缺陷第一（44%）、代码改进第二（39%），两目标正是业界评审的主目标。设计草案：评审任务书九块化（目标/快照/输入/知识/约束/工作流/输出），工作流里「逐条核验验收标准（三值判定+证据）→ 六维质量排查（各配判据）」双线并行，输出报告固定三节（总体结论/验收核验/质量发现），机器块按拍板决定是否扩核验节与 detail 字段。

**意义**：两目标从「AI 自行发挥」升级为「具名分类＋可执行判据＋证据纪律＋如实分级」——这正是 0008 分析任务书重设计时已经验证过的配方（六类排查＋哨兵词＋级别判据），本轮把它推广到评审任务书；「无法核验」作为一等判定值（PR-Agent `requires_further_human_verification` 先例）让「代码评审判不了的事」诚实显形而不是硬编结论。

## 3. 调研结论

### 3.1 Google 官方评审指南：查什么、以什么为准绳

来源：[What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)（全文直抓）。

1. **九维清单**（官方总结清单原文转写）：**Design**（与系统整体契合、这是不是这段代码该在的地方、与其他系统交互是否协调）；**Functionality**（站在开发者意图与用户视角查行为，「亲自验证 UI 变更时应让开发者演示走查」）；**Complexity**（逐行问「能看懂吗」＋「真的需要吗」两问；过度设计也是缺陷——「为未来推测性需求写的代码」要拦）；**Tests**（正确、设计良好、不过度也不欠缺）；**Naming**；**Comments**（解释为什么而不是是什么）；**Style**；**Consistency**（与既有代码库一致，不一致处是代码库该改还是本次该改）；**Docs**（关联文档同步）。
2. **证据纪律与准绳**：逐行读（「skim it and assume」是显式反模式）；上下文要看整个文件与其余代码库（「不要只看 diff」）；准绳是**代码库健康度**——「一个 CL 让代码库整体健康度下降，就不要接受」；时序上「维护正在进行中」是常态。
3. **正面反馈**也在清单里（值得夸的就夸）——人评特有的维度。

### 3.2 质量模型与安全审计：质量审计的具名分类

1. **SonarSource 三域**（[官方产品页](https://www.sonarsource.com/products/sonarqube)）：**Reliability**（bugs）/ **Security**（vulnerabilities＋security hotspots）/ **Maintainability**（code smells＋技术债），各域 A–E 评级，Quality Gate 卡**新增代码**的门。映射：目标二的「风险漏洞或 bug」在业界是两个独立域（缺陷≠漏洞），可维护性是第三域。
2. **OWASP Secure Code Review Cheat Sheet**（[官方页](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html)标题结构直抓）：
   - Common Vulnerability Patterns 六类：**Input Validation / Injection / Authentication & Session Management / Access Control / Deserialization / Cryptographic Implementation Flaws**；
   - Review Checklists 七张：Input Validation、Authentication & Session Management、Authorization、Cryptography、Business Logic、Configuration & Deployment、Security Monitoring；
   - Review Techniques 四法：Code Pattern Analysis / Data Flow Analysis / Threat-Based Review / Business Logic Review。
   - 映射：安全维的判据不必自造——OWASP 六类模式就是现成枚举。
3. 微软 ICSE 2013（[Bacchelli & Bird](https://ieeexplore.ieee.org/document/6606617)，[PDF](https://sback.it/publications/icse2013.pdf)）：找缺陷是第一动机（44% 受访开发者列第一）、代码改进紧随（39%）；实际评审评论中缺陷占比低于预期，知识转移/代码改进是大头。映射：**两目标的排序（验收达成→质量）与业界动机面一致**；AI 评审会话砍掉知识转移维度是诚实的（它没有团队），聚焦缺陷与质量反而更纯。

### 3.3 AI 评审产品：与任务书最同构的先例

**Qodo PR-Agent `/review`**（`pr_agent/settings/pr_reviewer_prompts.toml`，main 分支原文直抓——本轮最重要的一份材料）：

1. **逐条验收核验是结构化一等输出**（目标一直接先例）：`TicketCompliance` 要求先把工单需求「用自己的话复述为清单」，然后三分：`fully_compliant_requirements` / `not_compliant_requirements` / `requires_further_human_verification`——第三值明确定义为「**cannot be assessed through code review alone**, are unclear, or need further human review (e.g., browser testing, UI checks)」。
2. **发现纪律**（可直抄的措辞级先例）：「For clear bugs and security issues, be thorough…For lower-severity concerns, be certain before flagging」；「When confidence is limited but the potential impact is high (e.g., data loss, security), report it with an explicit note on what remains uncertain. Otherwise, **prefer not reporting over guessing**」；「Do not flag intentional design choices or stylistic preferences unless they introduce a clear defect」；「Do not overstate impact. If an issue only arises under specific inputs or environments, say so upfront」。
3. **每条发现带定位与内容**：`KeyIssuesComponentLink` = relevant_file + issue_header（如 'Possible Bug'）+ issue_content（「为什么是问题＋触发的具体场景」）+ start_line/end_line。
4. **安全关切显式问、零发现显式答**：`security_concerns` 字段——无则回答字面 'No'（优雅零发现的机器可读版，spec-kit "Report zero issues gracefully" 同款）；`relevant_tests: Yes|No` 单独成字段。
5. **总体风险评级带判据**：`risk_level: low|medium|high`——「high 仅当明确 bug/安全/重大逻辑风险；medium＝不明确坏但有需人工细看的非平凡区域；low＝小、低影响、无重要问题」。
6. **失败模式推演**（最多 3 条，防泛泛而谈）：`FailureMode` = what（合并后怎么坏）/ where / trigger（现实触发输入）/ detected_by（什么测试或告警能抓到，抓不到写 'nothing'）/ covered_in_this_pr——「grounded in the visible changes, **not generic risks**. Return an empty list when no concrete scenario is supported」。
7. **AI/人分工**：`review_priority_files`（人该先看哪些文件）——AI 报告面向人类复核的定位，与 skyaxis「报告读者没读过你的评审过程」同构。

**GitHub Copilot code review**（[官方文档](https://docs.github.com/en/copilot/using-github-copilot/code-review/using-copilot-code-review)页面直抓）：Lite 档＝「glaring issues such as **bugs, security vulnerabilities, style inconsistencies**」；Balanced 档＝「deeper analysis of **complex logic, security-sensitive code, cross-service changes**」。映射：AI 评审的默认盘面就是 缺陷/安全/一致性 三件套，深档加复杂逻辑与跨服务。

**CodeRabbit**（[官方博客](https://www.coderabbit.ai/blog/code-reviews-made-easy-how-to-improve-code-quality)）：AI 管「high-volume, lower-judgment categories（null 检查、风格、常见安全模式）」，人管「higher-level design and architectural decisions」。映射：AI 提议/人裁决的分工边界有业界共识背书——AI 不替人下架构裁决，与本项目「不裁决」约束同源。

### 3.4 需求符合性验证：业界现状与空白

1. PR-Agent `TicketCompliance`（3.3-1）是唯一抓到的**已发布**结构化核验先例。
2. **spec-kit 没有已发布的对应命令**：[#1745](https://github.com/github/spec-kit/issues/1745)（2026-03）请求新增 `/speckit.verify`「验证全部验收标准已满足」，承认当前「manual verification passes are needed」；[#1865](https://github.com/github/spec-kit/issues/1865) 请求核验勾选任务「确实实现了」。映射：验收标准符合性核验是规范驱动开发的公认空白——skyaxis 若做结构化承载，超出 spec-kit 已发布面（诚实记录，非从众理由；直抄先例是 PR-Agent）。

## 5. 重设计草案（待拍板后定稿）

### 5.1 设计原则（承 0008 配方）

1. 评审任务书加入九块族（目标/快照/输入/知识/约束/工作流/输出），评审专属措辞；dev 与其余用途零改动。
2. 回传面改动幅度按 D2/D4 拍板执行；`# skyaxis-review` 标记、proposed 播种纪律、幂等锚、完成口径默认不动（D2-A 不建新裁决环）。
3. 文档中文、不进词典（sow.ts 既有约定）；静态段纯函数常量。
4. 零发现的诚实纪律（六维逐维给结论、「未发现」+残余风险说明）与级别判据进书。

### 5.2 新模板草案（形制示意，措辞实施轮定稿）

````markdown
# 评审任务书 · <需求标题>

## 目标
为需求「<标题>」的评审阶段做一次只读代码评审：对照验收标准核验当前实现是否达成（目标一），并排查代码本身的质量风险（目标二），产出一份供需求负责人裁决的评审报告——报告读者没读过你的评审过程，只读结论与证据。两个产物：
1. 验收核验——逐条标准 × 当前代码：满足 / 不满足 / 无法核验（仅凭读代码判不了的如实标注，注明需什么人工验证），每条带证据（路径:行号）。
2. 质量发现——缺陷、安全漏洞与显著风险（六维判据见「工作流」），每条带证据与触发场景。
本阶段不改任何代码、不裁决——验收通过与处置由用户在工作台完成。

## 需求快照（工作台账本，生成时快照）
标题/描述/当前阶段；验收标准逐条 C 编号；工作包清单（±各包 commits 改动面锚——D1；零 commits 诚实缺席行）

## 输入 / 参考知识
（同今日五块版的 [输入]/[知识注入]，移形不改义）

## 约束
- 严格只读：不修改、创建、删除任何文件；不建分支、不提交、不推送；不运行代码/测试/构建（需运行才能核验的列入「无法核验」）——报告会话内交付，不写文件。
- 不裁决：核验结论与发现皆为建议，验收（通过/不通过）、处置、阶段推进全部由用户在工作台完成。
- 有据：每条核验与发现给出证据（路径:行号）；查不到依据的显式标「推测」；与参考知识冲突的发现至少「高」级并注明条目标题。
- 如实分级：不夸大影响——仅特定输入/环境才触发的问题开头说明条件；有把握才报（不确定但可能高危的，注明不确定处）；零发现如实写「未发现」并说明残余风险与未覆盖范围。
- 有限停止：仅当关键输入不可读或标准信息不足以核验时停下来问用户。

## 工作流
1. 通读基线文档与验收标准，列核验清单。
2. 定位改动面（工作包+commits 锚；缺席时以工作包边界为界），不做全库漫游；探察过的文件记入报告。
3. 逐条核验：找到对应实现→判定→记证据；跨包标准逐包注明。
4. 六维质量排查（判据示例——D3 定档）：
   - 缺陷：会实际出错的逻辑/边界/并发/资源问题（有触发场景才算）；
   - 安全：注入、输入校验、认证与会话、访问控制、敏感信息、加密误用（OWASP 六类）；
   - 性能与容量：量级、超时、资源上限、明显低效路径；
   - 复杂度与可维护性：过度设计、重复、误导性命名/注释（Google 复杂度两问）；
   - 测试：改动是否有对应测试，缺口列出；
   - 一致性：与既有实现/参考知识冲突处。
5. 汇总报告（三节），总体结论先行。
先查后问：能从代码与文档查证的自己查；只有影响结论的取舍留给需求方。

## 输出
评审结束时先给出完整报告正文（markdown），结尾附机器可读发现块。报告三节：
1. 总体结论——验收面达成概况（n 满足/m 不满足/k 无法核验）＋总体风险（高/中/低，判据）＋建议人先看的文件。
2. 验收核验——每条：C1 满足｜证据：路径:行号（或需人工验证的说明）。
3. 质量发现——每条：Q1 [维度·级别] 标题＋说明＋证据＋触发场景；级别降序；六维逐维给结论。
```yaml
# skyaxis-review
# findings 每条 = 一个待用户裁决的发现；severity: high|medium|low
#   - title: 发现标题（64 字内）
#     severity: high
#     detail: 说明与证据（路径:行号）        ← D4
findings: []
（± criteriaChecks 核验节：ref/result(satisfied|unmet|not-verifiable)/evidence ← D2-A）
```
说明：findings 只列发现（含「某标准不满足」类结论的缺陷化表达），裁决与处置由用户完成；逐条核验结论（D2-B 时）写在报告正文。
完成自检（全部满足才算收尾）：每条标准有判定与证据 · 无法核验项已列明 · 六维逐维有结论 · 每条发现有级别/证据/触发场景 · 发现块已附。
````

### 5.3 各决策点连带面预估

| 决策点 | 连带面 |
| --- | --- |
| D2-A 结构化核验 | protocol（ReviewReportEntry +criteriaChecks）→ review-parse 扩解析 → endpoint 播种（幂等收敛分支同样不重播）→ review-section 渲染核验行（信息面，不建裁决环）→ fetcher/测试跟随 |
| D2-B 散文模板 | 仅 sow.ts + sow.test.ts |
| D4-A findings +detail | protocol（ReviewVerdict +detail 可选，宿主铸行时带上）→ review-parse 校验 → 裁决表单展示证据（只读）→ 测试跟随 |
| D1-A commits 进快照 | sow.ts 快照节渲染 wp.commits（hash 短式+note；零 commits 诚实缺席行），SowContext 零新增（record 已含） |

## 6. 决策点（待用户拍板）

- **D1 形制与快照锚**：A（推荐）九块化＋快照节挂 commits 改动面锚（零 commits 诚实缺席）＋只读/不运行约束；B 保持五块最小修补（只加目标/约束两段文字，不加 commits）。
- **D2 目标一承载**：A（推荐）机器块扩 `criteriaChecks` 节（ref/三值 result/evidence），宿主播种为报告的核验行（信息展示，不建新裁决环、不改完成口径）；B 仅散文模板（报告第一节固定核验表，机器块/协议零改动）；C 不做逐条核验。
- **D3 目标二维度**：A（推荐）六维＋逐维判据（缺陷/安全 OWASP 六类/性能容量/复杂度可维护性/测试/一致性）；B 全量清单（Google 九维+OWASP 全 checklist，上下文膨胀）；C 不给维度，仅「有据+如实分级」纪律。
- **D4 findings 字段**：A（推荐）扩 `detail`（说明与证据 路径:行号，随播种行落账本，裁决表单只读展示）；B 保持 title+severity，证据纪律只约束散文。
