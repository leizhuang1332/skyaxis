> 状态：**已定稿**。本文件即 [决策 0005](../decisions/0005-AI工作台治理决策-产物独立文件存储与分级级联清理.md)「P1b 前置门收窄」指定的三项验证落盘位置；P2/P3/P5 前置全部闭环。

## 白话摘要

research 0006 把 AI 工作台的设计画好了，但有三处功能**依赖 DSH 宿主的能力**、当时无法确认「让不让做」——如同装修图纸画好，三面墙不知道是不是承重墙，动工前先问物业。本报告就是问完的答复单。**只读本节 + 结论速览即可掌握全貌**；其余章节是带源码引用的审计链，供实施时查证，不必通读。

**P0-3：AI 在等我说话时，我能不能知道？**
场景：P2 要在工作台里显示 session 卡片（●运行中 / ○待输入 / ✓已结束）。宿主的会话列表**不提供**「待输入」——列表只有「在跑 / 没在跑但有过记录 / 从没开始过」三种。但核验发现另一扇门：宿主有个**广播频道**（waterfall），AI 请求批准或提问时会向所有客户端广播「某某会话在等人」——所以「待输入」能知道，只是要从广播频道听，不能从列表看（部署面还需实机验证一次）。**意义**：P2 卡片三种状态稳了，「待输入」作为后续增量。

**P0-2：AI 的最后一段话，程序能不能自己读到？**
场景：P3 的声明块。设计是 session 结束时 AI 输出一段机器可读的 `# skyaxis-declare`，v1 靠用户**手动复制粘贴**回工作台。答案：**能，全文**——宿主有好几条正式读取通道（最强的一条连已关闭的会话都能从磁盘读回）。**意义**：P3 可以做「一键导入」，不用人肉搬运；粘贴保留为手动兜底。

**P0-1：skyaxis 能不能自己开一个 session 并把任务书填进去？**
场景：任务书投递 v1 是「复制到剪贴板 → 用户去新会话粘贴」。答案：**三档全部允许**——开新会话 ✓、预填输入框 ✓、甚至替用户按发送 ✓。但推荐只用前两档：**自动开 + 自动填，发送键留给用户**——「人握门禁」是本项目自定的纪律，替用户按发送就越线了。**意义**：P5 时「下发任务书」可以做到点一下 → 新会话已备好、文本已在输入框 → 用户回车。

## 1. P0-3 三态判定 → partial

### 1.1 摘要面事实：待输入不可判定（调查与核验一致确认）

- **SessionSummary 全部 11 字段**（`dsh-api-session-controller/lib/types/client/sessions/service.d.ts:32-55`）：`id, title?, displayTitle, cwd?, parentId?, origin?, running, completed?, blank, updatedAt, projectionValues?`——**无任何 pending-user-turn / waiting-on-user 字段**；wire 级列表行更薄（`types.d.ts:144-154`，连 title/completed 都无）。
- **基底是硬两态**：`AgentStatus = 'idle' | 'running'`（`dsh-agent/lib/types/runtime-types.d.ts:90`，注释明示 disposal 非第三可观察态）；host 侧 `running = agents.get(id)?.status === 'running'`（`dsh-api-session-controller/lib/index.js:1818`，冷会话 `summarizeCold:1848` 硬编码 false）——**没有第三个状态可上 wire**。approval 等待保持回合开启 ⇒ running 仍读 true，与真运行不可区分。
- **`completed` 是客户端通知位，非宿主事实**（`client.js:2874-2890` + `flattenLineage:574`）：仅在客户端**观察到**未选中会话的 running→idle 边沿时武装、选中即清除、**载入时已 idle 的会话永远 false**——这是 task-graph 缺陷①的根因（见 §1.3）。
- **`blank` = 未开始判别位**（空日志位，host 摘要推导镜像）——三态降级的第三态由此可得。
- 事件流确有 `approval/asked|decided|policy` 词汇与 `turn/start|turn/end{reason}`（`dsh-session/lib/types/known-event-types.js:82-84`），但客户端事件窗口仅对**当前绑定（staged）会话**开启（`connector.ts:209-212` 只订阅当前 binding；research 0003 §六同结论）；`blocked` 终因是「pre-step 拒绝并丢弃已认领消息」（`dsh-agent/lib/index.js:22-24`），不是等待。

### 1.2 核验驳回记录：waterfall 转发面（partial 的来源）

调查初判「待输入完全不可判定」被核验**驳回**，驳回要点全部经源码复核：

- **转发允许清单**：`dsh-api-remotes/lib/types/remote-events.d.ts:12-69` 将 `'approval/request'` 与 `'user-questions/request'` 连同 `agentId` 转发给**每个**浏览器客户端（waterfall 模式）；host 循环逐 agent 转发（`api-remotes/lib/index.js:115-125`）。
- **跨刷新存活**：gateway 把 pending 转发事件存 `pendingRemoteEvents`，对**每个新客户端代全量重放**（`dsh-api-gateway/lib/index.js:598`）——恰是初判用以否定可观察性的「刷新即丢」场景的反例。
- **被动参与即可追踪**：客户端被动参与 waterfall（`next()`）即可维护 per-agentId 待决状态——**含 subagent**，无需任何新宿主面设施；既有消费先例 = dsh-client-ui-chat 的 ApprovalCommand（`conversation.approval.detail`）。
- **「payload 类型缺席」系误判**：初判的缺席 grep 跑在 `node_modules/@deepseek-ai/`（symlink）上；真实 store 内 `dsh-user-approval/lib/types/types.d.ts` 声明了 approval 事件 payload，且 `dsh-api-remotes`（skyaxis **直接依赖**）经 `export type {} from '@deepseek-ai/dsh-user-approval/types'` 把类型增强带进编译（`dsh-api-remotes/lib/types/client/index.d.ts:32`）。**research 0003 §4.2「runtime 未安装时消费方看不到类型」对 approval 对不成立——修正记档**。
- **存留警示**：在装宿主的 control stream 实际只观察到 queues/jobs/projections（无 approvals/questions 转发）；实机 401 墙无法探测部署面——**能力在场、部署未证**，P2b 接线时须实机验证一次。

### 1.3 task-graph 两缺陷修法（钉死，修随 P2 动工首刀）

| 缺陷 | 根因（已核） | 修法 |
| --- | --- | --- |
| `subagents.ts:97-99` summaryStatus 谎报（跑完很久的 session 报「未开始」） | 读的是客户端通知位 `completed`——载入时已 idle 的会话永远 false ⇒ 非 running 且非 completed 全部落 pending | 改**三态派生**：`running→'running'`；`!running && !blank→'done'`；`blank→'pending'`；彻底弃用 completed 位 |
| `types.ts:15` 'waiting' 空转枚举 | 自画布 MVP 首提交（a586e39）起零生产者（`infer.ts:25` 明文「v0.3 不生成」），仅词典/CSS 支持面陪跑 | **移除**枚举成员 + dictionary/register/view/CSS 支持面；P2b 若接线 waterfall 待决追踪，再引入受数据源支撑的 'waiting'（届时有真生产者） |

### 1.4 P2 设计影响

- **实时卡片 v1 = 三态降级**：running（含 approval 等待——摘要面不可区分）/ 空闲有史（!running && !blank）/ 未开始（blank）。research 0006 §7.2「不可得则降级为运行/空闲两态」的降级条款**无需触发**——blank 白送了第三态。
- **P2b 增量 = waterfall 待决追踪**：approval/问题形态的「待输入」可从转发面判定（含 subagent、跨刷新），作为卡片第四态/角标；部署面实机验证一次后定性。

## 2. P0-2 终态抓取 → yes（全文深度）

### 2.1 事实链

- **事件日志即真源**：`assistant/message` 事件携带完整装配的 `AssistantMessage`（`ContentBlock[]` 含 text）与精确 provider 流（`dsh-session/lib/types/types.d.ts:236-242, 309-317`）——**全文滞留，无摘要/截断**；运行时提交点 `agent-loop agent.ts:473-482` 逐字 append。
- **四条读取路径**（按对 skyaxis 的适配度排序）：
  1. **`ctx.sessionQuery.readSession(sessionId)`**（`dsh-session-query/lib/types/index.d.ts:63-70`）——宿主进程内读取完整原始事件日志（**live 或冷持久均可、不激活会话**），最后一条 `assistant/message` 即终态全文。**P3 的首选路径**。
  2. **自注册投影**：`apply` 收每条已提交事件——**仓内既有先例** `src/agent-metrics.ts:100-118`（`request/header` 同款折叠），可做零轮询的终态消息快照。
  3. `agent/turn-stopping` 钩子（`dsh-agent/lib/types/runtime-types.d.ts:380-400`）——回合收口拿活 agent，`snapshotEvents()` 取冻结全文。
  4. wire `session/page` / `session/follow`（typert RPC）+ 客户端 `eventSource` 窗口——**后者 stage-gated**（仅当前绑定），不适合后台抓取。
- **磁盘兜底**：`$DSH_HOME/sessions/<cwd-slug>/<id>/session.v3.jsonl.zstd`（zstd JSONL 全量日志）+ `readColdSessionLog`（replay-validated 冷读）。
- **深 cap 面仅外围**：`session.search` snippet 240 码点、`listEvents` 仅元数据——均不影响上述路径。
- **实测**：无 plain-GET HTTP 路由（`/` 401、`/session/page` 与 `/rpc/session/page` 404）——全文读取只在 auth-gated 应用或 typert 网关协议内，不可 URL 抓取。

### 2.2 P3 设计影响

声明块自动抓取 = **host 侧 `ctx.sessionQuery.readSession(boundSessionId)` → 最后一条 `assistant/message` 全文 → 解析 `# skyaxis-declare` fenced yaml**。深度=全文，无降级需要；剪贴板导入保留为纯手动兜底（D3 拍板不变——自动深度从「未知」升级为「全文可行」）。

## 3. P0-1 编程启动 session → yes（三档全在）

### 3.1 三档能力与档位定性

| 档 | 能力（证据锚） | 档位定性（对 0006 §5.3 权责表） |
| --- | --- | --- |
| `sessions.create` | `ISessions.create()` 公共特性契约（「Create or adopt a Session on the Host」，`contract/sessions.d.ts:29-37`）→ wire `session/create` RPC → host `SessionController.create()`（`index.js:571-599`，纯业务无门禁）；GUI 的「新会话」即同方法调用方。**注意：无预填参数**——预填须走 setDraft/prompt | 「观察之外的行动」——四权清单（批准拆分/计划/验收/推进）不含 session 生命周期，**无用户专属权冲突** |
| `inputActions.setDraft` | 会话作用域 slot 组件的**标准属性**（「Replace the whole draft」）；亦可达 `ctx.conversation.input: SessionInputResolver`。浏览器侧作曲器状态（按会话持久、跨切换/刷新存活）——**连 host RPC 都不是** | 「UI 本地写」——摩擦最低的预填路径 |
| `prompt` 注入 | `ISession.prompt()` / `inputActions.submit()` 以**用户身份**发送，SDK 零强制同意门；唯一后置门 = agent 常规工具审批 | 「用户身份行动」——跨过自设同意线，需单独立项裁决 |

适配注意：skyaxis client inject 尚无 `dsh-client-ui-conversation`——走 slot-props 路线（inputActions 标准属性）**免新增 inject**；走 `ctx.conversation.input` 须加。

### 3.2 P5 设计影响（推荐形态）

**任务书投递 v2 = `create()` + `open()` + `setDraft(任务书)`，用户按下发送**。SDK 允许全自动发送（prompt 档），但 P2「人握门禁」与诚实 UI 纪律要求**发送决定留在用户手里**；预填 + 用户发送拿到「剪贴板消失」的全部收益而不越同意线。自动 prompt 列 v2+ 届时单独立项。

### 3.3 开放问题（P5 动工时验证）

- prompt 注入首轮的工具审批行为（推测与人工输入同路——待实机验证）
- blank 会话复用（`SessionSummary.blank` 注释「New Session 复用同工作区的 blank 会话」）与 `create()` 的交互——工作台「开工」流应否 adopt 既有 blank 会话
- `subagents.prompt`（SessionSubagentsRemote 支持按父地址直发 catalog 子代理）——若任务书执行应跑在协调会话的子代理里则相关
